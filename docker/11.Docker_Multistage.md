## 1. Why Multi-Stage Builds Exist — The Problem First

### The Story — Building a Car

Imagine you are building a car.

To build it, you need:
- A huge factory with welding robots
- Paint booths
- Assembly machines
- Testing equipment
- Dozens of specialist tools

But when you deliver the car to the customer, you deliver just the car.

You do NOT ship the factory with the car.
You do NOT deliver the welding robots inside the car boot.
The customer only needs the finished car — not the tools that made it.

**This is EXACTLY the problem with Docker images before multi-stage builds.**

### The Problem — Build Tools Ending Up in Production Images

When you build a Node.js application, you need during BUILD time:
- TypeScript compiler (`tsc`)
- Development dependencies (`jest`, `eslint`, `webpack`)
- Source maps and debug tools
- Test files

But at RUNTIME in production, you only need:
- Compiled JavaScript files (`dist/`)
- Production dependencies (`express`, `pg`, etc.)
- Nothing else

**Without multi-stage builds:**

```dockerfile
# Single-stage Dockerfile — everything ends up in one image
FROM node:20

WORKDIR /app

# Install ALL dependencies including devDependencies
COPY package*.json ./
RUN npm install              # includes TypeScript, Jest, Webpack, etc.

# Copy all source code
COPY . .

# Build (compile TypeScript → JavaScript)
RUN npm run build

# The image now contains:
# ✓ TypeScript compiler (not needed at runtime)
# ✓ Jest testing framework (not needed at runtime)
# ✓ Webpack (not needed at runtime)
# ✓ 800MB of node_modules (most not needed at runtime)
# ✓ Source files (.ts) (only .js files needed at runtime)
# ✓ Test files (not needed at runtime)
# Result: 1.2GB image
```

**The person deploying this gets a 1.2GB image when they only needed 120MB.**

### The Solution — Multi-Stage Builds

Multi-stage builds let you:
1. Use a FULL environment with all tools to BUILD
2. Copy ONLY the finished artifact to a MINIMAL final image
3. Discard the build environment completely

```
Stage 1 (builder):                  Stage 2 (production):
Full node:20 image (1.2GB)     →    node:20-alpine (minimal, 30MB)
All devDependencies            →    Only production deps
TypeScript compiler            →    No build tools
Source .ts files               →    Only compiled .js files
Test files                     →    No test files
─────────────────────────────────────────────────────────
Final image size: 120MB (was 1.2GB)
```

The builder stage is used and then thrown away.
It never becomes part of the final image.

## 2. What is a Multi-Stage Build?

### Simple Definition

A multi-stage build is a Dockerfile with **multiple `FROM` instructions**.

Each `FROM` starts a new stage.
Each stage is a completely separate build environment.
You can copy files FROM one stage INTO another stage.
Only the LAST stage becomes the final image (unless you target a specific stage).

### The Syntax

```dockerfile
# Stage 1 — give it a name with AS
FROM node:20-alpine AS builder
# ... do build work here ...

# Stage 2 — another FROM starts a new stage
FROM node:20-alpine AS production
# Copy FROM the builder stage
COPY --from=builder /app/dist ./dist
# ... minimal setup here ...
```

**Breaking down the new keywords:**

`AS builder` = give this stage the name `builder`.
Without a name, stages are numbered 0, 1, 2...
Names make the Dockerfile readable and let you reference stages by name.

`COPY --from=builder` = the `--from` flag on COPY tells Docker:
"Do not copy from the build context (your local machine). Copy FROM this specific stage."
`builder` = the name of the stage to copy from (matches the `AS builder` name).

### What Happens During Build

```
docker build -t myapp:1.0 .

Step 1: Docker reads the Dockerfile
Step 2: Executes Stage 1 (builder) — full build environment
Step 3: Produces artifacts (compiled code, binaries)
Step 4: Executes Stage 2 (production) — minimal base image
Step 5: COPY --from=builder copies ONLY selected files from Stage 1
Step 6: Stage 1 is DISCARDED — it never becomes part of the final image
Step 7: Stage 2 becomes the final image that gets tagged as myapp:1.0
```

The builder stage images are temporary.
After the build completes, only the final stage remains.

## 3. The Core Concept — Build Stage vs Final Stage

### What Goes in the Build Stage

Everything needed to PRODUCE the artifact:

```
Build tools:
  - Compiler (tsc, gcc, javac, go build, mvn)
  - Build systems (webpack, vite, rollup)
  - Package managers with dev dependencies (npm install, pip install)
  - Test runners (jest, pytest, go test)

Source files:
  - .ts files (TypeScript source)
  - .java files (Java source)
  - .go files (Go source)
  - .py files (Python source)
  - React JSX/TSX files

Dev dependencies:
  - TypeScript
  - Jest, Mocha (test frameworks)
  - ESLint, Prettier (code quality)
  - Webpack, Vite (bundlers)
```

### What Goes in the Final Stage

ONLY what is needed to RUN in production:

```
Artifacts:
  - Compiled JavaScript (dist/ folder)
  - Compiled Java .jar or .war
  - Compiled Go binary
  - Bundled React HTML/CSS/JS

Production dependencies only:
  - npm packages in "dependencies" (not "devDependencies")
  - Python packages from requirements.txt (not dev requirements)

Runtime:
  - Node.js runtime (if running Node.js app)
  - JRE (if running Java — not JDK)
  - Nothing (if running a static binary like Go)

NO:
  - Source files
  - Test files
  - Dev dependencies
  - Build tools
  - Compiler
```

### The Mental Model — Factory vs Product

```
FACTORY (Build Stage):           PRODUCT (Final Stage):
┌────────────────────────┐       ┌──────────────────────┐
│ Full Node.js (JDK etc) │       │ Minimal Alpine Linux  │
│ TypeScript compiler    │       │ Node.js runtime       │
│ Webpack bundler        │  →→→  │ Your compiled app     │
│ Jest test runner       │  →→→  │ Production packages   │
│ ESLint linter          │       │                       │
│ Source .ts files       │       │ That's it.            │
│ Test files             │       │                       │
│ 800MB node_modules     │       │ ~30MB node_modules    │
└────────────────────────┘       └──────────────────────┘
     1.2GB (thrown away)                120MB (shipped)
```

## 4. Multi-Stage Build — Node.js Example

This is the most common use case. Let us build it step by step.

### Project Structure

```
myapp/
├── src/
│   ├── index.ts       ← TypeScript source
│   └── routes/
│       └── user.ts
├── package.json
├── tsconfig.json
├── .dockerignore
└── Dockerfile
```

### The Single-Stage Problem (Before)

```dockerfile
# ❌ Single-stage — everything in one image
FROM node:20

WORKDIR /app
COPY package*.json ./
RUN npm install            # includes ALL devDependencies (TypeScript, etc.)
COPY . .
RUN npm run build          # compile TypeScript → dist/

CMD ["node", "dist/index.js"]

# Final image size: ~1.2GB
# Contains: compiler, devDeps, source files, test files
```

### The Multi-Stage Solution (After)

```dockerfile
# ── Stage 1: Install dependencies and build ────────────────────────────────
FROM node:20-alpine AS deps

WORKDIR /app

# Copy ONLY dependency files first (maximise layer cache)
COPY package*.json ./

# Install ALL dependencies including devDependencies
# We need TypeScript, Jest, etc. to build
RUN npm ci

# ── Stage 2: Build the TypeScript application ──────────────────────────────
FROM deps AS builder

WORKDIR /app

# Copy source code
COPY tsconfig.json ./
COPY src/ ./src/

# Compile TypeScript to JavaScript
# Output goes to /app/dist/
RUN npm run build

# ── Stage 3: Production image ──────────────────────────────────────────────
FROM node:20-alpine AS production

# Security: create non-root user
RUN addgroup -S -g 1001 appgroup && \
    adduser  -S -u 1001 -G appgroup appuser

WORKDIR /app

# Copy ONLY package files for production install
COPY package*.json ./

# Install ONLY production dependencies (no devDependencies)
# This means no TypeScript, no Jest, no Webpack — much smaller
RUN npm ci --only=production && npm cache clean --force

# Copy ONLY the compiled output from the builder stage
# This copies /app/dist/ from the builder container
COPY --from=builder /app/dist ./dist

# Set correct ownership on all files
RUN chown -R appuser:appgroup /app

# Switch to non-root user
USER appuser

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
    CMD wget -qO- http://localhost:3000/health || exit 1

CMD ["node", "dist/index.js"]
```

**Line by line explanation of the key parts:**

`FROM node:20-alpine AS deps` = start stage 1, name it `deps`.
`node:20-alpine` = Node.js 20 on Alpine Linux (smaller than `node:20` on Debian).

`RUN npm ci` vs `RUN npm install`:
`npm ci` = "clean install". Installs EXACTLY what is in `package-lock.json`. Faster and more reproducible than `npm install`. Preferred in CI/CD.

`FROM deps AS builder` = start stage 2, name it `builder`.
This stage STARTS FROM the `deps` stage — it inherits everything deps installed.
This avoids running `npm ci` again in this stage.

`RUN npm run build` = runs the `build` script from `package.json`.
Usually this means `"build": "tsc"` — running TypeScript compiler.
Output is TypeScript compiled to JavaScript in the `dist/` folder.

`FROM node:20-alpine AS production` = start the FINAL stage.
A fresh Alpine-based image. Nothing from previous stages — clean slate.

`COPY --from=builder /app/dist ./dist` = the key instruction.
`--from=builder` = source is the `builder` stage (not your local machine).
`/app/dist` = the path INSIDE the builder stage to copy from.
`./dist` = where to put it in the current stage (relative to WORKDIR `/app`).

`npm ci --only=production` = install only production dependencies.
`--only=production` = skip everything in `devDependencies`. No TypeScript. No Jest. Much smaller.

### Size Comparison

```
Before multi-stage: ~1.2GB
After multi-stage:  ~120MB
Reduction:          90% smaller
```

## 5. Multi-Stage Build — Go Binary Example

Go is the best language for demonstrating multi-stage build power.
A Go application compiles to a SINGLE STATIC BINARY.
That binary has no external dependencies.
The final image can be `FROM scratch` — literally nothing.

### Why Go + Scratch = Incredibly Small Images

```
Go source code + go compiler → single binary
That binary needs: nothing (statically linked)
Final image: the binary only
Result: 5-15MB image instead of 800MB+
```

### The Dockerfile

```dockerfile
# ── Stage 1: Build the Go binary ──────────────────────────────────────────
FROM golang:1.22-alpine AS builder

# Install git for go module downloads that need it
RUN apk add --no-cache git

WORKDIR /app

# Copy dependency files first (for layer cache)
COPY go.mod go.sum ./

# Download dependencies
# This layer is cached unless go.mod or go.sum changes
RUN go mod download

# Copy all Go source files
COPY . .

# Build the binary
# CGO_ENABLED=0 = disable C interop, produce a pure Go static binary
# GOOS=linux    = target operating system (Linux)
# -o myapp      = output binary name
# .             = build the main package in current directory
RUN CGO_ENABLED=0 GOOS=linux go build -o myapp .

# ── Stage 2: Minimal final image ──────────────────────────────────────────
FROM scratch

# scratch = completely empty image. No OS, no shell, no tools.
# Only works if the binary is truly static (CGO_ENABLED=0)

# Copy the binary from builder
COPY --from=builder /app/myapp /myapp

# Copy TLS certificate authorities
# Needed if the binary makes HTTPS requests to external services
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/

EXPOSE 8080

# Run the binary directly (no shell available in scratch)
ENTRYPOINT ["/myapp"]
```

**Breaking down the Go build command:**

`CGO_ENABLED=0` = an environment variable. Disables CGO (C Go).
CGO = the mechanism to call C libraries from Go.
When CGO is enabled, the binary links against system C libraries (glibc).
These libraries must exist on the runtime system.
With `CGO_ENABLED=0`, the binary is completely self-contained. All code compiled in.

`GOOS=linux` = target operating system. Even if you build on macOS, this produces a Linux binary.

`go build -o myapp .` = build the package in the current directory.
`-o myapp` = name the output binary `myapp`.

**Why copy ca-certificates?**

Even though `scratch` has nothing, your Go app might make HTTPS requests (to AWS APIs, databases, etc.).
HTTPS requires validating SSL certificates against known Certificate Authorities.
The CA certificates file (`ca-certificates.crt`) contains all trusted CAs.
Without this file, your app would reject ALL HTTPS connections.

### Size Comparison

```
golang:1.22-alpine build image:  ~350MB
Final scratch image:             ~8MB
Reduction:                       97.7% smaller
```

## 6. Multi-Stage Build — Java Maven Example

Java is another great example.
Building requires the full JDK (Java Development Kit).
Running only requires the JRE (Java Runtime Environment — smaller than JDK).

```dockerfile
# ── Stage 1: Build with Maven and full JDK ────────────────────────────────
FROM maven:3.9-eclipse-temurin-17 AS builder

WORKDIR /app

# Copy pom.xml first (dependency file)
COPY pom.xml .

# Download dependencies without building
# This layer is cached unless pom.xml changes
RUN mvn dependency:resolve -q

# Copy source code
COPY src ./src

# Build the application, skip tests
# -DskipTests = do not run tests during Docker build
# (run tests separately in CI before building the image)
RUN mvn package -DskipTests -q

# The .jar file is in /app/target/

# ── Stage 2: Minimal runtime with JRE only ────────────────────────────────
FROM eclipse-temurin:17-jre-alpine AS production

# JRE (runtime only) is about 80MB
# JDK (full development kit) is about 200MB+

# Non-root user
RUN addgroup -S -g 1001 appgroup && \
    adduser -S -u 1001 -G appgroup appuser

WORKDIR /app

# Copy the compiled JAR from builder
COPY --from=builder /app/target/*.jar app.jar

RUN chown appuser:appgroup app.jar

USER appuser

EXPOSE 8080

# JVM flags for container awareness
# -XX:+UseContainerSupport = JVM reads cgroup memory limits (not host RAM)
# -XX:MaxRAMPercentage=75.0 = use 75% of available container memory for heap
ENTRYPOINT ["java", \
    "-XX:+UseContainerSupport", \
    "-XX:MaxRAMPercentage=75.0", \
    "-jar", "app.jar"]
```

**Breaking down JVM flags:**

`-XX:+UseContainerSupport` = tells the JVM to read container memory limits from cgroups instead of total host RAM.
Without this: a JVM in a 512MB container on a 64GB server sets heap to ~48GB (75% of 64GB). OOMKilled immediately.
With this: JVM reads the 512MB cgroup limit and sizes heap correctly.

`-XX:MaxRAMPercentage=75.0` = use 75% of the available container memory for the Java heap.
Leave 25% for non-heap memory (code cache, thread stacks, etc.).

`mvn dependency:resolve` = downloads all Maven dependencies listed in `pom.xml` into the local Maven cache.
Separating this from `mvn package` means: if only source code changes (not pom.xml), the dependency download is cached.

### Size Comparison

```
maven:3.9-eclipse-temurin-17 (build): ~600MB
eclipse-temurin:17-jre-alpine (final): ~200MB
Reduction: 67% smaller
```

## 7. Multi-Stage Build — Python Example

Python has two approaches depending on the type of application.

### Approach 1 — Pure Python App (No Compilation)

```dockerfile
# ── Stage 1: Install dependencies ─────────────────────────────────────────
FROM python:3.12-slim AS deps

WORKDIR /app

# Install build dependencies needed for some Python packages
# (some packages compile C extensions during pip install)
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc \
    libpq-dev \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .

# Install to a specific directory
# --prefix=/install = install packages to /install directory
# Makes it easy to copy just the packages to the next stage
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ── Stage 2: Production image ──────────────────────────────────────────────
FROM python:3.12-slim AS production

# Non-root user
RUN useradd -r -u 1001 -g root appuser

WORKDIR /app

# Copy installed packages from deps stage
COPY --from=deps /install /usr/local

# Copy only application code (no test files, no requirements.txt)
COPY --chown=appuser:root src/ ./src/
COPY --chown=appuser:root app.py .

USER appuser

EXPOSE 5000

CMD ["python", "app.py"]
```

**Key Python-specific point:**

`pip install --prefix=/install` = install packages into a custom directory instead of the system Python location.
`/install` inside the builder stage becomes the isolated package directory.
Then `COPY --from=deps /install /usr/local` copies them into the standard Python location in the final image.

This trick lets you install packages (including compile C extensions) in the builder, then copy only the compiled result — not the compiler tools — to the final image.

### Approach 2 — Python with Wheel Pre-building

```dockerfile
# ── Stage 1: Build Python wheels (compiled packages) ──────────────────────
FROM python:3.12-slim AS builder

# Install C compiler (needed to build wheels)
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc \
    g++ \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .

# Build wheels (binary packages) for all dependencies
# A wheel (.whl) is a pre-compiled Python package
RUN pip wheel --no-cache-dir --no-deps --wheel-dir /wheels -r requirements.txt

# ── Stage 2: Production (no compiler needed) ───────────────────────────────
FROM python:3.12-slim AS production

WORKDIR /app

# Install from pre-built wheels — no compiler needed!
COPY --from=builder /wheels /wheels
RUN pip install --no-cache-dir --no-index --find-links=/wheels /wheels/* && \
    rm -rf /wheels

COPY app.py .

USER nobody

EXPOSE 5000
CMD ["python", "app.py"]
```

`pip wheel --wheel-dir /wheels` = download and compile all packages into `.whl` files (binary wheels).
In the final stage, `pip install --no-index --find-links=/wheels` installs from these pre-built wheels.
No compiler needed in the final image — the compilation already happened in the builder stage.

## 8. Multi-Stage Build — React Frontend Example

React applications need Node.js to build but only need a static file server to run.

```dockerfile
# ── Stage 1: Build the React app ──────────────────────────────────────────
FROM node:20-alpine AS builder

WORKDIR /app

# Dependency installation first (cache optimisation)
COPY package*.json ./
RUN npm ci

# Copy source
COPY . .

# Build for production
# Output: /app/build/ (Create React App) or /app/dist/ (Vite)
RUN npm run build

# ── Stage 2: Serve with nginx (no Node.js at all!) ────────────────────────
FROM nginx:1.25-alpine AS production

# Copy built static files from React build
COPY --from=builder /app/build /usr/share/nginx/html

# Copy custom nginx configuration (optional)
COPY nginx.conf /etc/nginx/nginx.conf

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

**The power of this pattern:**

The builder stage has full Node.js (to run webpack/vite and produce HTML/CSS/JS).
The final image has ONLY nginx — a web server serving static files.
Node.js is completely gone from the final image.

```
node:20-alpine (builder): ~150MB
nginx:1.25-alpine (final):  ~41MB
The Node.js runtime:          completely removed
Your React app:              compiled to HTML + CSS + JS (maybe 2MB)
Final image size:            ~43MB (was 150MB+ with Node in it)
```

### Custom nginx.conf for React Router

If your React app uses React Router (client-side routing), you need a custom nginx config:

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    # For React Router — send all requests to index.html
    # React Router handles routing client-side
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Cache static assets
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
}
```

## 9. Advanced Multi-Stage Techniques

### Technique 1 — Naming Stages and Targeting Specific Stages

```dockerfile
FROM node:20-alpine AS base
# ... setup common to all stages ...

FROM base AS test
RUN npm ci
COPY . .
CMD ["npm", "test"]

FROM base AS development
RUN npm ci
COPY . .
CMD ["npm", "run", "dev"]

FROM base AS builder
RUN npm ci --only=production
COPY . .
RUN npm run build

FROM node:20-alpine AS production
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/index.js"]
```

Target a specific stage:
```bash
# Run only up to the test stage
docker build --target test -t myapp:test .

# Run only up to development stage
docker build --target development -t myapp:dev .

# Build the full production image (default — last stage)
docker build -t myapp:prod .
```

`--target test` = build stops at the stage named `test`. Useful in CI pipelines.

### Technique 2 — Multiple COPY --from Sources

You can copy from multiple different stages in one final stage:

```dockerfile
FROM node:20-alpine AS frontend-builder
COPY frontend/ .
RUN npm ci && npm run build

FROM golang:1.22-alpine AS backend-builder
COPY backend/ .
RUN CGO_ENABLED=0 go build -o api .

FROM alpine:3.19 AS production
# Copy from BOTH builder stages
COPY --from=frontend-builder /app/build /var/www/html
COPY --from=backend-builder /app/api /usr/local/bin/api

CMD ["/usr/local/bin/api"]
```

### Technique 3 — COPY --from a Public Registry Image

You can copy files from ANY Docker image — not just stages in your Dockerfile:

```dockerfile
FROM node:20-alpine

# Copy binaries from official images instead of installing them
COPY --from=golang:1.22-alpine /usr/local/go/bin/go /usr/local/bin/go
COPY --from=alpine:3.19 /bin/sh /bin/sh

# This avoids running apt-get install or package managers
# You get pre-built binaries directly
```

### Technique 4 — BuildKit Cache Mounts in Multi-Stage

Combine multi-stage with BuildKit cache mounts for even faster builds:

```dockerfile
# syntax=docker/dockerfile:1

FROM node:20-alpine AS deps
WORKDIR /app
COPY package*.json ./

# Cache mount: the npm cache persists between builds
# Even if package.json changes, npm reuses cached package tarballs
RUN --mount=type=cache,target=/root/.npm \
    npm ci

FROM deps AS builder
COPY . .
RUN npm run build

FROM node:20-alpine AS production
WORKDIR /app
COPY package*.json ./

RUN --mount=type=cache,target=/root/.npm \
    npm ci --only=production

COPY --from=builder /app/dist ./dist
CMD ["node", "dist/index.js"]
```

`--mount=type=cache,target=/root/.npm` = this directory is a persistent cache between builds.
When you run `npm ci`, it downloads packages to `/root/.npm` cache first, then installs from there.
On the next build, packages are already in the cache — much faster downloads.

### Technique 5 — Using ARG in Multi-Stage for Flexible Builds

```dockerfile
# Allow choosing which stage to build optimise for
ARG BUILD_ENV=production

FROM node:20-alpine AS builder
ARG BUILD_ENV
COPY package*.json ./
RUN npm ci
COPY . .
RUN if [ "$BUILD_ENV" = "production" ]; then npm run build; else npm run build:dev; fi

FROM node:20-alpine AS production
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/index.js"]
```

```bash
# Build for production
docker build -t myapp:prod .

# Build with development optimizations
docker build --build-arg BUILD_ENV=development -t myapp:dev .
```

## 10. Choosing the Right Final Stage Base Image

The final stage base image determines the minimum size and security profile.

### Option 1 — Alpine (~5MB base)

```dockerfile
FROM alpine:3.19
```

Pros: tiny, fewer packages = fewer CVEs
Cons: uses musl libc (not glibc) — some apps have compatibility issues
Best for: Go binaries, simple shell scripts, nginx

### Option 2 — Distroless (Google)

```dockerfile
FROM gcr.io/distroless/nodejs20-debian12
```

Distroless images contain:
- The language runtime (Node.js, Python, Java)
- Standard library
- CA certificates
- timezone data

They do NOT contain:
- Shell (`sh`, `bash`)
- Package manager (`apt`, `apk`)
- Any development tools

Pros: smaller attack surface (no shell = attacker cannot get interactive access), based on trusted Debian packages
Cons: cannot use `docker exec ... sh` for debugging (no shell!), slightly larger than alpine

```dockerfile
# Node.js distroless example
FROM gcr.io/distroless/nodejs20-debian12

WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules

# No USER needed — distroless runs as non-root by default
# No CMD, use ENTRYPOINT in exec form
ENTRYPOINT ["node", "dist/index.js"]
```

### Option 3 — Scratch (Empty)

```dockerfile
FROM scratch
```

Absolutely nothing — 0 bytes.
Only usable for statically compiled binaries (Go, Rust).

Pros: smallest possible, no attack surface at all
Cons: no shell, no debugging tools, binary must be completely self-contained

### Option 4 — Language-Specific Slim Images


## 11. How Much Size Reduction to Expect

### Real Numbers From Common Stacks

| Application Type | Single Stage | Multi-Stage | Reduction |
|-----------------|-------------|-------------|-----------|
| Node.js TypeScript API | 1.2GB | 120MB | 90% |
| React Frontend | 400MB | 43MB | 89% |
| Go REST API | 350MB | 8MB | 97.7% |
| Java Spring Boot | 600MB | 200MB | 67% |
| Python Flask API | 1.0GB | 200MB | 80% |

### Why Size Matters in Production

**Build and deployment speed:**
- 1.2GB image takes ~2-3 minutes to push/pull on a typical CI connection
- 120MB image takes ~15 seconds
- 10 deployments per day × 2.5 min saved = 25 minutes per day
- 500 deployments per month = 12+ hours saved

**Storage costs:**
- AWS ECR charges per GB stored and transferred
- 10× smaller image = 10× lower storage cost
- With many images (every commit), this adds up

**Security:**
- Every package in the image is a potential CVE
- 1.2GB has hundreds of packages → hundreds of potential vulnerabilities
- 8MB binary has almost none
- Smaller attack surface = less to patch = less to scan

**Auto-scaling:**
- Kubernetes starts a new pod when traffic spikes
- Pod pulls image before starting
- 1.2GB image: new pod takes 3 minutes to start
- 8MB image: new pod starts in seconds
- This is the difference between catching a traffic spike and missing it

### Lab 3 — Target a Specific Stage

```bash

WORKDIR /app
COPY package*.json ./
RUN npm install

FROM base AS test
COPY . .
RUN echo "Running tests..." && echo "All tests passed!"

COPY src/ ./src/
RUN npm run build

# Build ONLY up to test stage
```

Useful in CI pipelines:

```bash
docker build --target production -t myapp:prod .  # build for deploy
```

### Lab 6 — Measure Build Cache Efficiency

```bash
cd /home/$USER/docker-labs/multistage-lab

cat > Dockerfile.cache << 'EOF'
FROM node:20-alpine AS builder
WORKDIR /app

# GOOD ORDER: package files first (changes rarely)
COPY package*.json ./
RUN npm install    # cached unless package*.json changes

# Source code second (changes frequently)
COPY src/ ./src/
RUN npm run build  # only rebuilds when src/ changes

FROM node:20-alpine AS production
WORKDIR /app
COPY package*.json ./
RUN npm install --only=production
COPY --from=builder /app/dist ./dist
CMD ["node", "dist/app.js"]
EOF

# First build — everything downloads (no cache)
time docker build -f Dockerfile.cache -t cache-test:1 .

# Second build — fully cached (no changes)
time docker build -f Dockerfile.cache -t cache-test:2 .
# Notice: much faster — "Using cache" for most steps

# Change source code only
echo "// small change" >> src/app.js
time docker build -f Dockerfile.cache -t cache-test:3 .
# npm install is CACHED (package*.json unchanged)
# Only src copy and build re-run
```

Observe the time difference. Good layer ordering + multi-stage = fast builds in CI.

```bash
# Clean up
docker rmi cache-test:1 cache-test:2 cache-test:3 2>/dev/null
```

## 13. Quick Revision Cheatsheet

| Concept | Summary |
|---------|---------|
| Multi-stage build | Dockerfile with multiple FROM instructions |
| Build stage | Full toolchain for building/compiling |
| Final stage | Minimal image with only what is needed to RUN |
| `AS name` | Give a stage a name for reference |
| `COPY --from=name` | Copy files from a named stage |
| `--target name` | Build only up to a specific stage |
| Why use it | Reduce image size, remove build tools, improve security |
| `CGO_ENABLED=0` | Produce static Go binary (no external library dependencies) |
| `FROM scratch` | Empty base — for static binaries only |
| Distroless | Language runtime only — no shell, no package manager |

| Pattern | Use For |
|---------|---------|
| node build → node:alpine runtime | TypeScript/JavaScript apps |
| golang build → scratch | Go static binaries |
| maven build → eclipse-temurin JRE | Java/Spring Boot apps |
| node build → nginx:alpine | React/Vue/Angular frontends |
| python build wheels → python:slim | Python apps with C extensions |

| Command | What It Does |
|---------|-------------|
| `docker build -t image:tag .` | Build using last stage as final image |
| `docker build --target stage-name .` | Build only up to this stage |
| `COPY --from=stage-name /src /dest` | Copy from a previous stage |
| `COPY --from=image:tag /src /dest` | Copy from any Docker Hub image |
| `docker images` | See all images and their sizes |
| `docker history image:tag` | See all layers and sizes |
| `docker run --rm wagoodman/dive image:tag` | Visually explore layers |

| Key Rules | Remember |
|-----------|---------|
| Layer order | Least-frequently-changed at top, most-frequently-changed at bottom |
| One final stage | The last FROM becomes the image you push |
| Build stage is discarded | Intermediate stages are NOT in the final image |
| `--only=production` | npm flag to exclude devDependencies |
| `-DskipTests` | Maven flag to skip tests during build |
| `CGO_ENABLED=0` | Go flag for static binary (required for scratch base) |
