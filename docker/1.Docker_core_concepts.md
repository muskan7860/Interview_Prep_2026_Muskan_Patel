## 1. Why Did Docker Come? The Problem Before Docker

### 🧠 Simple Story First

Imagine you build an app on your laptop. It works perfectly.
You send it to your friend (or your production server). They say:

> **"It's not working on my machine!"**

Why? Because their machine has:
- A different OS version
- Different libraries installed
- Different environment variables
- Different Python/Node/Java version

This was the **biggest problem** in software teams before Docker.

### 🏭 The Old Way — Virtual Machines (VMs)

Before Docker, teams used **Virtual Machines** to solve this.

A VM is like having a **full separate computer inside your computer**.
- It has its own OS, its own kernel, its own memory
- It solves the "works on my machine" problem
- BUT it is **very heavy** — each VM is 10–20 GB
- Takes **minutes to start**
- You can run maybe 5–10 VMs on one machine

### 🐳 Docker Came and Changed Everything

Docker introduced **containers**.

A container is like a **lightweight VM** — but it shares the host machine's OS kernel.
- Starts in **seconds**
- Uses **MBs instead of GBs**
- You can run **hundreds** of containers on one machine
- Ships your app with everything it needs — code, libraries, config

> **One-line answer for interviews:**
> *"Docker solves the 'works on my machine' problem by packaging the application and all its dependencies into a portable container that runs consistently across any environment."*

## 2. What is Docker? Simple Explanation

### 🎯 Analogy — Shipping Container

Think about how shipping works in the real world.

Before shipping containers existed, every ship had to load goods differently — boxes, barrels, sacks — it was a mess. Workers had to know exactly what each ship could carry.

Then someone invented the **standard shipping container**.
- Every container is the same shape and size
- Any ship, train, or truck can carry it
- You pack your goods inside — nobody cares what's inside

**Docker works the same way:**
- You pack your app + its dependencies inside a **Docker container**
- Any machine running Docker can run that container
- The machine doesn't need to know what's inside

### 🏗️ What Docker Actually Is

Docker is a **platform** (a tool + set of standards) that lets you:

| Action | What it means |
|--------|--------------|
| **Build** | Create an image from a Dockerfile |
| **Ship** | Push the image to a registry (Docker Hub, ECR) |
| **Run** | Start a container from that image anywhere |

### 🧩 Main Components of Docker

```

│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │

│  │(Recipe)  │→ │(Snapshot)│→ │(Running) │  │
│  └──────────┘  └──────────┘  └──────────┘  │

│               ┌──────────┐                  │
│               │ Registry │                  │
│               │(Storage) │                  │

└─────────────────────────────────────────────┘
```

## 3. Image vs Container

### 🧠 Simple Analogy

| Concept | Real World Example |
|---------|-------------------|
| **Image** | A **recipe** (or a class in programming) |
| **Container** | A **cooked dish** made from that recipe (or an object) |

You can cook the same recipe 10 times and get 10 dishes.
You can run the same image 10 times and get 10 containers.

The **recipe doesn't change** when you cook. Same with images — they are **read-only**.

### 📋 Technical Definition

**Image:**
- A read-only, immutable filesystem snapshot
- Built from a Dockerfile
- Made of multiple layers stacked on top of each other
- Stored in a registry (Docker Hub, ECR, GCR)
- Identified by a SHA256 digest (e.g., `sha256:abc123...`)
- Tagged for human use (e.g., `myapp:1.0.0`, `nginx:latest`)

**Container:**
- A running instance of an image
- Has a **thin writable layer** on top of the image layers
- Has its own **namespaces** (isolated environment)
- Has **cgroup limits** (resource control)
- Ephemeral by default — when you delete it, the writable layer is gone

### 🔑 Key Differences Table

| Feature | Image | Container |
|---------|-------|-----------|
| State | Read-only, immutable | Has a writable layer on top |
| Storage | Registry / local cache | Runs on host machine |
| Identity | SHA256 digest + tag | Container ID + name |
| Lifetime | Permanent (until deleted) | Ephemeral (temporary) |
| Multiple instances | One image | Many containers from one image |
| Data persistence | No | Only via volumes |

### 💡 Important Interview Point

> *"Multiple containers from the same image share all the read-only layers. Only the thin writable layer is unique per container. This is why Docker is so efficient — no data is duplicated."*

## 4. Layers — How Docker Builds Things

### 🧠 Simple Analogy — Transparent Sheets

Imagine you are making a drawing using **transparent sheets** stacked on top of each other.

- Sheet 1 (bottom): Background color
- Sheet 2: A house shape
- Sheet 3: Trees
- Sheet 4: Your name on top

When you look from above, you see everything combined.
If you remove Sheet 4, Sheets 1–3 are still there unchanged.

**Docker layers work exactly like this.**

### 📦 How Layers Are Created

Every instruction in a Dockerfile that **changes the filesystem** creates a new layer.

```dockerfile
FROM ubuntu:22.04          # Layer 1 — base OS
RUN apt-get update         # Layer 2 — update package list
RUN apt-get install -y python3  # Layer 3 — install python
COPY app.py /app/          # Layer 4 — copy your code
RUN pip install flask      # Layer 5 — install flask
```

```
┌─────────────────────────────────┐  ← Container writable layer (CoW)
├─────────────────────────────────┤
│   Layer 5: pip install flask    │
├─────────────────────────────────┤
│   Layer 4: COPY app.py          │
├─────────────────────────────────┤
│   Layer 3: install python3      │
├─────────────────────────────────┤
│   Layer 2: apt-get update       │
├─────────────────────────────────┤
│   Layer 1: ubuntu:22.04 base    │
└─────────────────────────────────┘
```

### ⚡ Layer Caching — Why Layer Order Matters

Docker **caches** each layer. If a layer hasn't changed, Docker reuses it from cache. This makes builds fast.

**But if one layer changes, ALL layers BELOW it are rebuilt.**

```dockerfile
# ❌ BAD ORDER — any code change rebuilds npm install
COPY . .               # If any file changes → cache MISS here
RUN npm install        # This runs again every time!

# ✅ GOOD ORDER — npm install cached unless package.json changes
COPY package.json .    # Only changes when dependencies change
RUN npm install        # Cached! Fast!
COPY . .               # Only app code here
```

> **Interview insight:** *"I always order Dockerfile instructions from least-frequently-changed to most-frequently-changed to maximize layer cache hits and speed up CI/CD build times."*

## 5. Union Filesystem (OverlayFS)

> 🟡 **Read this slowly. Every word is explained. No assumptions.**

---

### 🧠 Step 1 — What is a Filesystem? (Start from Zero)

Before we talk about Union Filesystem, let's understand what a **filesystem** is.

A **filesystem** is simply how your computer **stores and organises files**.

Think of it like this:
- Your laptop has a hard disk
- On that hard disk, files are stored in folders
- The filesystem is the system that decides: where is each file, what is its name, who can read it

On Linux (Ubuntu), the filesystem starts from `/` which is called **root**.
Everything on your computer lives inside `/`.

```
/                     ← root, top of everything
├── etc/              ← configuration files
├── home/             ← user home folders
├── var/              ← variable data, logs
└── usr/              ← programs and tools
```

This is your normal Linux filesystem. Simple.

---

### 🧠 Step 2 — What is a Union Filesystem?

A **Union Filesystem** means: **take multiple folders and show them as ONE single folder**.

You are combining (unioning) multiple directories into one view.

**Simple real-life story:**

Imagine you have **3 notebooks**:
- Notebook 1: Has chapter 1 and chapter 2 written
- Notebook 2: Has chapter 3 and chapter 4 written
- Notebook 3: Is blank — you use this to write new notes

Now imagine magic glasses that let you see all 3 notebooks as **one single notebook**.
- You can read chapters 1, 2, 3, 4 (from notebooks 1 and 2)
- When you write something new, it goes into Notebook 3 (the blank one)
- Notebooks 1 and 2 are **never changed**. They stay exactly as they are.

That is exactly what a Union Filesystem does with Docker layers.

---

### 🧠 Step 3 — How Docker Uses Union Filesystem

When Docker builds an image, it creates **layers** (we learned this in Section 4).

Each layer is a **folder on your hard disk** with some files in it.

When a container starts, Docker uses **OverlayFS** to show all those layer folders as **one single filesystem** to the container.

The container thinks it has a normal Linux filesystem. It does not know it is actually looking at many folders merged together.

---

### 🧠 Step 4 — What is OverlayFS?

**OverlayFS** is the specific technology Linux uses to do this merging.

"Overlay" means **place on top of**.

Docker uses OverlayFS to stack layers on top of each other.

OverlayFS needs 4 things to work:

---

#### 📁 The 4 Parts of OverlayFS — Explained Simply

**Part 1 — lowerdir (Read-Only Layers)**

This is all the image layers stacked together.
These are **read-only** — nothing can change these.
Think of it as the printed pages of a book — you can read them, but you cannot change the printing.

**Part 2 — upperdir (Writable Layer)**

This is the container's own private scratch area.
When the container creates or changes a file, it goes here.
Think of it as a **blank sticky note** that you paste on top of the book page.

**Part 3 — merged (The Combined View)**

This is what the container actually sees.
It is the book pages (lowerdir) + your sticky notes (upperdir) shown as one.
The container does not know about lowerdir or upperdir separately. It just sees one filesystem.

**Part 4 — workdir (Internal Helper)**

This is OverlayFS's private scratch space to do its internal work.
You never touch this. OverlayFS uses it internally.
Think of it as the editor's desk — you never sit there, but the editor needs it.

---

### 🗂️ Where Does All This Live on Your Ubuntu Machine?

When you install Docker on Ubuntu, Docker stores everything inside this folder:

```
/var/lib/docker/
```

**What is `/var/lib/docker/`?**

- `/var` = a folder on your Ubuntu system for data that changes over time (variable data)
- `/var/lib` = a folder for application data that applications store permanently
- `/var/lib/docker/` = the folder where Docker stores ALL its data — images, containers, layers, volumes

Inside it, layers are stored here:

```
/var/lib/docker/overlay2/
```

Let's look at what is inside:

```
/var/lib/docker/overlay2/
│
├── abc123def456/          ← one layer (each gets a unique ID)
│   ├── diff/              ← the actual files that this layer adds or changes
│   ├── link               ← a short nickname for this layer (used internally)
│   └── lower              ← tells OverlayFS which layers are below this one
│
├── xyz789ghi012/          ← another layer
│   ├── diff/
│   ├── link
│   └── lower
│
└── container-layer-id/    ← the running container's own layer
    ├── diff/              ← where container's writes go (upperdir)
    ├── merged/            ← the combined view the container sees
    └── work/              ← OverlayFS internal helper (workdir)
```

**Breaking down each folder:**

`diff/` — This folder contains the actual file changes for that layer.
For example, if a layer installs nginx, the `diff/` folder contains the nginx binary, its config files, etc.

`link` — A short ID file. OverlayFS uses short IDs to avoid path length limits on Linux.

`lower` — A text file listing which layers are below this one.
Example content: `ABCD:EFGH:IJKL` — these are the IDs of the layers below.

`merged/` — Only exists on container layers. This is the magic combined view.
When the container opens a file, it is opening a file from `merged/`.

---

### 🧠 Step 5 — Copy-on-Write (CoW) Explained Simply

**CoW = Copy on Write**

This is the rule OverlayFS follows when a container tries to change a file.

**The rule is:**
> A container cannot directly change a file in the lower (read-only) layers.
> It must first COPY the file to its own writable layer (upperdir).
> Then it can change the copy.
> The original in lowerdir is NEVER touched.

**Story to remember:**

Imagine you have a **library book** (lowerdir — read-only).
You want to make notes on page 10.
You cannot write in the library book.
So you **photocopy page 10** and take it home (copy to upperdir).
Now you write your notes on your photocopy.
The library book stays clean and unchanged.

When someone else (another container) reads page 10, they still get the original library book page — not your photocopy.

---

### 🔬 Full Picture — What Happens When Container Reads and Writes

**Reading a file:**

```
Container wants to read /etc/nginx/nginx.conf

OverlayFS checks upperdir first → not there
OverlayFS checks lowerdir layers → found in Layer 3
Container reads the file from Layer 3
```

**Writing to a file:**

```
Container wants to modify /etc/nginx/nginx.conf

Step 1: OverlayFS finds the file in lowerdir (Layer 3)
Step 2: OverlayFS copies the ENTIRE file to upperdir
Step 3: Container's change is applied to the copy in upperdir
Step 4: Next time container reads the file, upperdir version is shown
        (upperdir always wins over lowerdir for the same filename)

Layer 3 original is NEVER changed.
```

**Creating a new file:**

```
Container creates /tmp/myfile.txt

Step 1: File does not exist in lowerdir at all
Step 2: OverlayFS creates it directly in upperdir
Step 3: Done. Simple.
```

**Deleting a file:**

```
Container deletes /etc/hostname

Step 1: OverlayFS cannot remove it from lowerdir (read-only)
Step 2: OverlayFS creates a special "whiteout" file in upperdir
        A whiteout is like a black sticker that hides the file below
Step 3: When container looks for /etc/hostname — OverlayFS sees the whiteout
        and hides the original. File appears deleted to the container.
```

---

### ⚠️ Important Interview Point About CoW

> *"If a container modifies a very large file — for example a 500MB log file — OverlayFS copies the ENTIRE 500MB file to the container's writable layer first, even if the container only changed one line. This is why you should never store large data inside containers. Always use Docker volumes for data that needs to persist or that changes frequently."*

---

### 🔑 Full Summary — OverlayFS in One Picture

```
What the container sees (merged view):
┌─────────────────────────────────┐
│  /etc/nginx/nginx.conf          │  ← from upperdir (container changed it)
│  /tmp/myfile.txt                │  ← from upperdir (container created it)
│  /usr/bin/nginx                 │  ← from Layer 3 lowerdir (read from image)
│  /bin/bash                      │  ← from Layer 1 lowerdir (base OS)
└─────────────────────────────────┘

What actually exists on disk:
upperdir:  nginx.conf (modified copy), myfile.txt (new file)
lowerdir:  Layer 3 → nginx binary
           Layer 2 → some other files
           Layer 1 → base OS files (bash, ls, etc.)
```

The container sees ONE clean filesystem.
Underneath, OverlayFS is silently merging everything.

## 6. Linux Namespaces — Isolation

### 🧠 Simple Analogy

Imagine you are in a **co-working space**.

Everyone shares the same building (the host machine / Linux kernel).
But each company has its own **private office** with:
- Their own door (network)
- Their own whiteboard (filesystem)
- Their own employee list (process list)
- Their own company name (hostname)

They can't see into each other's offices. That's **namespace isolation**.

### 🔑 The 6 Namespaces Docker Uses

| Namespace | What it isolates | Simple Example |
|-----------|-----------------|----------------|
| **pid** | Process IDs | Container's PID 1 is isolated from host PIDs |
| **net** | Network stack | Container has its own IP, ports, routing table |
| **mnt** | Filesystem mount points | Container sees its own `/` (root filesystem) |
| **uts** | Hostname | Container can have its own hostname |
| **ipc** | Shared memory, semaphores | Isolated inter-process communication |
| **user** | User and Group IDs | UID 0 inside container ≠ UID 0 on host (rootless) |

### ⚠️ Critical Point — Shared Kernel

```
┌─────────────────────────────────────────────┐
│              Host Machine                    │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │Container1│  │Container2│  │Container3│  │
│  │(own ns)  │  │(own ns)  │  │(own ns)  │  │
│  └──────────┘  └──────────┘  └──────────┘  │
│                                             │
│  ══════════ SHARED HOST KERNEL ═══════════  │
└─────────────────────────────────────────────┘
```

> **This is the key difference between containers and VMs:**
> Containers share the host kernel. A kernel vulnerability affects ALL containers on the host.
> For untrusted or multi-tenant workloads, use gVisor or kata-containers (which give each container its own kernel).

## 7. cgroups — Resource Control

> 🟡 **Every term explained. Read slowly.**

---

### 🧠 Step 1 — What Problem Does cgroups Solve?

We learned that **namespaces** give each container its own isolated view.
Container 1 cannot see Container 2's processes. Good.

But here is a new problem:

Imagine 10 containers are running on one Linux machine.
Container 1 is running a heavy job and starts using:
- 100% of the CPU
- All available memory
- All disk I/O

What happens to the other 9 containers?
They **starve**. They slow down or crash. Their apps fail.

This is called the **noisy neighbour problem**.
One container is "noisy" (using too many resources) and it hurts all the "neighbours" (other containers).

**cgroups solves this.**

---

### 🧠 Step 2 — What is cgroups?

**cgroups** = Control Groups.

It is a feature built into the **Linux kernel** (the core of the OS).

cgroups lets you put processes into groups and then set **limits** on how many resources each group can use.

Simple definition:
> **cgroups = limits on what a container is ALLOWED to consume**

If namespaces control what a container can **see** —
then cgroups control what a container can **use**.

---

### 🧠 Step 3 — Real Life Analogy

Think of a **shared office building** with electricity.

The building has a total power supply of 1000 watts.
10 companies share the building.

Without limits:
Company 1 runs all its computers and air conditioning. It uses 900 watts.
The other 9 companies have only 100 watts left. Their lights flicker. Their computers crash.

With limits (cgroups):
The building manager says: "Each company gets maximum 100 watts."
Now Company 1 cannot take more than 100 watts.
Every company runs fine.

Docker's cgroups work exactly the same way.
Each container gets a maximum limit for CPU, memory, etc.
One container cannot steal resources from others.

---

### 🧠 Step 4 — What Resources Can cgroups Control?

| Resource | Docker Flag | Simple Explanation |
|----------|-------------|-------------------|
| **CPU** | `--cpus=1.5` | Container can use maximum 1.5 CPU cores worth of time |
| **Memory** | `--memory=512m` | Container can use maximum 512 MB of RAM |
| **Memory soft** | `--memory-reservation=256m` | Soft suggestion — try to stay under 256MB |
| **PIDs** | `--pids-limit=100` | Container can create maximum 100 processes |
| **Block I/O** | `--blkio-weight=500` | Limit how fast container reads/writes to disk |

---

### 🧠 Step 5 — How Does CPU Limiting Work? (Simple Explanation)

When you say `--cpus=1.5`, Docker does NOT pin the container to specific CPU cores.

Here is what actually happens:

Linux uses a system called **CFS — Completely Fair Scheduler**.
Think of CFS as a **timekeeper** that gives each process a fair share of CPU time.

Docker tells CFS:
- "Every 100 milliseconds (ms), this container gets 150ms of CPU time"
- This equals 1.5 CPUs worth of work per time period

```
Time period = 100ms
CPU quota   = 150ms  (= 1.5 CPUs)

Meaning: In every 100ms window, this container can use
         150ms of CPU processing time.
         (possible because we might have multiple cores)

If quota used up → container is PAUSED until next time window
```

**Why is this useful?**
If the machine has 8 CPUs and they are all idle, the container can burst and use more.
If the machine is busy, the container is throttled to its quota. Fair.

---

### 🧠 Step 6 — How Does Memory Limiting Work?

When you say `--memory=512m`, you set a **hard ceiling**.

- Container tries to allocate memory
- If total memory used goes above 512MB → the Linux kernel **kills the process**
- This is called **OOM Kill** — Out Of Memory Kill
- The kernel sends signal SIGKILL (force kill, no warning) to the container process

```bash
# You will see this in docker inspect:
"OOMKilled": true

# And in system logs:
dmesg | grep -i oom
# Output: "Out of memory: Kill process 12345 (node) score 900 or sacrifice child"
```

**Two memory limits you should always set:**

```bash
docker run \
  --memory=512m \            # hard limit — if exceeded, process is killed
  --memory-reservation=256m \ # soft limit — scheduler hint, not enforced
  nginx
```

`--memory-reservation` is a soft limit.
It tells the kernel: "Try to keep this container under 256MB."
But if memory is available, it can go higher (up to the hard limit of 512m).

---

### 🧠 Step 7 — What is pids-limit? (Fork Bomb Protection)

A **fork bomb** is a type of attack or accident where a process keeps creating child processes endlessly.

```bash
# A fork bomb in bash (DO NOT RUN THIS)
:(){ :|:& };:
# This creates infinite processes and crashes the system
```

`--pids-limit=100` tells the kernel:
"This container group can never have more than 100 processes total."

If the container tries to create process number 101, the kernel refuses.
This protects your host machine from fork bombs.

---

### 🧠 Step 8 — Where Do cgroups Live on Your Ubuntu Machine?

cgroups are managed through a special folder in Linux called the **cgroup filesystem**.

On modern Ubuntu with **cgroups v2**:

```
/sys/fs/cgroup/
```

**What is `/sys/fs/cgroup/`?**

- `/sys` = a special folder in Linux that exposes kernel information as files
  (Not real files — they are windows into the kernel's internals)
- `/sys/fs/cgroup/` = where the kernel exposes cgroup settings and stats as readable files

For a Docker container, you can find its limits here:

```bash
# Get the full container ID
CID=$(docker inspect mycontainer --format '{{.Id}}')

# Look at memory limit
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/memory.max
# Output: 536870912  (= 512 * 1024 * 1024 = 512MB in bytes)

# Look at CPU quota
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/cpu.max
# Output: 150000 100000
# Meaning: 150000 microseconds per 100000 microsecond period = 1.5 CPUs
```

These are not normal files. Reading them asks the kernel:
"What is the current limit for this container?"
The kernel answers by showing a number.

---

### 🔑 Full Summary — cgroups in One Picture

```
Without cgroups:
┌──────────────────────────────────────────┐
│              Host Machine                │
│  Container 1 → uses 90% CPU             │
│  Container 2 → starving, only 5% CPU    │
│  Container 3 → starving, only 5% CPU    │
└──────────────────────────────────────────┘

With cgroups:
┌──────────────────────────────────────────┐
│              Host Machine                │
│  Container 1 → max 33% CPU (enforced)   │
│  Container 2 → max 33% CPU (enforced)   │
│  Container 3 → max 33% CPU (enforced)   │
└──────────────────────────────────────────┘
```

> **SRE interview story:** *"In my banking project at Atos, we had a batch processing container that was not given memory limits. One night it had a memory leak and consumed all the RAM on the EC2 instance. This OOM-killed all other containers on that node — 12 microservices went down at 2 AM. After that incident, we made memory limits mandatory for every container in our Docker Compose and Kubernetes manifests. We also set up CloudWatch alarms for memory usage above 80%."*

## 8. Container Runtime — containerd and runc

> 🟡 **We will build this understanding piece by piece. Every new word is explained before we use it.**

---

### 🧠 Step 1 — What is a "Runtime"?

A **runtime** is software that is responsible for actually running something.

Examples:
- Java Runtime (JRE) = what actually runs your Java program
- Node.js runtime = what actually runs your JavaScript code
- Container runtime = what actually runs your Docker container

Before Docker can run a container, it needs a **container runtime** — software that talks to the Linux kernel and says: "create these namespaces, apply these cgroup limits, mount this filesystem, and start this process."

---

### 🧠 Step 2 — Why Are There Multiple Runtimes? (containerd AND runc?)

This confused many people. Let me explain simply.

Docker's architecture has **layers** — just like a company has a CEO, managers, and workers.

```
CEO (gives big orders)
  → Manager (breaks it into tasks)
    → Worker (actually does the physical work)
```

Docker's runtime stack works the same way:

```
Docker CLI (you type commands here)
  → dockerd — the "CEO" (manages everything high-level)
    → containerd — the "Manager" (manages container lifecycle)
      → runc — the "Worker" (actually talks to the Linux kernel)
```

Each layer has a specific job. Let's understand each one.

---

### 🧠 Step 3 — What is dockerd?

**dockerd** = Docker Daemon.

A **daemon** is just a background program that keeps running on your computer all the time, waiting for instructions.

Think of dockerd like a **restaurant manager**:
- Stays in the restaurant all day
- Takes orders from customers (Docker CLI)
- Manages the kitchen (images, containers, networks, volumes)
- Does NOT cook the food themselves — delegates to the kitchen

**What dockerd manages:**
- Docker images (pull, push, build, store)
- Docker networks (create bridges, assign IPs)
- Docker volumes (create, attach)
- Docker Compose and Swarm

**Where does dockerd live?**

On your Ubuntu machine, dockerd runs as a system service:
```bash
systemctl status docker      # check if dockerd is running
```

---

### 🧠 Step 4 — What is `/var/run/docker.sock`?

This is the thing that confused you. Let me explain from zero.

**What is a socket?**

A **socket** is a communication channel — like a phone line between two programs.

When two programs on the same computer want to talk to each other, they use a socket.

**What is a Unix socket?**

A **Unix socket** is a special type of socket that only works on the same machine. It appears as a file on your filesystem, but it is not a real file — it is a communication channel that looks like a file.

**What is `/var/run/docker.sock`?**

- `/var/run/` = a folder where Linux stores runtime files (files created while the system is running)
- `docker.sock` = the Unix socket file that dockerd creates when it starts

When the Docker CLI wants to talk to dockerd, it **sends a message through this socket file**.

```
You type:  docker run nginx
                ↓
Docker CLI reads: where is dockerd?
Docker CLI finds: /var/run/docker.sock
Docker CLI sends message through this socket → dockerd receives it
dockerd does the work → sends reply back through socket
Docker CLI shows you the result
```

**Analogy:**

Think of `/var/run/docker.sock` as a **letter slot in a door**.
- dockerd is inside the room, waiting for letters
- Docker CLI pushes a letter (your command) through the slot
- dockerd reads the letter, does the work, pushes a reply back

That is all it is. A communication channel between the CLI and the daemon.

**Why does this matter?**

If you try to use Docker and get this error:
```
Got permission denied while trying to connect to the Docker daemon socket at
unix:///var/run/docker.sock
```

It means: your user does not have permission to use that socket file.
Fix: `sudo usermod -aG docker $USER` — adds your user to the docker group which has permission to access the socket.

---

### 🧠 Step 5 — What is containerd?

**containerd** (pronounced "container-dee") is the actual container runtime that manages the **lifecycle of containers**.

Lifecycle = the complete life of a container:
- Create → Start → Pause → Resume → Stop → Delete

containerd is like the **kitchen manager**:
- Knows how to create containers
- Knows how to start and stop them
- Manages image storage (snapshots of filesystems)
- Does NOT cook the food — delegates actual Linux work to runc

**Why does Kubernetes use containerd directly?**

In the old days:
```
Kubernetes → dockershim (adapter) → dockerd → containerd → runc
```

dockerd did things Kubernetes never needed (Docker Compose, Swarm, GUI features).
It was a waste.

Since Kubernetes 1.24 (2022):
```
Kubernetes → containerd → runc
```

Kubernetes talks directly to containerd. Faster, simpler, less overhead.
Your Docker images still work — the image format (OCI) did not change.

---

### 🧠 Step 6 — What is runc?

**runc** is the lowest-level piece. It is a small program that:
1. Takes a container specification (what namespaces, what cgroups, what filesystem)
2. Calls the Linux kernel to set it all up
3. Starts the container process
4. Exits (its job is done)

runc is like the **line cook** — it actually does the physical work.

It calls these Linux kernel functions:
- `clone()` — creates a new process with separate namespaces
- `mount()` — mounts the OverlayFS filesystem
- `cgroups` setup — applies CPU and memory limits
- `exec()` — starts your actual application (nginx, node, etc.)

After runc starts the container, **runc exits**. Its job is done.

---

### 🧠 Step 7 — What is containerd-shim?

Here is a problem:

If containerd manages containers, and containerd restarts (for an upgrade or a crash) — do all containers die?

**No — because of the shim.**

**containerd-shim** is a tiny helper process. There is **one shim per container**.

The shim:
- Stays alive even if containerd restarts
- Keeps the container's STDIN/STDOUT/STDERR pipes open
- Reports back to containerd when the container exits

Think of the shim as a **babysitter**:
- The parents (containerd) go out (restart)
- The babysitter (shim) stays with the child (container)
- When parents come back (containerd restarts), the babysitter reports: "child is fine, still running"

```bash
# You can see shim processes on your machine
ps aux | grep containerd-shim
# One line per running container
```

---

### 🚀 Step 8 — FULL STORY: What Happens When You Run `docker run nginx`

Now let's put it ALL together. You type one command. Here is everything that happens behind the scenes.

```
docker run nginx
```

**What is nginx?**
nginx is a popular web server. The nginx image is stored on Docker Hub.

---

**STEP 1 — Docker CLI sends a request**

You type `docker run nginx` in your terminal.

The Docker CLI program does NOT run nginx itself.
It sends a message to dockerd through the socket file `/var/run/docker.sock`.

The message says: "Please run a container from the nginx image."

```
Your terminal
    │
    │  (message sent through /var/run/docker.sock)
    ▼
dockerd is waiting, receives the message
```

---

**STEP 2 — dockerd checks: do we have the nginx image?**

dockerd checks its local image cache:
```
/var/lib/docker/image/   ← where image metadata is stored
/var/lib/docker/overlay2/ ← where image layers are stored
```

Is the nginx image already downloaded? Let's say NO — it is the first time.

dockerd goes to **Docker Hub** (hub.docker.com) — the public registry where images are stored.

**What is a registry?**
A registry is an online storage service for Docker images.
Docker Hub is the default public registry.
Think of it like an App Store — but for Docker images.

dockerd:
1. Contacts Docker Hub
2. Gets the image manifest (a list of all layers nginx needs)
3. Downloads each layer in parallel
4. Stores layers in `/var/lib/docker/overlay2/`

---

**STEP 3 — dockerd tells containerd to create a container**

Now dockerd has the image. It instructs containerd:
"Create a container using this image. Here are the settings."

dockerd sends an **OCI bundle** to containerd.

**What is an OCI bundle?**

OCI = Open Container Initiative. It is an industry standard for containers.

An OCI bundle has two things:
- `config.json` — a file describing exactly how to run the container:
  - Which namespaces to create
  - Which cgroup limits to apply
  - Which user to run as
  - What command to run (nginx)
  - What environment variables to set
- `rootfs/` — the container's root filesystem (the merged OverlayFS view)

---

**STEP 4 — containerd spawns a shim**

containerd creates a **containerd-shim** process for this container.

The shim will be the permanent babysitter for this container.

```bash
# After this step, you would see:
ps aux | grep containerd-shim
# containerd-shim-runc-v2 -namespace moby -id <container-id> ...
```

---

**STEP 5 — shim calls runc to set up the container**

The shim calls `runc create` with the OCI bundle.

runc now talks directly to the **Linux kernel** and does all the real work:

```
runc calls the Linux kernel:

1. clone(CLONE_NEWPID)   → create new PID namespace
                            container will have its own process list

2. clone(CLONE_NEWNET)   → create new network namespace
                            container will have its own network interface

3. clone(CLONE_NEWMNT)   → create new mount namespace
                            container will have its own filesystem view

4. clone(CLONE_NEWUTS)   → create new UTS namespace
                            container will have its own hostname

5. cgroup setup          → apply memory limit, CPU limit, pids-limit
                            (writes to /sys/fs/cgroup/...)

6. mount OverlayFS       → merge image layers into one filesystem
                            lowerdir = nginx image layers
                            upperdir = new empty writable layer
                            merged   = what container will see

7. drop capabilities     → remove dangerous Linux powers the container
                            doesn't need (e.g., ability to load kernel modules)

8. apply seccomp         → filter which system calls the container can make
                            (security restriction)
```

---

**STEP 6 — runc starts the nginx process**

runc calls `exec()` — the Linux function that starts a program.

This starts: `nginx -g 'daemon off;'`

**Why `daemon off`?**
By default nginx runs in "daemon mode" — it starts, then goes to background.
If it goes to background, the foreground process exits.
If the foreground process exits, Docker thinks the container is done and stops it.
`daemon off` tells nginx: stay in the foreground. Keep running.

The nginx process is now running. It is PID 1 inside the container.

**runc exits** — its job is done.

---

**STEP 7 — shim stays, runc is gone**

The shim process stays alive.
It watches the nginx process.
If nginx crashes, the shim reports back to containerd.

```
Running processes on host after this step:
containerd              ← still running, managing all containers
containerd-shim         ← one per container, babysitting nginx
nginx                   ← the actual container process
```

---

**STEP 8 — dockerd sets up networking**

While all of the above was happening, dockerd also sets up networking.

This is how a container gets an IP address and can connect to the internet.

**Step 8a — Create a virtual ethernet pair (veth pair)**

A **veth pair** is like a **virtual ethernet cable**.
It has two ends. Whatever you put in one end comes out the other end.

```
veth pair:
  end1 (veth0abc) ← stays on the host machine
  end2 (eth0)     ← goes inside the container's network namespace
```

**Step 8b — Connect host end to docker0 bridge**

**What is docker0?**

docker0 is a **virtual network switch** that Docker creates on your host machine.

When you install Docker, it creates `docker0` automatically.
It is like a private local network switch inside your machine.
All containers connect to this switch.

```bash
# You can see it on your Ubuntu machine
ip addr show docker0
# Output: docker0: inet 172.17.0.1/16
# Docker is 172.17.0.1 — the gateway for all containers
```

The host end of the veth cable plugs into docker0.

**Step 8c — Place container end inside container's network namespace**

The other end of the veth cable is placed inside the container.
Inside the container, this end is called `eth0`.

```
Host machine:
  docker0 (172.17.0.1) ← veth0abc ← connected
                                         |
                                    virtual cable
                                         |
Container:                          eth0 (172.17.0.2) ← container's IP
```

**Step 8d — Assign IP via IPAM**

**IPAM = IP Address Management**

dockerd has a built-in system that keeps track of which IPs have been given out.
It assigns the container an IP like `172.17.0.2`.

The container can now communicate with:
- The host machine (via 172.17.0.1)
- Other containers on the same docker0 bridge
- The internet (via iptables NAT rules that Docker sets up)

**Step 8e — Port forwarding (if -p flag was used)**

If you ran `docker run -p 8080:80 nginx`, then dockerd also sets up an **iptables rule**.

**What is iptables?**
iptables is Linux's built-in firewall and routing system.
It can redirect network traffic from one port to another.

The rule says:
"Any traffic arriving on host port 8080 → redirect to container IP:80"

```
Browser on your laptop
    ↓
http://your-server:8080
    ↓
iptables rule: redirect to 172.17.0.2:80
    ↓
nginx inside container receives the request
    ↓
nginx sends response back
```

### 🔑 Full Picture — docker run nginx in One Diagram

```
You type: docker run nginx
                │
                ▼
    [Docker CLI] — sends request via /var/run/docker.sock
                │
                ▼
    [dockerd] — checks image cache
         │         → image not found → pulls from Docker Hub
         │         → image downloaded → layers in /var/lib/docker/overlay2/
         │
         │ — instructs containerd with OCI bundle
                │
                ▼
    [containerd] — creates container
         │
         │ — spawns containerd-shim
                │
                ▼
    [containerd-shim] — calls runc
                │
                ▼
    [runc] — talks to Linux kernel:
         │   • create namespaces (pid, net, mnt, uts)
         │   • apply cgroup limits (memory, CPU)
         │   • mount OverlayFS (lowerdir=image, upperdir=writable)
         │   • drop capabilities, apply seccomp
         │   • exec nginx process
         │
         │ — runc exits (job done)
                │
                ▼
    [containerd-shim stays] — babysitting nginx process
                │
                ▼
    [dockerd sets up network]
         • creates veth pair
         • plugs into docker0 bridge
         • assigns IP 172.17.0.2
         • sets up iptables for port forwarding
                │
                ▼
    nginx is running! Container is live.
```

---

### 🔑 Why This Matters for Kubernetes

> When Kubernetes needs to run a container, it does NOT use dockerd at all (since K8s 1.24).
> Kubernetes talks **directly to containerd** via a standard interface called CRI (Container Runtime Interface).
> containerd then calls runc exactly as described above.
>
> Your Docker images work perfectly in Kubernetes because the image format (OCI) is identical.
> Only the top layer (dockerd) was removed. Everything below it stayed the same.

### Lab 3 — Image vs Container in Action

```bash
# Run a container from nginx image
docker run -d --name webserver nginx

# List running containers
docker ps

# List all containers (including stopped)
docker ps -a

# See the IMAGE is unchanged, CONTAINER has writable layer
docker inspect webserver | jq '.[0].GraphDriver.Data'

# Write something to the container
docker exec webserver bash -c "echo 'Hello from container' > /tmp/test.txt"
docker exec webserver cat /tmp/test.txt

# Stop and remove the container — data is GONE
docker stop webserver && docker rm webserver

# Image still exists unchanged
docker images nginx
```

---

### Lab 4 — Observe Copy-on-Write (CoW)

```bash
# Start TWO containers from the SAME image
docker run -d --name c1 nginx
docker run -d --name c2 nginx

# Write to ONLY c1
docker exec c1 bash -c "echo 'I am container 1' > /tmp/test.txt"

# Verify isolation — c2 does NOT have the file
docker exec c1 cat /tmp/test.txt   # ✅ works
docker exec c2 cat /tmp/test.txt   # ❌ No such file

# Confirm both containers share the SAME lower layers
docker inspect c1 --format '{{.GraphDriver.Data.LowerDir}}'
docker inspect c2 --format '{{.GraphDriver.Data.LowerDir}}'
# Output should be IDENTICAL — same shared read-only layers

# But their UpperDir (writable layer) is DIFFERENT
docker inspect c1 --format '{{.GraphDriver.Data.UpperDir}}'
docker inspect c2 --format '{{.GraphDriver.Data.UpperDir}}'

# Cleanup
docker rm -f c1 c2
```

---

### Lab 5 — Observe Linux Namespaces

```bash
# Run a container
docker run -d --name nstest nginx

# Get container's PID on the HOST
CPID=$(docker inspect nstest --format '{{.State.Pid}}')
echo "Container process PID on host: $CPID"

# View the container's namespaces from the host
ls -la /proc/$CPID/ns/

# View HOST's namespace (PID 1 = systemd/init)
ls -la /proc/1/ns/

# Compare: different inode numbers = different namespaces!

# Enter the container's NETWORK namespace from the host
# (without going into the container)
sudo nsenter -t $CPID -n ip addr show
# You'll see eth0 with 172.17.x.x — the container's network

# Cleanup
docker rm -f nstest
```

### Lab 6 — cgroups Resource Limits

```bash
# Run container with explicit limits
docker run -d --name limited \
  --memory=128m \
  --memory-reservation=64m \
  --cpus=0.5 \
  --pids-limit=50 \
  nginx

# Verify limits are applied
docker inspect limited | jq '.[0].HostConfig | {
  Memory,
  MemoryReservation,
  CpuQuota,
  CpuPeriod,
  PidsLimit
}'

# Live resource usage
docker stats limited

# Check memory limit directly in cgroup filesystem (cgroups v2)
CID=$(docker inspect limited --format '{{.Id}}')
cat /sys/fs/cgroup/system.slice/docker-${CID}.scope/memory.max
# Output: 134217728 (= 128 * 1024 * 1024 bytes)

# Cleanup
docker rm -f limited
```

## 10. Quick Revision Cheatsheet

| Concept | One-Line Summary |
|---------|-----------------|
| **Image** | Read-only blueprint made of layers, stored in registry |
| **Container** | Running instance of image with thin writable layer + namespaces |
| **Layers** | Each Dockerfile instruction that changes FS = one immutable layer |
| **OverlayFS** | Merges read-only layers + writable layer into one unified view |
| **CoW** | Container copies file to writable layer before modifying it |
| **Namespaces** | Isolate what the container can SEE (pid, net, mnt, uts, ipc, user) |
| **cgroups** | Limit what the container can USE (CPU, memory, PIDs, I/O) |
| **containerd** | High-level runtime, CRI-compliant, manages lifecycle |
| **runc** | Low-level OCI runtime, calls Linux kernel to create container |
| **shim** | One per container, keeps container alive if containerd restarts |
| **docker.sock** | Unix socket Docker CLI uses to talk to dockerd |
