## 1. What is `docker history`? Why Does It Exist?

### The Problem It Solves

Imagine you pulled an image from Docker Hub.
It is 500MB.
You want to know:
- Why is it so big?
- Which step made it big?
- Can I reduce the size?
- What exactly was installed inside it?

You cannot open an image like a zip file and look inside easily.
`docker history` solves this.

It shows you **every layer** that was used to build the image — what instruction created it, when, and how much space it takes.

### What `docker history` Actually Does

When you run `docker history node:20-alpine`:

**Step 1** — Docker CLI asks `dockerd`: "Give me the build history of this image"

**Step 2** — `dockerd` reads the image metadata from `/var/lib/docker/`

**Step 3** — The image metadata stores a list of every instruction that was run to build it

**Step 4** — Docker prints that list on your screen, newest layer at the TOP

Think of it like reading the **construction diary** of a building — every step recorded in reverse order (most recent first).

## 2. Understanding Layers Before Reading the Output

### What is a Layer? (From Absolute Zero)

When someone builds a Docker image, they write a Dockerfile.
A Dockerfile is a list of instructions.

Each instruction that **changes files on the filesystem** creates a new **layer**.

A layer is simply a **snapshot of what changed** at that step.

**Real life analogy — Building a House:**

```
Step 1: Pour the foundation        → Layer 1 (9.11MB  — the ground)
Step 2: Build the walls            → Layer 2 (adds weight)
Step 3: Put on the roof            → Layer 3 (adds weight)
Step 4: Paint the walls            → Layer 4 (adds paint)
Step 5: Write house number on door → Layer 5 (0 weight — just metadata)
```

The final house is ALL these layers combined.
You cannot see the layers separately when you look at the finished house.
But they are all there underneath.

**Docker image layers work exactly the same way:**

```
Step 1: ADD alpine Linux filesystem          → Layer 1 (9.11MB)
Step 2: SET environment variable NODE_VERSION → Layer 2 (0B — metadata)
Step 3: RUN install Node.js                  → Layer 3 (130MB)
Step 4: RUN apk add packages                 → Layer 4 (5.48MB)
Step 5: COPY docker-entrypoint.sh            → Layer 5 (20.5KB)
Step 6: SET ENTRYPOINT                       → Layer 6 (0B — metadata)
Step 7: SET CMD                              → Layer 7 (0B — metadata)
```

The final image `node:20-alpine` is ALL these layers stacked together.

### The Most Important Point — Build Order vs Display Order

`docker history` shows layers in **REVERSE order**.
The **newest layer is at the TOP**.
The **oldest layer is at the BOTTOM**.

This confuses almost every beginner.

```
What you see in docker history (display order — newest first):
──────────────────────────────────────────────────────────
Row 1 (TOP)    CMD ["node"]                    ← BUILT LAST
Row 2          ENTRYPOINT [...]
Row 3          COPY docker-entrypoint.sh
Row 4          RUN apk add ...
Row 5          ENV YARN_VERSION
Row 6          RUN addgroup ... (install Node)
Row 7          ENV NODE_VERSION
Row 8          CMD ["/bin/sh"]
Row 9 (BOTTOM) ADD alpine-minirootfs...        ← BUILT FIRST
──────────────────────────────────────────────────────────

What actually happened when building (execution order — oldest first):
──────────────────────────────────────────────────────────
Step 1 (FIRST)  ADD alpine-minirootfs...       ← start here
Step 2          CMD ["/bin/sh"]
Step 3          ENV NODE_VERSION
Step 4          RUN addgroup ... (install Node)
Step 5          ENV YARN_VERSION
Step 6          RUN apk add ...
Step 7          COPY docker-entrypoint.sh
Step 8          ENTRYPOINT [...]
Step 9 (LAST)   CMD ["node"]                   ← end here
──────────────────────────────────────────────────────────
```

**Rule to remember:**
> When reading `docker history`, flip it mentally.
> Read from BOTTOM to TOP to understand how the image was actually built.

## 4. Why Does IMAGE Show `<missing>`?

This is the question that confuses almost every beginner.
Let me explain it completely.

### The Wrong Understanding

Many people think: "Oh no, my layers are corrupted or missing!"

**The layers are NOT missing. They are all there.**

### The Correct Understanding

`<missing>` simply means:
> "This layer exists and is stored on your disk. But it does not have its OWN separate image ID assigned to it."

### Why Does This Happen?

When an image is built with **BuildKit** (the modern build system):

BuildKit stores each layer efficiently.
But intermediate layers (all the steps in the middle) are **not given their own separate image IDs**.

Only the FINAL complete image gets an image ID (`fb4cd12c85ee`).

**Real life analogy — Building a house:**

```
Foundation work      → no separate address
Wall construction    → no separate address
Roof installation    → no separate address
Interior finishing   → no separate address
Completed house      → gets house number: 42B Baker Street ← only the final gets an ID
```

You do not give a house number to every intermediate stage of construction.
Only the finished house gets a number.

Same with Docker:
Only the final image gets an image ID.
All intermediate build steps show `<missing>`.

### Another Way to Think About It

`<missing>` does NOT mean the data is gone.

It means: "No image ID is registered for this intermediate step."

The actual layer data is stored safely in `/var/lib/docker/`.
You can still use the image perfectly.
`docker run node:20-alpine` works fine.

### Why Only the TOP Row Has an ID

```
IMAGE
fb4cd12c85ee   ← TOP row = the FINAL image = has an ID
<missing>      ← intermediate build step = no ID needed
<missing>
<missing>
```

The top row represents the complete, final, published image.
That image has the tag `node:20-alpine` and the ID `fb4cd12c85ee`.

```bash
# Confirm: the IMAGE column matches docker images output
docker images node:20-alpine
# IMAGE ID: fb4cd12c85ee  ← same as top row of docker history
```

## 5. Your Output — Every Single Row Explained

Now let us read your output from **BOTTOM to TOP** (the order they were actually built):

---

### Row 9 (BOTTOM) — The Very First Step

```
ADD alpine-minirootfs-3.23.4-x86_64.tar.gz /&    9.11MB
```

**`ADD`** = a Dockerfile instruction that copies files into the image.
In this case, it is adding a compressed archive file.

**`alpine-minirootfs-3.23.4-x86_64.tar.gz`**

Let us break this filename down:

`alpine` = Alpine Linux — a very small Linux distribution. About 5MB when installed.
Used as base because it is tiny and secure.

`minirootfs` = "minimal root filesystem"
`root filesystem` = the complete set of files that Linux needs to boot and operate.
`mini` = stripped down to the bare minimum.

`3.23.4` = Alpine Linux version 3.23.4

`x86_64` = built for Intel/AMD 64-bit processors (your ThinkPad)

`.tar.gz` = a compressed archive file.
`.tar` = tape archive — a format that bundles many files into one file
`.gz` = gzip compressed — the bundle is then compressed to save space
Together `.tar.gz` = a compressed bundle of files

**What `ADD` does with a `.tar.gz` file:**
Unlike `COPY`, the `ADD` instruction automatically EXTRACTS tar archives.
So this instruction:
1. Takes the compressed Alpine Linux filesystem
2. Extracts it
3. Puts all the extracted files into `/` (the root of the image)

**Size: 9.11MB** = after extraction, Alpine Linux takes 9.11MB.

**In simple terms:**
This step installs Alpine Linux as the base operating system for this image.
Everything else will be installed ON TOP of this Alpine Linux foundation.

---

### Row 8 — CMD ["/bin/sh"]

```
CMD ["/bin/sh"]    0B
```

**`CMD`** = Container Default Command.
Sets what command runs when someone starts a container and does not specify a command.

**`/bin/sh`** = the path to the shell program on Linux.

`/bin` = a folder that contains basic programs (binaries) needed by the OS
`sh` = shell — a program that reads and executes commands

So this says: "If nobody tells this container what to do, open a shell."

This is the default Alpine Linux behaviour — if you just start it with no command, it gives you a shell.

**Size: 0B** = CMD does not add any files. It only stores metadata (instructions about what to run).

---

### Row 7 — ENV NODE_VERSION=20.20.2

```
ENV NODE_VERSION=20.20.2    0B
```

**`ENV`** = Environment Variable.
Sets a variable that will be available inside the container when it runs.

**`NODE_VERSION=20.20.2`**

`NODE_VERSION` = the name of the variable
`=` = assignment
`20.20.2` = the value — this is the version of Node.js that will be installed

**Why set this as a variable first?**

Because the next `RUN` instruction will USE this variable to download the correct Node.js version:
```bash
RUN curl -fsSL "https://nodejs.org/dist/v${NODE_VERSION}/node-v${NODE_VERSION}-linux-x64-musl.tar.xz"
```

It is like defining a constant before using it in code.
If they want to upgrade Node.js version, they only change this one line.

**Size: 0B** = ENV stores only metadata. No files are added.

---

### Row 6 — RUN addgroup (Install Node.js) — THE BIG ONE

```
RUN /bin/sh -c addgroup -g 1000 node &&    130MB
```

This is the LARGEST layer — 130MB.

**What does this full command do?**

The `&` at the end means the full command is cut off in display.
Run `docker history --no-trunc node:20-alpine` to see the full command.

The full command does several things chained together with `&&`:

```bash
# Step 1: Create a group called 'node' with group ID 1000
addgroup -g 1000 node

# Step 2: Create a user called 'node' with user ID 1000 in the node group
adduser -u 1000 -G node -s /bin/sh -D node

# Step 3: Download and install Node.js version 20.20.2
# (downloads the binary, extracts it, puts it in /usr/local/)

# Step 4: Verify the download with checksum
# Step 5: Clean up downloaded files
```

**Breaking down the first part:**

`/bin/sh` = run using the shell program
`-c` = the `-c` flag means "execute this command string"
So `/bin/sh -c "some command"` means: open the shell and run this command

`addgroup` = a command on Alpine Linux to create a group

`-g 1000` = assign group ID 1000
`-g` = group ID flag
`1000` = the number. User IDs and Group IDs below 1000 are reserved for system use. 1000+ are for regular users.

`node` = name of the group being created

`&&` = AND operator. Only run the next command IF this command succeeded.

**Why 130MB?**

Node.js itself is a large binary (~80MB).
Plus its dependencies, npm, and related files.
This is the biggest layer because it installs the main software.

---

### Row 5 — ENV YARN_VERSION=1.22.22

```
ENV YARN_VERSION=1.22.22    0B
```

Same as ENV NODE_VERSION — sets a variable.

**What is Yarn?**

Yarn is an alternative to npm (Node Package Manager).
Both npm and yarn are tools for installing JavaScript packages/libraries.

`YARN_VERSION=1.22.22` = the version of Yarn that will be installed in the next RUN step.

**Size: 0B** = metadata only, no files.

---

### Row 4 — RUN apk add (Install Extra Packages)

```
RUN /bin/sh -c apk add --no-cache --virtual &    5.48MB
```

**`apk`** = Alpine Package Keeper.
This is Alpine Linux's package manager.
It installs software on Alpine, just like:
- `apt install` on Ubuntu/Debian
- `yum install` on CentOS/RedHat
- `brew install` on macOS

**`add`** = the sub-command to install packages

**`--no-cache`**

`--` = these dashes indicate this is a flag (option)
`no-cache` = do NOT save the package list to disk after installing

Normally, `apk` downloads a package index (a list of all available packages) and saves it to disk.
`--no-cache` says: "Download what I need but do NOT save the package index to disk."
This keeps the image smaller.

**`--virtual`**

Virtual packages in Alpine are temporary grouped installs.
You install a bunch of packages under a virtual name, then later remove all of them at once by deleting the virtual group name.
Used for build dependencies that are needed to compile something but not needed at runtime.

**`&`** = command is cut off. Use `--no-trunc` to see the full list of packages installed.

The packages installed here typically include:
- `ca-certificates` = TLS certificate authorities (needed for HTTPS connections)
- `yarn` = the Yarn package manager (version set by `YARN_VERSION`)
- Build tools needed temporarily

**Size: 5.48MB** = all these packages installed add 5.48MB.

---

### Row 3 — COPY docker-entrypoint.sh

```
COPY docker-entrypoint.sh /usr/local/bin/ #&    20.5kB
```

**`COPY`** = copies a file from the build context into the image.

**`docker-entrypoint.sh`** = a shell script file.
`.sh` = shell script extension.
A shell script is a text file containing a series of commands.

**`/usr/local/bin/`** = where the script is copied to inside the image.

Let us break down this path:

`/usr` = user programs folder
`/usr/local` = programs installed locally (not by the OS package manager)
`/usr/local/bin` = executables (runnable programs) installed locally

Putting the script here means it will be in the system's PATH — executable from anywhere by just typing its name.

**`#&`** = this is the display cutoff character again. The full instruction had more text after this.

**What does `docker-entrypoint.sh` actually do?**

This script runs FIRST every time a container starts.
It sets up the environment before your actual command runs.

For `node:20-alpine`, it typically:
1. Checks if the first argument is a Node.js command
2. Sets up any needed environment
3. Runs the command you specified (or the default `node`)

**Size: 20.5kB** = a small shell script. Only 20.5 kilobytes.

---

### Row 2 — ENTRYPOINT

```
ENTRYPOINT ["docker-entrypoint.sh"]    0B
```

**`ENTRYPOINT`** = the program that ALWAYS runs when a container starts.
You cannot replace it just by passing a command to `docker run`.

This says: "Always run `docker-entrypoint.sh` first."

**Connection with CMD:**
```
ENTRYPOINT ["docker-entrypoint.sh"]   ← always runs
CMD ["node"]                          ← passed as argument to entrypoint
```

Together they run: `docker-entrypoint.sh node`

If you run: `docker run node:20-alpine npm install`
Docker runs: `docker-entrypoint.sh npm install`
(CMD is replaced by `npm install`, ENTRYPOINT stays)

**Size: 0B** = metadata only. Just stores the instruction.

---

### Row 1 (TOP) — CMD ["node"]

```
fb4cd12c85ee   CMD ["node"]    0B
```

**`CMD ["node"]`** = the default command passed to the entrypoint.

If you run `docker run node:20-alpine` with no command, it runs:
```
docker-entrypoint.sh node
```
Which starts the Node.js interactive REPL (Read-Eval-Print Loop — like a Python interactive shell).

If you run `docker run node:20-alpine node myapp.js`, it runs:
```
docker-entrypoint.sh node myapp.js
```

**Size: 0B** = metadata only.

**`fb4cd12c85ee`** = THIS is the final image ID. The complete, finished image.
This is why only this row has an IMAGE ID.

## 6. Why Do Some Layers Show 0B Size?

This is a very common question.

**The rule is simple:**

Only instructions that **physically add, remove, or change FILES** on the disk create a layer with size.

Instructions that only store **instructions or settings** (metadata) have 0B size.

| Instruction | Adds/Changes Files? | Size |
|------------|-------------------|------|
| `RUN apt install` | ✅ Yes — installs files | Non-zero |
| `RUN npm install` | ✅ Yes — downloads packages | Non-zero |
| `COPY file.txt .` | ✅ Yes — copies a file | Size of file |
| `ADD archive.tar.gz /` | ✅ Yes — extracts files | Size extracted |
| `ENV MY_VAR=value` | ❌ No — just metadata | 0B |
| `CMD ["nginx"]` | ❌ No — just metadata | 0B |
| `ENTRYPOINT [...]` | ❌ No — just metadata | 0B |
| `EXPOSE 8080` | ❌ No — just metadata | 0B |
| `WORKDIR /app` | ❌ Usually no | 0B |
| `ARG BUILD_VERSION` | ❌ No — just metadata | 0B |

**In your output:**
```
130MB  ← RUN installed Node.js (real files added)
5.48MB ← RUN apk add (real packages added)
9.11MB ← ADD alpine filesystem (real files extracted)
20.5kB ← COPY added a script file
0B     ← ENV, CMD, ENTRYPOINT (all metadata — no files)
```

## 7. What is the `dive` Tool?

### The Problem With `docker history`

`docker history` shows you layers and sizes.
But it does NOT show you:
- Which specific files are inside each layer
- Which files are being duplicated across layers
- Which files are "wasted" (modified in a later layer — they waste space)

### What `dive` Solves

`dive` is a third-party tool (not made by Docker, made by the open source community).

It gives you an **interactive visual explorer** for Docker image layers.

You can:
- See every file inside every layer
- Navigate through layers one by one
- See exactly which files were added, modified, or deleted in each layer
- See a "wasted space" percentage — how much of the image size is duplicated or inefficient
- Find the exact Dockerfile instruction that caused your image to be large

### Why Developers and DevOps Engineers Use `dive`

When you want to reduce image size:

1. `docker history` tells you WHICH layer is large (e.g., RUN install = 130MB)
2. `dive` tells you WHAT FILES inside that layer are taking space

Together they help you optimise images.

## 8. The `dive` Command — Every Word Explained

Here is the command:

```bash
docker run --rm -it \
  -v /var/run/docker.sock:/var/run/docker.sock \
  wagoodman/dive node:20-alpine
```

This looks complex. Let us break it into every single piece.

---

### `docker run`

You already know this.
It runs a container from an image.

---

### `--rm`

`--` = indicates this is a flag (an option)
`rm` = remove

**What it does:**
Automatically DELETE the container when it finishes running.

Without `--rm`:
After `dive` closes, a stopped container stays on your disk.
You would need to manually run `docker rm <container-id>` to clean up.

With `--rm`:
The moment you close `dive`, the container is automatically deleted.
No cleanup needed.

**Why use it here?**
`dive` is a one-time tool. You open it, explore, close it.
You do not need the container to stay after that.
`--rm` keeps your system clean automatically.

---

### `-it`

This is actually TWO flags combined:

**`-i`** = interactive

`-i` keeps the container's STDIN (standard input) open.
STDIN = the input channel — keyboard input, data piped in.

Without `-i`, the container cannot receive any keyboard input from you.
`dive` needs keyboard input (arrow keys, Tab, etc.) to navigate.
So `-i` is required.

**`-t`** = pseudo-TTY (terminal)

A TTY = TeleTYpewriter = in modern usage, a terminal interface.

Without `-t`, the output does not look like a proper terminal.
No colours, no cursor movement, no proper layout.

`-t` creates a fake terminal session inside the container that works like a real terminal.
This is what makes `dive`'s visual interface display correctly.

**Combined `-it`:**
`-it` together = "Give me a proper interactive terminal session with this container."

You use `-it` any time you want to interact with a container's terminal:
```bash
docker run -it ubuntu bash        # open bash shell in Ubuntu container
docker run -it python:3.12 python # open Python interactive shell
docker run -it --rm node node     # open Node.js REPL
```

---

### `\`

The backslash at the end of the first line.

This is a **line continuation character** in bash (the Linux shell).

It means: "This command continues on the next line."

Without backslash, you would write everything on one line:
```bash
docker run --rm -it -v /var/run/docker.sock:/var/run/docker.sock wagoodman/dive node:20-alpine
```

That is very long and hard to read.

With backslash, you split it across multiple lines for readability:
```bash
docker run --rm -it \
  -v /var/run/docker.sock:/var/run/docker.sock \
  wagoodman/dive node:20-alpine
```

Both are identical to the computer. The backslash says "ignore this newline — it is the same command."

---

### `-v /var/run/docker.sock:/var/run/docker.sock`

This is the most important and most confusing part.

**`-v`** = volume mount.
`-v` is the flag for mounting something from your host machine into the container.

**The format is:** `-v host_path:container_path`

Left of `:` = path on YOUR machine (host)
Right of `:` = path INSIDE the container

So: `-v /var/run/docker.sock:/var/run/docker.sock`

Means:
- Take `/var/run/docker.sock` from YOUR machine
- Make it available at `/var/run/docker.sock` inside the `dive` container
- Same path on both sides — same name

**But WHY does `dive` need your docker.sock?**

Here is the key insight.

`dive` is a program running INSIDE a Docker container.
Inside its container, `dive` cannot normally see anything about your Docker installation.
It is isolated.

But `dive`'s job is to inspect Docker images that are on YOUR machine.

**How does `dive` reach your Docker?**

By accessing `/var/run/docker.sock` — the communication channel to your `dockerd`.

When `dive` connects to `/var/run/docker.sock`, it is talking directly to your `dockerd`.
It can then ask `dockerd`: "Give me the layer information for `node:20-alpine`."
`dockerd` gives it the data.
`dive` displays it in its visual interface.

**Simple analogy:**

`dive` is a guest staying in your house (inside a container).
Normally a guest cannot access your home office (your Docker data).
But you give them a key to the office (`/var/run/docker.sock`).
Now the guest can go into your office and read your files (inspect Docker images).

**Security note:**
Giving a container access to `/var/run/docker.sock` is very powerful.
That container can control ALL of Docker on your machine — run containers, delete images, everything.
Only do this with tools you trust.
`wagoodman/dive` is a trusted, widely-used open source tool.

This is the **image name** to run.

**`wagoodman`** = the Docker Hub username of the person who created `dive`.
His name is Alex Goodman (username: wagoodman).

**`/`** = separator between username and image name.

### Using `dive` — What You See

When `dive` opens, you see a split screen:

```
┌─────────────────────────────────┬──────────────────────────────────┐
│  Layers (left panel)            │  Current Layer Contents (right)  │
│                                 │                                  │
│  ● CMD ["node"]          0B    │  Permission  UID:GID  Size  File │

│  ● RUN addgroup...     130MB   │                                   │
│  ● ENV NODE_VERSION      0B    │                                   │

│  ● ADD alpine...        9.11MB │                                   │
│                                 │                                  │

└─────────────────────────────────┴──────────────────────────────────┘
```

**Keyboard navigation in dive:**

| Key | What it does |
|-----|-------------|
| `Tab` | Switch between left panel (layers) and right panel (files) |
| `↑` `↓` arrow keys | Move up and down through layers or files |
| `Ctrl+U` | Show only the files that changed in the currently selected layer |
| `Ctrl+A` | Show all files in the current view |
| `Ctrl+C` or `q` | Quit dive |

**The "Wasted Space" metric:**

`dive` calculates how much space is wasted in the image.

Wasted space happens when:
1. A file is added in Layer 3
2. That same file is modified or deleted in Layer 5
3. The ORIGINAL file in Layer 3 still takes up space even though it was changed later

Example:
```
Layer 3: RUN wget big-file.tar.gz && tar -xz    ← 100MB added
Layer 4: RUN rm big-file.tar.gz                 ← tries to delete it

Problem: big-file.tar.gz still exists in Layer 3!
         Deleting in a later layer does not remove it from the earlier layer.
         It just hides it. Both layers still take space.
         This is 100MB wasted.

Fix: Do it all in ONE layer:
Layer 3: RUN wget big-file.tar.gz && tar -xz && rm big-file.tar.gz
         Now the file is downloaded, extracted, AND deleted in the same layer.
         It never gets committed to any layer. 0MB wasted.
```

### Lab 1 — Run `docker history` on Your Image

```bash
docker history node:20-alpine
```

**What happens:**
Docker CLI asks `dockerd` for the build history of `node:20-alpine`.
`dockerd` reads the image manifest from `/var/lib/docker/`.
The manifest contains a list of all layers and their metadata.
Docker prints them newest-first.

### Lab 2 — See the Full Commands Without Truncation

```bash
docker history node:20-alpine --no-trunc
```

**Every word:**

`docker history node:20-alpine` = base command you already know

`--no-trunc` = no truncation
`--` = this prefix means it is a long-format flag
`no` = do not
`trunc` = truncate (cut short)
Combined: do not cut the output short — show the complete full text

**This will show the full RUN command like:**
```
RUN /bin/sh -c addgroup -g 1000 node     && adduser -u 1000 -G node -s /bin/sh -D node     && apk add --no-cache ...
```

Instead of the shortened version ending in `&`.

---

### Lab 3 — See History With Sizes in a Clean Format

```bash
docker history node:20-alpine --format "{{.Size}}\t{{.CreatedBy}}"
```

**Breaking down:**

`--format` = change how the output is displayed

`"{{.Size}}\t{{.CreatedBy}}"` = a Go template string
- `{{.Size}}` = show the Size field
- `\t` = a tab character (for alignment)
- `{{.CreatedBy}}` = show the CreatedBy field

This shows only size and instruction, making it easier to see which steps are large.


You will see `node:20` (Debian-based) has many more layers and much larger sizes.
`node:20-alpine` is much smaller because Alpine Linux is minimal.

### Lab 5 — Install and Run `dive`

```bash
# Run dive using Docker itself (no installation needed)
docker run --rm -it \
  -v /var/run/docker.sock:/var/run/docker.sock \
  wagoodman/dive node:20-alpine
```

**What happens step by step:**

Step 1: `docker run` starts

Step 2: Docker checks if `wagoodman/dive` is downloaded locally
- If NO → pulls it from Docker Hub automatically
- If YES → uses the cached version

Step 3: Docker creates a container from `wagoodman/dive`

Step 4: Docker sets up the volume mount:
`/var/run/docker.sock` from your machine becomes accessible inside the container

Step 5: The `dive` program starts inside the container

Step 6: `dive` connects to `/var/run/docker.sock` — which is YOUR docker.sock

Step 7: `dive` asks YOUR `dockerd`: "Give me all layers of `node:20-alpine`"

Step 8: `dockerd` returns the layer data

Step 9: `dive` displays the visual interface on your terminal

Step 10: You press `q` or `Ctrl+C` to close

Step 11: `--rm` ensures the container is automatically deleted

**Navigate with:**
- `Tab` = switch panels
- Arrow keys = move through layers / files
- `Ctrl+U` = show only changed files in selected layer
- `q` = quit

### Lab 6 — Build Your Own Image and See Its History

```bash
# Create a test folder
mkdir ~/docker-labs/history-test
cd ~/docker-labs/history-test

# Create a simple Dockerfile
cat > Dockerfile << 'EOF'
FROM alpine:3.19
ENV MY_APP_VERSION=1.0
RUN apk add --no-cache curl
COPY Dockerfile /app/Dockerfile
CMD ["sh"]
EOF

# Build the image
docker build -t my-history-test:1.0 .

# Now see YOUR image's history
docker history my-history-test:1.0

# Compare with dive
docker run --rm -it \
  -v /var/run/docker.sock:/var/run/docker.sock \
  wagoodman/dive my-history-test:1.0
```

**What to observe:**
- Your FROM creates the base layer
- ENV shows as 0B
- RUN apk add shows a non-zero size
- COPY shows the size of the Dockerfile file you copied
- CMD shows 0B

This makes the theory real — you built the layers yourself and can see exactly what each one did.

## 10. Why This Matters in Interviews

---

### Q: How do you find out which layer is making your Docker image large?

> "My first step is `docker history myimage:tag`. This shows every layer with its size, so I can immediately identify which instruction added the most data. For example, if I see a `RUN npm install` layer at 800MB, I know my node_modules is the problem. My second step is running `dive` — `docker run --rm -it -v /var/run/docker.sock:/var/run/docker.sock wagoodman/dive myimage:tag`. Dive lets me see exactly which files inside that layer are taking space. It also shows a wasted space percentage — files that were added in one layer and then deleted or modified in a later layer, wasting space. Together, `docker history` tells me which layer is large, and `dive` tells me exactly what files inside that layer are responsible."

---

### Q: What does `<missing>` mean in `docker history` output?

> "It does not mean the layers are missing or corrupted. It means those intermediate build layers do not have their own separate image IDs registered. When an image is built with BuildKit — Docker's modern build engine — only the final complete image gets an image ID. All the intermediate build steps exist on disk and work correctly, but they are not individually tagged. Only the top row in `docker history` shows an image ID because that represents the final, complete image."

---

### Q: Why do some layers show 0B size in `docker history`?

> "Only instructions that physically add, remove, or change files on the filesystem create a layer with actual size. Instructions like RUN, COPY, and ADD that write files to disk create sized layers. Instructions like ENV, CMD, ENTRYPOINT, EXPOSE, and ARG only store metadata — they do not touch the filesystem. So they show 0B. In the `node:20-alpine` image for example, the RUN instruction that installs Node.js is 130MB because it writes binaries to disk, but ENV NODE_VERSION=20.20.2 is 0B because it only stores a variable in the image configuration."

## 11. Quick Revision Cheatsheet

| Command | What It Does |
|---------|-------------|
| `docker history <image>` | Show all layers, sizes, and instructions that built the image |
| `docker history --no-trunc <image>` | Show full instruction text without cutting |
| `docker history --format "{{.Size}}\t{{.CreatedBy}}" <image>` | Custom format — size and instruction only |
| `docker run --rm -it -v /var/run/docker.sock:/var/run/docker.sock wagoodman/dive <image>` | Interactive visual layer explorer |

| Column in `docker history` | Meaning |
|---------------------------|---------|
| `IMAGE` | Image ID — only the final image has one, others show `<missing>` |
| `CREATED` | When this layer was built |
| `CREATED BY` | The Dockerfile instruction that created this layer |
| `SIZE` | Disk space this layer adds |
| `COMMENT` | Build engine used (`buildkit.dockerfile.v0`) |

| Flag | Meaning |
|------|---------|
| `--rm` | Delete container when it exits |
| `-i` | Keep STDIN open (receive keyboard input) |
| `-t` | Pseudo-TTY (proper terminal display) |
| `-it` | Combined: interactive terminal session |
| `-v host:container` | Mount host path into container |
| `--no-trunc` | Show full output without cutting |

| Fact | Detail |
|------|--------|
| Display order | Newest layer TOP, oldest BOTTOM |
| Build order | Bottom to top (read history in reverse) |
| `<missing>` | Layer exists but has no separate image ID (BuildKit behaviour) |
| 0B layers | Metadata-only instructions: ENV, CMD, ENTRYPOINT, EXPOSE |
| Non-zero layers | File-changing instructions: RUN, COPY, ADD |
| `wagoodman/dive` | Open source tool to visually explore image layers |
| Why `-v docker.sock` | `dive` needs to talk to YOUR dockerd to read image data |
