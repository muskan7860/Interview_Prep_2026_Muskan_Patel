## 1. Why Does Docker Compose Exist? The Problem First

### Life Without Docker Compose

Imagine you are building a web application.
It has three parts:

```
1. Frontend  → React app        → runs on port 3000
2. Backend   → Node.js API      → runs on port 5000
3. Database  → PostgreSQL       → runs on port 5432
```

To start all three WITHOUT Docker Compose, you would type:

```bash
# Command 1 — create the network
docker network create myapp-network

# Command 2 — create the volume
docker volume create postgres-data

# Command 3 — start the database
docker run -d \
  --name postgres \
  --network myapp-network \
  -v postgres-data:/var/lib/postgresql/data \
  -e POSTGRES_DB=myapp \
  -e POSTGRES_USER=appuser \
  -e POSTGRES_PASSWORD=secret \
  postgres:15

# Command 4 — start the backend
docker run -d \
  --name backend \
  --network myapp-network \
  -p 5000:5000 \
  -e DATABASE_URL=postgresql://appuser:secret@postgres:5432/myapp \
  -e NODE_ENV=production \
  myapp-backend:latest

# Command 5 — start the frontend
docker run -d \
  --name frontend \
  --network myapp-network \
  -p 3000:3000 \
  -e REACT_APP_API_URL=http://localhost:5000 \
  myapp-frontend:latest
```

**Five commands. Every time.**

And when you want to stop everything:

```bash
docker stop postgres backend frontend
docker rm postgres backend frontend
docker network rm myapp-network
```

**More commands. Every time.**

If you make a mistake in any command, you have to figure out which step failed and restart from there.

If a new developer joins your team, you have to explain all five commands to them.
They will likely make mistakes.

**This does not scale.**

### The Solution — Docker Compose

With Docker Compose, you write ALL of this configuration ONCE in a single file called `docker-compose.yml`.

Then you only ever need:

```bash
docker compose up -d    # start everything
docker compose down     # stop and remove everything
```

Two commands. Always. For any application size.

The configuration is in a file that you can:
- Put in version control (Git)
- Share with the whole team
- Review for mistakes before running
- Run identically on any machine

## 2. What is Docker Compose?

### Simple Definition

Docker Compose is a tool that:
- Reads a `docker-compose.yml` file you write
- Creates all the networks, volumes, and containers you defined
- Manages them as a group (start all, stop all, restart all)

**Simple analogy:**

Without Docker Compose = ordering food item by item at a restaurant.
"I want the soup. Now I want the bread. Now I want the main course. Now I want dessert."
Each item is a separate interaction. Easy to forget one.

With Docker Compose = ordering a set meal.
"I want Set Meal A."
The kitchen knows exactly what Set Meal A includes and brings everything together.

The `docker-compose.yml` file is your menu definition.
`docker compose up` is you saying "bring me Set Meal A."

### Docker Compose v1 vs v2 — Important Difference

There are two versions of the Compose tool:

**v1 (old):** Installed separately. Command was `docker-compose` (with hyphen).
**v2 (current):** Built into Docker. Command is `docker compose` (space, no hyphen).

```bash
# Old v1 way (still works but deprecated)
docker-compose up

# New v2 way (use this)
docker compose up
```

Your Docker version (29.1.3) includes Compose v2. Always use `docker compose` (with space).

### What Docker Compose Does NOT Do

Docker Compose is for **single machine** deployments.
It manages containers on ONE Docker host.

For managing containers across MULTIPLE machines, you need:
- Docker Swarm (older, simpler)
- Kubernetes (industry standard)

This is important to know for interviews.

## 3. What is YAML? Understanding the File Format

### Why You Need to Understand YAML First

The `docker-compose.yml` file is written in **YAML**.

YAML = YAML Ain't Markup Language.

If you do not understand YAML syntax, the Compose file will look confusing.
Let us understand YAML from zero.

### YAML Basics

YAML is a way to write structured data in plain text.
It uses **indentation** (spaces) to show structure.

**Simple analogy:**

YAML is like a **structured shopping list with categories:**

```
Vegetables:
  - Tomatoes
  - Onions
  - Carrots
Fruits:
  - Apples
  - Bananas
Dairy:
  - Milk
  - Cheese
```

That IS valid YAML.

### YAML Key Rules

**Rule 1 — Indentation means nesting:**
```yaml
parent:
  child: value        # child belongs to parent (2 spaces indented)
  another_child: value
```

**Rule 2 — Use SPACES not TABS:**
```yaml
# CORRECT — uses spaces
services:
  webapp:
    image: nginx

# WRONG — uses tabs (invisible but will cause errors)
services:
	webapp:
		image: nginx
```

**Rule 3 — Key-value pairs:**
```yaml
key: value
name: muskan
port: 3000
enabled: true
```

**Rule 4 — Lists use dash (`-`):**
```yaml
ports:
  - "3000:3000"
  - "3001:3001"

environment:
  - NODE_ENV=production
  - PORT=3000
```

**Rule 5 — Comments use `#`:**
```yaml
# This is a comment — Docker ignores this line
services:
  web:            # This is also a comment
    image: nginx  # Sets the image to use
```

**Rule 6 — Strings with special characters need quotes:**
```yaml
# These need quotes because of special characters
password: "my:secret:password"    # colon would confuse YAML
message: "Hello World"            # safe to quote strings always

# Simple strings do not need quotes
image: nginx
name: myapp
```

## 4. The docker-compose.yml File — Every Key Explained

### The Top-Level Structure

A `docker-compose.yml` file has three main sections:

```yaml
services:    # defines your containers
  ...

networks:    # defines custom networks (optional)
  ...

volumes:     # defines named volumes (optional)
  ...
```

Every container you want to run is defined under `services`.
Networks and volumes are optional — Compose creates defaults automatically.

### A Minimal Example

```yaml
services:
  webapp:
    image: nginx
    ports:
      - "8080:80"
```

This is a complete, valid `docker-compose.yml`.
It defines one service called `webapp` using the nginx image, with port 8080 on the host mapped to port 80 inside the container.

Run it with:
```bash
docker compose up -d
```

That is the entire workflow.

## 5. The `services` Section

This is the heart of your Compose file.
Every container you want to run is one entry under `services`.

### All Available Keys Under a Service

```yaml
services:
  myservice:                          # name you choose for this service

    image: nginx:alpine               # which Docker image to use
                                      # OR use 'build' instead of 'image'

    build:                            # build an image from a Dockerfile
      context: ./myapp               # folder containing the Dockerfile
      dockerfile: Dockerfile.prod    # name of the Dockerfile (default: Dockerfile)
      args:                          # build arguments (ARG in Dockerfile)
        APP_VERSION: "2.0"

    container_name: my-nginx         # give the container a specific name
                                     # without this, Compose names it automatically

    ports:                           # publish ports (host:container)
      - "8080:80"
      - "8443:443"

    environment:                     # set environment variables
      NODE_ENV: production
      PORT: "3000"
      DB_HOST: database              # use service name for DNS

    env_file:                        # load variables from a file
      - .env                         # a file with KEY=VALUE lines
      - .env.production

    volumes:                         # mount volumes or bind mounts
      - postgres-data:/var/lib/postgresql/data    # named volume
      - ./src:/app/src                            # bind mount
      - ./config/nginx.conf:/etc/nginx/nginx.conf:ro  # read-only bind

    networks:                        # which networks this service connects to
      - frontend-network
      - backend-network

    depends_on:                      # wait for these services to start first
      database:
        condition: service_healthy   # wait until healthy (needs healthcheck)

    healthcheck:                     # how to check if this service is healthy
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 10s

    restart: unless-stopped          # restart policy
                                     # no | always | on-failure | unless-stopped

    command: ["node", "server.js"]   # override CMD from image

    entrypoint: ["node"]             # override ENTRYPOINT from image

    working_dir: /app                # set working directory inside container

    user: "1001:1001"                # run as this user:group

    read_only: true                  # container filesystem is read-only

    tmpfs:                           # create tmpfs mounts
      - /tmp
      - /run

    logging:                         # logging configuration
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

    labels:                          # add metadata labels
      app: mywebapp
      version: "2.0"
      environment: production

    profiles:                        # only start with specific profiles
      - debug

    deploy:                          # deployment configuration (Swarm mode)
      replicas: 3
      resources:
        limits:
          cpus: "0.5"
          memory: 512M
```

Let us now go through the most important keys in detail.

---

### `image` vs `build`

**`image`** — use an existing image from a registry:
```yaml
services:
  database:
    image: postgres:15        # pull postgres version 15 from Docker Hub
```

**`build`** — build your own image from a Dockerfile:
```yaml
services:
  webapp:
    build:
      context: .              # current directory is the build context
      dockerfile: Dockerfile  # Dockerfile in current directory
```

```yaml
services:
  webapp:
    build:
      context: ./frontend     # look for Dockerfile inside the 'frontend' folder
      dockerfile: Dockerfile.dev  # use this specific Dockerfile name
```

You can use BOTH — build an image and give it a tag for caching:
```yaml
services:
  webapp:
    build:
      context: .
    image: mycompany/webapp:latest  # tag the built image with this name
```

---

### `ports`

Publishes container ports to the host machine.

```yaml
ports:
  - "8080:80"       # host port 8080 → container port 80
  - "8443:443"      # host port 8443 → container port 443
  - "127.0.0.1:5432:5432"  # only expose on localhost (more secure)
```

**Why use quotes around ports?**
`8080:80` in YAML without quotes can be interpreted as a time value (hours:minutes).
Always quote port mappings to be safe.

---

### `volumes`

```yaml
services:
  database:
    volumes:
      - postgres-data:/var/lib/postgresql/data  # named volume
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql:ro  # bind mount read-only

  webapp:
    volumes:
      - ./src:/app/src    # bind mount for development
```

**Named volumes** must also be declared at the top level under `volumes:`.
**Bind mounts** (paths starting with `./` or `/`) do not need top-level declaration.

---

### `restart`

Defines what Docker should do if a container stops.

```yaml
restart: no              # never restart (default)
restart: always          # always restart, even after Docker daemon restart
restart: on-failure      # restart only if exit code is non-zero (error)
restart: unless-stopped  # restart always EXCEPT if you manually stopped it
```

**For production services:** use `unless-stopped` or `always`.
**For development:** use `no` or `on-failure`.

---

### `command` and `entrypoint`

Override the CMD or ENTRYPOINT from the image:

```yaml
services:
  webapp:
    image: node:20-alpine
    command: ["npm", "run", "dev"]          # override CMD
    entrypoint: ["node", "--experimental"]  # override ENTRYPOINT
```

## 6. The `networks` Section

### Why Define Networks in Compose?

When you run `docker compose up`, Compose automatically creates a default network for all services in the file.
All services can talk to each other by name on this default network.

But sometimes you want **isolation** — for example:
- Frontend should reach the API but NOT the database directly
- The database should only be reachable by the API

For this, you define custom networks and assign services to specific ones.

### Syntax

```yaml
services:
  frontend:
    image: nginx
    networks:
      - public-network

  api:
    image: node:20-alpine
    networks:
      - public-network    # can talk to frontend
      - private-network   # can talk to database

  database:
    image: postgres:15
    networks:
      - private-network   # ONLY reachable by api, not by frontend

networks:
  public-network:         # declare the network
    driver: bridge        # bridge is the default and most common

  private-network:
    driver: bridge
```

**What happens:**
- `frontend` and `api` are on `public-network` → they can communicate
- `api` and `database` are on `private-network` → they can communicate
- `frontend` and `database` are NOT on the same network → they CANNOT communicate
- Even if someone compromises the frontend, they have no network path to the database

### Using an External Network

Sometimes you want a network that was created outside of Compose (maybe by another Compose file):

```yaml
networks:
  existing-network:
    external: true    # this network already exists, do not create it
    name: my-existing-network
```

## 7. The `volumes` Section

Named volumes used by any service must be declared at the top level.

```yaml
services:
  database:
    volumes:
      - postgres-data:/var/lib/postgresql/data

  cache:
    volumes:
      - redis-data:/data

volumes:
  postgres-data:      # declare the volume (Docker creates it if it does not exist)
  redis-data:         # declare another volume

  # With additional options:
  postgres-data:
    driver: local     # use local driver (default)
    labels:
      environment: production
```

**Using an external volume** (created outside of Compose):

```yaml
volumes:
  existing-volume:
    external: true    # this volume already exists, do not create it
```

## 8. depends_on — Controlling Start Order

### The Problem

Your Node.js backend needs the database to be running before it starts.
If the backend starts first and tries to connect to a database that is not ready — it crashes.

`depends_on` tells Compose: "Start this service only AFTER these other services."

### Simple depends_on (Start Order Only)

```yaml
services:
  backend:
    image: node:20-alpine
    depends_on:
      - database    # start database before backend

  database:
    image: postgres:15
```

**Important limitation:**
This only guarantees the `database` CONTAINER has started.
It does NOT guarantee PostgreSQL inside the container is actually ready to accept connections.

PostgreSQL takes a few seconds to initialize after the container starts.
If your backend tries to connect in those first seconds — connection refused.

### depends_on with condition (Proper Solution)

This is the correct and professional way.
It waits until the service is actually HEALTHY (passing its healthcheck):

```yaml
services:
  backend:
    image: node:20-alpine
    depends_on:
      database:
        condition: service_healthy    # wait until database is HEALTHY

  database:
    image: postgres:15
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s      # check every 5 seconds
      timeout: 5s       # each check times out after 5 seconds
      retries: 5        # must pass 5 times... no, must fail 5 times before unhealthy
      start_period: 10s # wait 10 seconds before starting checks
```

**What `condition: service_healthy` means:**

`service_healthy` = do not start the `backend` until `database` passes its healthcheck.

The database healthcheck runs `pg_isready -U postgres` every 5 seconds.
`pg_isready` = a PostgreSQL tool that returns success if PostgreSQL is accepting connections.
Once this passes, Compose starts the backend.

**Three conditions available:**

```yaml
depends_on:
  service-name:
    condition: service_started    # container started (default — does not wait for ready)
    condition: service_healthy    # healthcheck is passing
    condition: service_completed_successfully  # container exited with code 0 (for setup jobs)
```

## 9. environment — Passing Configuration

### Two Ways to Set Environment Variables

**Method 1 — Inline in the Compose file:**
```yaml
services:
  webapp:
    environment:
      NODE_ENV: production
      PORT: "3000"
      DB_HOST: database    # 'database' is the service name — Docker DNS resolves it
      DB_PORT: "5432"
```

**Method 2 — Using an .env file:**

Create a file named `.env` in the same folder as your `docker-compose.yml`:
```
# .env file contents
NODE_ENV=production
PORT=3000
DB_HOST=database
DB_PASSWORD=mysecretpassword
```

Reference it in Compose:
```yaml
services:
  webapp:
    env_file:
      - .env
```

Or reference variables from the host environment:
```yaml
services:
  webapp:
    environment:
      DB_PASSWORD: ${DB_PASSWORD}  # takes value from YOUR shell's environment
```

`${DB_PASSWORD}` = this syntax means "read the value of `DB_PASSWORD` from the host environment."

### The .env File — Variable Substitution in Compose

Docker Compose automatically reads a `.env` file in the same directory.
You can use these variables ANYWHERE in the Compose file with `${VARIABLE_NAME}`:

```
# .env file
POSTGRES_VERSION=15
APP_PORT=3000
```

```yaml
# docker-compose.yml
services:
  database:
    image: postgres:${POSTGRES_VERSION}   # becomes postgres:15

  webapp:
    ports:
      - "${APP_PORT}:3000"               # becomes 3000:3000
```

**Security note:**
Never put real passwords in `docker-compose.yml` directly if it is in a public Git repo.
Put them in `.env` and add `.env` to your `.gitignore` file.

## 10. healthcheck — Is the Service Ready?

We saw healthcheck inside `depends_on`. Here is the full picture.

### Why Healthchecks Matter

A container being "running" does not mean the service inside is ready.
PostgreSQL takes time to initialize.
A Node.js server takes time to start.
During that time, `docker ps` shows the container as running — but it is not actually ready.

Healthchecks let Docker periodically check if the service is actually working.

### Healthcheck Syntax

```yaml
services:
  webapp:
    image: myapp:latest
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s      # run check every 30 seconds
      timeout: 10s       # if check takes longer than 10 seconds, it fails
      retries: 3         # must fail 3 times IN A ROW to become unhealthy
      start_period: 15s  # grace period — do not count failures in first 15 seconds
```

**Breaking down `test`:**

`["CMD", "curl", "-f", "http://localhost:3000/health"]`

This is a list of strings that forms a command.
`CMD` = run this command directly (without a shell)
`curl` = the HTTP tool
`-f` = fail silently on HTTP errors (return non-zero exit code for 4xx/5xx responses)
`http://localhost:3000/health` = the URL to check

If the command returns exit code `0` → healthy.
If it returns non-zero → unhealthy (after retries).

**Different test commands:**

```yaml
# For a web server with curl
test: ["CMD", "curl", "-f", "http://localhost:8080/health"]

# For a web server without curl (using wget instead — common in Alpine)
test: ["CMD-SHELL", "wget -qO- http://localhost:8080/health || exit 1"]

# For PostgreSQL
test: ["CMD-SHELL", "pg_isready -U postgres -d mydb"]

# For MySQL
test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]

# For Redis
test: ["CMD", "redis-cli", "ping"]

# TCP port check (when no HTTP endpoint exists)
test: ["CMD-SHELL", "nc -z localhost 5432 || exit 1"]
```

**CMD vs CMD-SHELL:**

`CMD` = run the command directly. No shell. No `&&`, `||`, `>`, etc.
`CMD-SHELL` = run through `/bin/sh -c`. Can use shell operators like `&&`, `||`, `>`.

### Health States

After a healthcheck is defined, the container shows one of three states:

```
starting   → container just started, within start_period grace window
healthy    → last check returned exit code 0
unhealthy  → check failed more than 'retries' times in a row
```

```bash
# See current health status
docker inspect mycontainer | jq '.[0].State.Health.Status'

# See the last 5 health check results (log of each check)
docker inspect mycontainer | jq '.[0].State.Health.Log'
```

## 11. profiles — Conditional Services

### What is a Profile?

A profile is a label you give to a service.
That service only starts when you explicitly enable that profile.

**Use case:**
You have extra services that are only needed sometimes:
- A database admin tool (pgAdmin) — only needed when debugging
- A mock email server — only needed in development
- A metrics tool — only needed when testing performance

You do not want these starting in production or every time you run `docker compose up`.
Profiles let you include them only when specifically needed.

### Syntax

```yaml
services:
  # These start ALWAYS (no profile)
  webapp:
    image: myapp:latest

  database:
    image: postgres:15

  # This ONLY starts when 'debug' profile is enabled
  pgadmin:
    image: dpage/pgadmin4
    profiles:
      - debug
    ports:
      - "5050:80"
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@admin.com
      PGADMIN_DEFAULT_PASSWORD: admin

  # This ONLY starts when 'dev' profile is enabled
  mailhog:
    image: mailhog/mailhog
    profiles:
      - dev
    ports:
      - "8025:8025"
```

### Using Profiles

```bash
# Start only the always-on services (webapp + database)
docker compose up -d

# Start with the debug profile (webapp + database + pgadmin)
docker compose --profile debug up -d

# Start with multiple profiles
docker compose --profile debug --profile dev up -d

# Or set via environment variable
COMPOSE_PROFILES=debug docker compose up -d
```

## 12. Docker Compose Commands

### The Essential Commands

```bash
# Start all services (in background with -d)
docker compose up -d
```

`docker compose` = the Docker Compose plugin command
`up` = start all services defined in docker-compose.yml
`-d` = detached mode. Run in background. Without this, logs stream to your terminal and Ctrl+C stops everything.

```bash
# Stop and remove all containers, networks
docker compose down
```

`down` = stop all services AND remove containers AND remove networks that Compose created.
Volumes are NOT removed by default.

```bash
# Stop and remove everything INCLUDING volumes (CAREFUL — data loss!)
docker compose down -v
```

`-v` = also remove volumes. This deletes all data in named volumes.
Use with extreme caution. You will lose database data.

```bash
# See running services
docker compose ps
```

Shows all services with their current status (running, exited, etc.)

```bash
# See logs of all services
docker compose logs
```

Shows all log output from all services combined.

```bash
# Follow logs in real time
docker compose logs -f
```

`-f` = follow. Keeps printing new log lines as they come in. Press Ctrl+C to stop following.

```bash
# See logs of only one specific service
docker compose logs -f webapp
```

`webapp` = the service name from your Compose file.

```bash
# Restart a specific service
docker compose restart webapp
```

Stops and restarts just the `webapp` service.

```bash
# Pull latest images for all services
docker compose pull
```

Downloads the latest version of all images defined with `image:` in your Compose file.

```bash
# Build images for services that use 'build:'
docker compose build
```

```bash
# Build and start (build then up)
docker compose up --build -d
```

`--build` = force rebuild images before starting. Use this when you change your Dockerfile or source code and want to rebuild before starting.

```bash
# Run a one-off command in a service
docker compose run --rm webapp sh
```

`run` = create a new container for a service and run a command in it.
`--rm` = delete the container when the command finishes.
`webapp` = which service to base the container on (inherits its image, networks, volumes).
`sh` = the command to run (open a shell).

```bash
# Execute a command in an ALREADY RUNNING service
docker compose exec webapp sh
```

`exec` = run a command in an already running container (like `docker exec`).
`webapp` = the running service name.

```bash
# Scale a service (run multiple copies)
docker compose up -d --scale webapp=3
```

`--scale webapp=3` = run 3 copies of the webapp service.
Note: if you have `container_name` set, you cannot scale (names must be unique).

```bash
# See resource usage
docker compose top
```

Shows all processes running inside all Compose services.

## 13. A Complete Real-World Example

Here is a complete three-tier application — frontend, backend API, PostgreSQL — using all the concepts we learned.

```yaml
# docker-compose.yml
# Full three-tier application with proper networking, volumes, healthchecks

services:

  # ─── PostgreSQL Database ────────────────────────────────────────────────────
  database:
    image: postgres:15-alpine
    container_name: myapp-database
    restart: unless-stopped

    environment:
      POSTGRES_DB: ${POSTGRES_DB:-myapp}          # use env var, default to 'myapp'
      POSTGRES_USER: ${POSTGRES_USER:-appuser}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}      # MUST be set in .env, no default

    volumes:
      - postgres-data:/var/lib/postgresql/data    # persist database files
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro  # run on first start

    networks:
      - backend-network    # only on backend network — frontend cannot reach it

    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-appuser} -d ${POSTGRES_DB:-myapp}"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s   # postgres needs time to initialize on first start

    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

  # ─── Node.js Backend API ────────────────────────────────────────────────────
  backend:
    build:
      context: ./backend   # folder containing backend Dockerfile
      dockerfile: Dockerfile
    image: myapp-backend:latest
    container_name: myapp-backend
    restart: unless-stopped

    depends_on:
      database:
        condition: service_healthy    # wait until PostgreSQL is ready

    environment:
      NODE_ENV: production
      PORT: "5000"
      DATABASE_URL: postgresql://${POSTGRES_USER:-appuser}:${POSTGRES_PASSWORD}@database:5432/${POSTGRES_DB:-myapp}
      JWT_SECRET: ${JWT_SECRET}

    volumes:
      - uploads-data:/app/uploads    # persist user uploaded files

    networks:
      - backend-network     # can talk to database
      - frontend-network    # can be reached by frontend

    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 15s

    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

  # ─── React Frontend ─────────────────────────────────────────────────────────
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    image: myapp-frontend:latest
    container_name: myapp-frontend
    restart: unless-stopped

    depends_on:
      backend:
        condition: service_healthy    # wait until backend API is ready

    ports:
      - "${FRONTEND_PORT:-3000}:80"  # expose to host on configurable port

    environment:
      REACT_APP_API_URL: http://localhost:${FRONTEND_PORT:-3000}/api

    networks:
      - frontend-network    # can reach backend, cannot reach database

    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:80"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 10s

  # ─── pgAdmin (only in debug profile) ────────────────────────────────────────
  pgadmin:
    image: dpage/pgadmin4:latest
    container_name: myapp-pgadmin
    restart: unless-stopped

    profiles:
      - debug    # only starts when --profile debug is used

    depends_on:
      database:
        condition: service_healthy

    ports:
      - "5050:80"

    environment:
      PGADMIN_DEFAULT_EMAIL: admin@myapp.com
      PGADMIN_DEFAULT_PASSWORD: ${PGADMIN_PASSWORD:-adminpassword}

    networks:
      - backend-network    # needs to reach database

# ─── Networks ──────────────────────────────────────────────────────────────────
networks:
  frontend-network:
    driver: bridge

  backend-network:
    driver: bridge

# ─── Volumes ───────────────────────────────────────────────────────────────────
volumes:
  postgres-data:          # database files — most important data
    labels:
      backup: "required"

  uploads-data:           # user uploaded files
    labels:
      backup: "required"
```

The `.env` file that goes with this:

```bash
# .env — do NOT commit this to Git
POSTGRES_DB=myapp
POSTGRES_USER=appuser
POSTGRES_PASSWORD=supersecurepassword123
JWT_SECRET=myverylongjwtsecretkey
FRONTEND_PORT=3000
PGADMIN_PASSWORD=adminpassword
```

Running this:

```bash
# Start the main application
docker compose up -d

# Start with pgAdmin for debugging
docker compose --profile debug up -d

# See all services and their health
docker compose ps

# Follow backend logs
docker compose logs -f backend

# Stop everything (keeps data in volumes)
docker compose down

# Stop and wipe all data (DANGEROUS)
docker compose down -v
```

```bash
# Create a lab directory
```

`cat > docker-compose.yml` = create a file named docker-compose.yml

`ports:` = port mappings list
`"8080:80"` = host port 8080 → container port 80

`./html:/usr/share/nginx/html:ro` = bind mount the local html/ folder, read-only

```bash
# Create an HTML file for nginx to serve

docker compose up -d
```

```bash
# Check it is running
docker compose ps

# Test it
curl http://localhost:8080

# Change the HTML file and see it update immediately (bind mount magic)
echo "<h1>Updated by Muskan!</h1>" > html/index.html
curl http://localhost:8080

# See logs
docker compose logs web

docker compose down
```

### Lab 3 — PostgreSQL with Healthcheck and depends_on

```bash
mkdir -p /home/$USER/docker-labs/compose-lab3
cd /home/$USER/docker-labs/compose-lab3

cat > docker-compose.yml << 'EOF'
services:
  database:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB: testdb
      POSTGRES_USER: testuser
      POSTGRES_PASSWORD: testpass
    volumes:
      - pg-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U testuser -d testdb"]
      interval: 5s
      timeout: 5s
      retries: 5
      start_period: 10s

  app:
    image: postgres:15-alpine
    depends_on:
      database:
        condition: service_healthy
    command: >
      sh -c "
        echo 'Database is healthy - connecting...' &&
        psql postgresql://testuser:testpass@database:5432/testdb -c 'SELECT NOW();'
      "

volumes:
  pg-data:
EOF
```

`command: >` = the `>` in YAML means the following indented block is one long string with newlines replaced by spaces. Used to write long commands across multiple lines for readability.

```bash
# Start everything

# 1. database container starts
# 2. healthcheck runs (starting state)
# 3. healthcheck passes (healthy state)
# 4. app container starts ONLY after database is healthy
# 5. app successfully connects to the database

# The app shows a timestamp from SELECT NOW()
```

Without `-d`, logs stream to your terminal so you can watch the sequence happen.

```bash

```

`-v` = also remove the pg-data volume (deletes database data — fine for this lab)

### Lab 5 — Profiles

```bash
mkdir -p /home/$USER/docker-labs/compose-lab5
cd /home/$USER/docker-labs/compose-lab5

cat > docker-compose.yml << 'EOF'
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"

  debug-tool:
    image: alpine
    profiles:
      - debug
    command: sh -c "echo 'Debug tool started!' && sleep infinity"

  monitoring:
    image: alpine
    profiles:
      - monitoring
    command: sh -c "echo 'Monitoring tool started!' && sleep infinity"
EOF
```

`sleep infinity` = keep the container running forever (otherwise it would exit immediately)

```bash
# Start WITHOUT any profile — only 'web' starts
docker compose up -d
docker compose ps
# Only 'web' shows up

# Start WITH debug profile — 'web' AND 'debug-tool' start
docker compose --profile debug up -d
docker compose ps
# Both 'web' and 'debug-tool' show up

# Stop all
docker compose --profile debug down

# Start with BOTH profiles
docker compose --profile debug --profile monitoring up -d
docker compose ps
# All three services running

# Clean up
docker compose --profile debug --profile monitoring down
```

## 15. Quick Revision Cheatsheet

| Key in docker-compose.yml | What It Does |
|--------------------------|-------------|
| `services:` | Top-level section. Every container is defined here. |
| `image:` | Which Docker image to use |
| `build:` | Build an image from a Dockerfile |
| `ports:` | Publish ports. Format: `"host:container"` |
| `volumes:` | Mount volumes or bind mounts |
| `networks:` | Which networks this service connects to |
| `environment:` | Set environment variables |
| `env_file:` | Load variables from a file |
| `depends_on:` | Start this service only after others |
| `healthcheck:` | Command to periodically test if service is ready |
| `restart:` | What to do when container stops |
| `command:` | Override CMD from image |
| `profiles:` | Only start with specific profile name |
| `container_name:` | Give container a specific name |
| `logging:` | Configure log driver and options |

| Command | What It Does |
|---------|-------------|
| `docker compose up -d` | Start all services in background |
| `docker compose down` | Stop and remove containers and networks |
| `docker compose down -v` | Same plus remove volumes (data loss!) |
| `docker compose ps` | See status of all services |
| `docker compose logs -f` | Follow all service logs |
| `docker compose logs -f servicename` | Follow one service's logs |
| `docker compose restart servicename` | Restart one service |
| `docker compose exec servicename sh` | Shell into running service |
| `docker compose run --rm servicename sh` | New container from service |
| `docker compose build` | Build all images |
| `docker compose up --build -d` | Build then start |
| `docker compose pull` | Pull latest images |
| `docker compose --profile name up -d` | Start with a profile |
| `docker compose top` | Show processes in containers |
| `docker compose config` | Validate and print the composed config |

| Concept | Remember |
|---------|----------|
| Default network | Compose creates one automatically — all services can talk by name |
| Custom networks | For isolation — control which services can reach each other |
| depends_on (simple) | Only guarantees container started, not service ready |
| depends_on + condition: service_healthy | Waits for healthcheck to pass — the right way |
| .env file | Auto-loaded by Compose — use `${VARIABLE}` in compose file |
| Profiles | Services without profiles always start. Profiled services only start when named. |
| `docker compose` vs `docker-compose` | New: `docker compose` (space). Old: `docker-compose` (hyphen). Use the new one. |
