## Basic Level Questions

### Q1. What is a Docker registry? Why do we need one?

**How the interviewer asks it:**
> "Explain what a Docker registry is and why it exists."

**Your Answer:**

> "A Docker registry is a storage and distribution server for Docker images. Think of it like GitHub but for container images instead of source code.
>
> We need it to solve the image distribution problem. When you build a Docker image on your laptop, it only exists on your machine. To deploy it to production servers, share it with teammates, or use it in a CI/CD pipeline, you need a central place to store and distribute it.
>
> The workflow is simple: you push your image to the registry once, and anyone with access can pull it from anywhere — your servers, your CI runner, your colleague's laptop. No manual copying of files, no scp, no shared drives.
>
> Docker Hub is the default public registry. When you run `docker pull nginx`, Docker automatically contacts Docker Hub. For company-specific private images, teams typically use AWS ECR, GitHub Container Registry, or a self-hosted registry."

---

### Q2. What is the difference between `docker pull` and `docker push`?

**How the interviewer asks it:**
> "Explain what these two commands do."

**Your Answer:**

> "`docker pull` downloads an image FROM a registry to your local machine. When you run `docker pull nginx:1.25`, Docker contacts the registry, checks which layers it needs, downloads only the layers you do not already have, and assembles the image locally. This download of only missing layers is efficient — if you already have Ubuntu base layers locally, and you pull a Node.js image built on Ubuntu, Docker reuses those existing layers.
>
> `docker push` uploads an image FROM your local machine TO a registry. Before pushing, you need to be authenticated to the registry. The image tag must include the registry URL and your username — for Docker Hub that is `username/imagename:tag`. Docker again only uploads layers the registry does not already have.
>
> The key prerequisite for push that is not needed for public pull: authentication. You must be logged in with `docker login` before pushing. For AWS ECR, you use a special command to get a temporary 12-hour token from AWS IAM."

### Q3. Why is the `latest` tag dangerous in production? What should you use instead?

**How the interviewer asks it:**
> "I see a lot of Dockerfiles using `:latest`. Is that a problem?"

**Your Answer:**

> "Yes, `latest` is dangerous in production because it is a mutable tag — it moves. `latest` does not mean 'the latest stable version' — it just means 'whatever was most recently pushed with this tag.'
>
> Here is the real danger: imagine you deploy 3 servers with `myapp:latest` on Monday — they all get version 1.5. On Wednesday, CI builds a new version 1.6 with a bug and pushes it as `myapp:latest`. On Thursday, one server crashes and auto-scaling starts a new one — it pulls `myapp:latest` and gets version 1.6. Now you have inconsistent servers: two running 1.5, one running 1.6. Worse, you may not even realise what changed because everything is labelled `latest`.
>
> The solution is semantic versioning for image tags:
> ```bash
> docker tag myapp myapp:2.1.3   # specific — immutable
> docker tag myapp myapp:2.1     # minor
> docker tag myapp myapp:2       # major
> docker tag myapp myapp:latest  # convenience alias
> ```
>
> In production I always reference the specific version like `myapp:2.1.3`. I also tag with the Git commit hash (`myapp:abc1234`) so I can always trace exactly which code is running. In my banking project, using commit hashes as image tags allowed us to instantly identify which code was deployed on any server just by looking at the running container image tag."

### Q4. What is the full format of a Docker image name?

**How the interviewer asks it:**
> "Explain the structure of `123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0`."

**Your Answer:**

> "A full Docker image name has four parts: `registry/namespace/imagename:tag`.
>
> Breaking down that ECR example:
>
> `123456789012.dkr.ecr.us-east-1.amazonaws.com` — this is the registry hostname. For AWS ECR, it includes your AWS account ID (`123456789012`), the ECR service identifier (`dkr.ecr`), the AWS region (`us-east-1`), and the AWS domain.
>
> `myapp` — this is the repository name (equivalent to the image name on Docker Hub).
>
> `1.0` — this is the tag, indicating the version.
>
> For Docker Hub, the format is simpler because it is the default registry:
> - `nginx` → expands to `docker.io/library/nginx:latest` (official image)
> - `muskanpatel71198/myapp:1.0` → expands to `docker.io/muskanpatel71198/myapp:1.0`
>
> When you push to any non-Docker Hub registry, the image name MUST start with the registry hostname. That is how Docker knows where to push. If it does not start with a hostname containing a dot or colon, Docker assumes Docker Hub."

### Q5. What is the difference between Docker Hub official images and community images?

**How the interviewer asks it:**
> "How do I know if an image from Docker Hub is safe to use?"

**Your Answer:**

> "Docker Hub has three categories of images.
>
> Official images are maintained by Docker Inc. in partnership with software vendors. They are reviewed for security, follow best practices, and receive regular updates. You identify them by their lack of a username prefix — just `nginx`, `postgres`, `node`, `python`. In production I only use official or verified publisher images for base images.
>
> Verified publisher images come from companies that Docker has verified — they have the company name as a prefix like `bitnami/postgresql` or `grafana/grafana`. These are also trustworthy.
>
> Community images are from regular users — `someuser/someimagename`. Quality and security vary enormously. These can contain malware, backdoors, or simply outdated software. I never use community images in production from unknown publishers. If I need something that only exists as a community image, I inspect the Dockerfile first, and consider building my own from an official base.
>
> For our banking application, we had a strict policy: only official Docker images for base images, and any third-party image required security team review. We scanned everything with Trivy before deployment."

### Q6. How does authentication work for Docker Hub, ECR, and private registries?

**How the interviewer asks it:**
> "Walk me through how you authenticate to push an image to Docker Hub and to AWS ECR."

**Your Answer:**

> "For Docker Hub, it is straightforward:
> ```bash
> docker login   # prompts for username and password
> # Or non-interactively in CI:
> echo '$DOCKER_PASSWORD' | docker login --username '$DOCKER_USERNAME' --password-stdin
> ```
> Docker stores the credentials in `~/.docker/config.json` as a base64-encoded string.
>
> For AWS ECR, it works differently because ECR uses AWS IAM for authentication. Instead of a permanent username/password, you get a temporary 12-hour token:
> ```bash
> aws ecr get-login-password --region us-east-1 | \
>   docker login --username AWS --password-stdin \
>   123456789012.dkr.ecr.us-east-1.amazonaws.com
> ```
> `aws ecr get-login-password` calls the AWS API, which checks your IAM permissions and returns a token. That token is piped to `docker login`. The username is always literally `AWS` for ECR.
>
> In CI/CD pipelines, I never hardcode credentials. For Docker Hub I use GitHub Actions secrets or Jenkins credentials. For ECR, I use IAM roles attached to the EC2 instance or GitHub Actions OIDC integration — so no credentials are stored anywhere at all. The AWS API grants access based on the IAM role, and the `aws ecr get-login-password` command works automatically."

### Q7. What is image scanning? What is Trivy and how do you use it?

**How the interviewer asks it:**
> "How do you ensure Docker images do not contain security vulnerabilities?"

**Your Answer:**

> "Docker images can contain hundreds of packages — OS packages, language runtimes, libraries. Any of these might have known security vulnerabilities called CVEs. Without scanning, you would deploy these vulnerabilities to production without knowing.
>
> Image scanning compares everything in your image against a database of known CVEs and reports what it finds with severity levels: Critical, High, Medium, Low.
>
> Trivy is my preferred scanner — it is free, open-source, maintained by Aqua Security, and very accurate:
> ```bash
> # Scan any image
> trivy image nginx:latest
>
> # Only show what matters (High and Critical)
> trivy image --severity HIGH,CRITICAL node:20-alpine
>
> # In CI — fail the pipeline if Critical vulnerabilities found
> trivy image --exit-code 1 --severity CRITICAL myapp:${GIT_HASH}
> ```
>
> The last command is the key for CI/CD. `--exit-code 1` means if critical vulnerabilities are found, Trivy returns exit code 1 and the pipeline fails. The image never gets pushed to the registry.
>
> This practice is called 'shifting security left' — catching vulnerabilities during build time rather than finding them in production through an incident.
>
> In my banking project, we ran Trivy in every CI pipeline. Critical vulnerabilities blocked the deployment. High vulnerabilities created a Jira ticket that had to be resolved within 48 hours. We also rescanned images weekly against the updated vulnerability database because new CVEs are discovered every day."

### Q8. What is ECR and why do companies use it instead of Docker Hub?

**How the interviewer asks it:**
> "Your company is on AWS. Should you use Docker Hub or ECR for storing images?"

**Your Answer:**

> "For a company on AWS, ECR is almost always the better choice for several reasons.
>
> First, access control. ECR integrates with AWS IAM. You can give an EC2 instance or ECS task an IAM role that allows it to pull images — no credentials stored anywhere. With Docker Hub, you need to manage username/password credentials on every server.
>
> Second, reliability. Docker Hub has pull rate limits — 100 pulls per 6 hours for anonymous, 200 for free accounts. In a CI/CD pipeline with many builds, or with auto-scaling adding new instances, you hit these limits easily. ECR has no rate limits from the AWS side.
>
> Third, network performance. ECR is inside the AWS network. Pulling images from ECR to ECS or EKS is fast because the data never leaves AWS. Docker Hub pulls cross the public internet — slower and you pay for data transfer.
>
> Fourth, security. ECR has built-in vulnerability scanning powered by Amazon Inspector, and you can enable image immutability — preventing a tag from being overwritten once pushed. This gives you stronger guarantees about what is actually running.
>
> The main cost consideration: ECR charges for storage and data transfer. Docker Hub's free tier is cheaper if you have very small usage. But for production AWS workloads, ECR is the standard choice.
>
> In our Atos project, we used ECR for all application images and Docker Hub only for pulling official base images like `node:20-alpine` or `postgres:15`."

### Q9. What is a lifecycle policy in ECR and why is it important?

**How the interviewer asks it:**
> "How do you prevent your ECR repository from filling up with old images?"

**Your Answer:**

> "Every time CI/CD runs, it typically pushes a new image. Without any cleanup, you accumulate hundreds or thousands of images over time, each taking storage space and incurring cost.
>
> ECR lifecycle policies are rules that automatically delete old images. You define the rules in JSON and apply them to a repository:
>
> ```json
> {
>   'rules': [
>     {
>       'rulePriority': 1,
>       'description': 'Keep only the 10 most recent images',
>       'selection': {
>         'tagStatus': 'any',
>         'countType': 'imageCountMoreThan',
>         'countNumber': 10
>       },
>       'action': { 'type': 'expire' }
>     }
>   ]
> }
> ```
>
> This rule keeps the 10 most recently pushed images and deletes everything older.
>
> More sophisticated policies can distinguish between tagged and untagged images, or between image ages versus counts.
>
> In practice, I usually keep the last 20 tagged images for rollback capability, and aggressively clean up untagged images (dangling images from builds that did not complete properly).
>
> Without lifecycle policies, I have seen ECR repositories with 2,000+ old images taking 50GB of storage. The lifecycle policy keeps it clean automatically with zero ongoing effort."

### Q10. How do you integrate image scanning into a CI/CD pipeline?

**How the interviewer asks it:**
> "Walk me through a secure CI/CD pipeline that builds, scans, and pushes a Docker image."

**Your Answer:**

> "Here is the pipeline I would build, using GitHub Actions as an example:
>
> ```yaml
> jobs:
>   build-and-push:
>     runs-on: ubuntu-latest
>     steps:
>       # Step 1: Check out the code
>       - uses: actions/checkout@v4
>
>       # Step 2: Build the image with the git commit hash as tag
>       - name: Build image
>         run: |
>           GIT_HASH=$(git rev-parse --short HEAD)
>           docker build -t myapp:${GIT_HASH} .
>
>       # Step 3: Scan for vulnerabilities BEFORE pushing
>       - name: Scan image with Trivy
>         uses: aquasecurity/trivy-action@master
>         with:
>           image-ref: myapp:${GIT_HASH}
>           severity: 'CRITICAL'
>           exit-code: '1'
>         # Pipeline STOPS HERE if Critical vulnerabilities found
>
>       # Step 4: Only reaches here if scan passed
>       - name: Login to ECR
>         run: |
>           aws ecr get-login-password --region us-east-1 | \
>             docker login --username AWS --password-stdin \
>             ${{ secrets.ECR_REGISTRY }}
>
>       # Step 5: Tag and push
>       - name: Push to ECR
>         run: |
>           GIT_HASH=$(git rev-parse --short HEAD)
>           docker tag myapp:${GIT_HASH} ${{ secrets.ECR_REGISTRY }}/myapp:${GIT_HASH}
>           docker push ${{ secrets.ECR_REGISTRY }}/myapp:${GIT_HASH}
>
>       # Step 6: Deploy
>       - name: Deploy
>         run: |
>           kubectl set image deployment/myapp \
>             myapp=${{ secrets.ECR_REGISTRY }}/myapp:${GIT_HASH}
> ```
>
> Key security principles in this pipeline:
> - Scan BEFORE push — never push a vulnerable image to the registry
> - Use commit hash tags — every deployment is traceable to exact code
> - No credentials in the code — AWS credentials come from IAM role, Docker Hub password from GitHub secrets
> - Fail the pipeline on Critical — vulnerabilities must be fixed before deployment"

### Q11. How do you handle Docker Hub rate limits in CI/CD?

**How the interviewer asks it:**
> "Our CI pipeline is hitting Docker Hub rate limits. How do you fix this?"

**Your Answer:**

> "Docker Hub's rate limit of 100 pulls per 6 hours for anonymous users is easy to hit in CI. There are several strategies.
>
> **Strategy 1 — Log in to Docker Hub in CI:**
> Even a free account gets 200 pulls per 6 hours. Add Docker Hub credentials to CI secrets and login at the start of each pipeline. This doubles your limit immediately.
>
> **Strategy 2 — Use ECR as a mirror/cache:**
> Pull official images from Docker Hub once, push them to your ECR, then pull from ECR. Your CI pulls from ECR — no rate limits. This is called a pull-through cache:
> ```bash
> # Pull from Docker Hub
> docker pull node:20-alpine
>
> # Push to your ECR
> docker tag node:20-alpine 123456789012.dkr.ecr.us-east-1.amazonaws.com/node:20-alpine
> docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/node:20-alpine
>
> # CI pulls from ECR instead
> ```
> AWS ECR now supports pull-through cache rules that automate this.
>
> **Strategy 3 — Use GitHub Container Registry or Quay.io:**
> Some public images are mirrored on other registries with no rate limits.
>
> **Strategy 4 — Upgrade Docker Hub account:**
> A Docker Pro or Team subscription gives unlimited pulls.
>
> In our setup at Atos, we used ECR as a mirror for all base images. Our Dockerfiles always pulled from our ECR mirror, never from Docker Hub directly. This also improved build times because ECR is inside AWS network — faster than Docker Hub."

### Q12. What is image immutability and why does it matter?

**How the interviewer asks it:**
> "What does image immutability mean in the context of a container registry?"

**Your Answer:**

> "Image immutability means that once an image is pushed with a specific tag, that tag cannot be overwritten with a different image.
>
> Without immutability, someone can push a new image over `myapp:1.0`. Suddenly `myapp:1.0` points to different code than it did yesterday. Anyone who pulls `myapp:1.0` gets different software than what was tested and approved. Rollbacks also become unreliable — you might 'rollback' to `myapp:1.0` and get code you have never seen before.
>
> ECR lets you enable image tag immutability per repository:
> ```bash
> aws ecr put-image-tag-mutability \
>   --repository-name myapp \
>   --image-tag-mutability IMMUTABLE
> ```
>
> After this, if you try to push a different image with the same tag, ECR rejects it with an error. The only way to 'update' is to use a different tag.
>
> Combined with semantic versioning — every new build gets a new version number — this gives you a strong guarantee: `myapp:2.1.3` always means exactly the same image, forever. This is essential for compliance and audit trails in regulated industries.
>
> In our banking project, image tag immutability was a mandatory requirement. Auditors needed to verify that the code deployed in production was exactly what was tested and approved. Immutable tags made this proof trivial — the tag never changed."

### Q13. "We pushed a critical security patch but our servers are still running the old vulnerable image. How do you ensure all servers update?"

**Your Answer:**

> "This is a deployment problem, not just a registry problem. Here is the full approach.
>
> **Step 1 — Verify the new image is actually in the registry:**
> ```bash
> aws ecr describe-images --repository-name myapp --query 'sort_by(imageDetails,&imagePushedAt)[-1]'
> ```
> Confirm the new version is pushed with the expected tag.
>
> **Step 2 — Force containers to use the new image:**
> If using Kubernetes:
> ```bash
> kubectl set image deployment/myapp myapp=ECR_URL/myapp:2.1.4-patched
> kubectl rollout status deployment/myapp
> ```
> Kubernetes does a rolling update — starts new pods with the new image, waits for them to be healthy, then removes old pods.
>
> If using Docker Compose on standalone servers:
> ```bash
> docker compose pull   # pull new image
> docker compose up -d  # recreate containers with new image
> ```
>
> **Step 3 — Verify the update:**
> ```bash
> # In Kubernetes
> kubectl get pods -o jsonpath='{.items[*].spec.containers[*].image}'
>
> # With docker
> docker inspect <container> | jq '.[0].Config.Image'
> ```
>
> **Prevention for the future:**
> Set up automatic image updates. Tools like Watchtower (for Docker) or Keel/ArgoCD (for Kubernetes) can automatically detect new images in the registry and update running containers.
>
> Also, periodic rescanning of running images with Trivy catches newly-discovered vulnerabilities — a CVE can be published for a vulnerability that has existed for years."

---

### Q14. "Someone pushed a malicious image to our registry. How do you detect and respond?"

**Your Answer:**

> "This is an insider threat or compromised credential scenario. Here is the response:
>
> **Immediate detection:**
> Run Trivy or another scanner against all images in the registry. A malicious image often contains known malware that Snyk and Trivy can detect. Also look for unusual packages or files — a production web server image should not contain network scanning tools or cryptocurrency miners.
>
> **Check registry access logs:**
> ECR logs all API calls to AWS CloudTrail. Review who pushed what and when:
> ```bash
> aws cloudtrail lookup-events \
>   --lookup-attributes AttributeKey=EventName,AttributeValue=PutImage \
>   --start-time 2026-01-01
> ```
>
> **Immediate response:**
> If a malicious image is confirmed, immediately delete it from the registry. In ECR, you can also make tags immutable to prevent it being pushed again.
>
> If it was already deployed, immediately stop the affected containers and deploy known-good versions.
>
> Rotate all credentials that had push access — the attacker may have stolen them.
>
> **Prevention:**
> Require all images to pass Trivy scan before being accepted into the registry. Set up registry webhooks that trigger a scan on every push. Use signed images (Docker Content Trust) so only images signed by authorised keys are accepted.
>
> Principle of least privilege for push access — only CI/CD service accounts should have push access. Developers should only have pull access in production registries."
