## 1. Why Does a Registry Exist? The Problem First

### The Story

You build a Docker image on your laptop.
It works perfectly.
Now you need to deploy it to a production server on AWS.

How does the image get from your laptop to the server?

**Option 1 — Copy the image manually:**
You could export the image to a file and copy it to the server.

```bash
# Export on your laptop
docker save myapp:1.0 > myapp.tar

# Copy to server somehow (SCP, USB, etc.)
scp myapp.tar user@server:/tmp/

# Load on the server
docker load < /tmp/myapp.tar
```

This works for one server.
But what about 10 servers? 100 servers?
What about automated deployments where no human is involved?
What about your CI/CD pipeline needing the image?
What about teammates who need the same image?

This approach does not scale at all.

**Option 2 — Use a Registry:**

A registry is a central storage server for Docker images.

- You push the image to the registry once
- Anyone with access can pull it from anywhere
- CI/CD pipelines pull automatically
- All your servers pull automatically
- Your team members pull automatically

```
Your Laptop          Registry              Production Servers
   │                    │                       │
   │  docker push ──────▶                       │
   │                    │◀───── docker pull ─────│
   │                    │◀───── docker pull ─────│
   │                    │◀───── docker pull ─────│
   │                    │                       │
   CI/CD Pipeline       │
   │◀─── docker pull ───│
```

One push. Everyone gets it. That is the registry.

## 2. What is a Docker Registry?

### Simple Definition

A Docker registry is a **storage and distribution server for Docker images**.

Think of it like **GitHub but for Docker images instead of code**.

Just as GitHub:
- Stores your code repositories
- Lets you push (upload) your code
- Lets others pull (download) your code
- Has public repos (anyone can see) and private repos (only authorised people)

A Docker registry:
- Stores your Docker images
- Lets you push (upload) your images
- Lets others pull (download) your images
- Has public images (anyone can pull) and private images (only authorised people)

### Two Types of Registries

**Public Registry:**
- Anyone can pull images without authentication
- Great for open-source software
- Examples: Docker Hub's public images, Quay.io public images

**Private Registry:**
- Requires authentication to push or pull
- For your company's proprietary images
- Examples: AWS ECR, Docker Hub private repos, self-hosted registry

### Registry vs Repository — Important Difference

These two words are often confused:

**Registry** = the whole server that stores images.
Example: `hub.docker.com` is a registry. `gallery.ecr.aws` is a registry.

**Repository** = a collection of images with the same name but different tags.
Example: `nginx` is a repository. It contains `nginx:latest`, `nginx:1.25`, `nginx:alpine`.

Think of it like this:
- Registry = a library building (contains many shelves)
- Repository = one shelf (contains different editions of the same book)
- Image = one specific edition of the book (tagged with a version)

## 3. Docker Hub — The Default Public Registry

### What is Docker Hub?

Docker Hub (`hub.docker.com`) is the default and most popular Docker registry.

When you type `docker pull nginx`, Docker automatically looks for the image on Docker Hub.
You do not need to specify any registry address — Docker Hub is the default.

### Types of Images on Docker Hub

**Official Images:**
These are images maintained by Docker Inc. or the software vendors themselves.
They are reviewed for security and best practices.
You can identify them — they have NO username prefix.

```bash
# Official images — no username prefix
docker pull nginx
docker pull postgres
docker pull node
docker pull python
docker pull ubuntu
docker pull redis
```

**Verified Publisher Images:**
Images from companies that have been verified by Docker.
They have a company name prefix.

```bash
# Verified publisher images
docker pull bitnami/postgresql
docker pull grafana/grafana
```

**Community Images:**
Images created by regular users.
Quality varies widely.
Anyone can publish these.

```bash
# Community images — username/imagename format
docker pull someuser/myapp
```

**Golden rule:** In production, only use Official images or Verified Publisher images.
Community images from unknown users can contain malware.

### Docker Hub Rate Limits

Docker Hub limits how many images you can pull without an account:

| User Type | Pull Limit |
|-----------|-----------|
| Anonymous (not logged in) | 100 pulls per 6 hours per IP |
| Free account (logged in) | 200 pulls per 6 hours |
| Pro/Team account | Unlimited |

In CI/CD pipelines, many builds run from the same IP address.
You can quickly hit the anonymous limit.
**Always log in to Docker Hub in CI/CD pipelines** using your account credentials.

## 4. Image Naming and Tagging — The Full Format

### The Complete Image Name Format

A Docker image has a full name with multiple parts:

```
registry/username/imagename:tag
│         │         │         │
│         │         │         └── version label (e.g., 1.0, latest, alpine)
│         │         └── the image name (e.g., nginx, myapp)
│         └── Docker Hub username OR organisation name
└── registry hostname (e.g., docker.io, 123456789.dkr.ecr.us-east-1.amazonaws.com)
```

### Examples With Every Part Explained

**Example 1 — Official image (short form):**
```
nginx
```
This is the SHORT form. Docker expands it to:
```
docker.io/library/nginx:latest
```
- `docker.io` = Docker Hub (the default registry)
- `library` = Docker's namespace for official images
- `nginx` = the image name
- `latest` = the default tag when none is specified

**Example 2 — Official image with tag:**
```
nginx:1.25-alpine
```
Expands to:
```
docker.io/library/nginx:1.25-alpine
```

**Example 3 — Your Docker Hub image:**
```
muskanpatel71198/myapp:2.0
```
- `docker.io` = Docker Hub (implied)
- `muskanpatel71198` = your Docker Hub username
- `myapp` = the image name
- `2.0` = the version tag

**Example 4 — AWS ECR image:**
```
123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
```
- `123456789012.dkr.ecr.us-east-1.amazonaws.com` = the ECR registry URL
  - `123456789012` = your AWS account ID
  - `dkr.ecr` = Docker ECR service
  - `us-east-1` = AWS region
  - `amazonaws.com` = AWS domain
- `myapp` = the repository name in ECR
- `1.0` = the version tag

**Example 5 — Google Container Registry:**
```
gcr.io/my-project-id/myapp:v3.1.2
```
- `gcr.io` = Google Container Registry
- `my-project-id` = your Google Cloud project ID
- `myapp` = image name
- `v3.1.2` = version tag

### How Tagging Works

A tag is just a **label** pointing to a specific image version.

One image can have MULTIPLE tags:

```bash
# Build an image
docker build -t myapp .

# Add multiple tags to the same image
docker tag myapp myapp:latest
docker tag myapp myapp:2.1.0
docker tag myapp myapp:2.1
docker tag myapp myapp:2
docker tag myapp muskanpatel71198/myapp:2.1.0
docker tag myapp 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:2.1.0

# All these tags point to the SAME underlying image (same SHA256 digest)
# Adding a tag does NOT copy the image — it just adds a new name
```

You can think of tags like nicknames.
One person can have many nicknames, but they all refer to the same person.
One image can have many tags, but they all refer to the same layer data.

## 5. Tagging Strategy — `latest` vs Versioned

### The Problem With `latest`

`latest` is the DEFAULT tag when you do not specify one.

```bash
docker pull nginx          # actually pulls nginx:latest
docker build -t myapp .    # creates myapp:latest
```

`latest` sounds good — "I always get the latest version!" — but it is actually dangerous in production.

**Why `latest` is dangerous:**

```
Monday: your CI builds myapp:latest = version 1.5
Tuesday: you deploy 3 servers, they all pull myapp:latest = 1.5 ✓

Wednesday: CI builds new myapp:latest = version 1.6 (has a bug)

Thursday: one server crashes, auto-scaling starts a new one
          new server pulls myapp:latest = 1.6 (the buggy version)

Now you have:
  Server 1: running version 1.5 (old, working)
  Server 2: running version 1.5 (old, working)
  Server 3: running version 1.6 (new, buggy!)

Your fleet is inconsistent. Some users get the buggy version.
This is called "tag mutation" — the tag changed under you.
```

### The Solution — Immutable Version Tags

**Professional tagging strategy:**

Use **Semantic Versioning** (SemVer) for your tags:

```
MAJOR.MINOR.PATCH
  │      │     │
  │      │     └── Bug fixes, no new features, no breaking changes
  │      └── New features added, backward compatible
  └── Breaking changes — incompatible with previous versions
```

```bash
# When you build a new version, tag it with the full version
docker build -t myapp:2.1.3 .
docker tag myapp:2.1.3 myapp:2.1    # also tag with minor version
docker tag myapp:2.1.3 myapp:2      # also tag with major version
docker tag myapp:2.1.3 myapp:latest  # also tag as latest

# Push all tags
docker push myapp:2.1.3
docker push myapp:2.1
docker push myapp:2
docker push myapp:latest
```

**In CI/CD, use Git commit hash for perfect traceability:**

```bash
# The Git commit hash is unique and immutable — perfect for docker tags
GIT_HASH=$(git rev-parse --short HEAD)   # e.g., abc1234
BUILD_DATE=$(date +%Y%m%d)               # e.g., 20260627

docker build -t myapp:${GIT_HASH} .
docker build -t myapp:${BUILD_DATE}-${GIT_HASH} .
```

`git rev-parse --short HEAD` = get the short (7-character) hash of the current Git commit.
This is unique per code change. If you see `abc1234` running in production, you can find the exact code.

### Tagging Best Practices Summary

```
DO use:
  myapp:2.1.3           ← specific semantic version (BEST for production)
  myapp:abc1234         ← git commit hash (perfect traceability)
  myapp:20260627-abc1234 ← date + hash (easy to see when built)

DO NOT use alone:
  myapp:latest          ← mutable, changes over time, not reproducible
  myapp                 ← same as :latest (no explicit version)
```

## 6. Push and Pull — How Images Move

### docker pull — Download an Image

`docker pull` downloads an image from a registry to your local machine.

```bash
# Pull from Docker Hub (default registry)
docker pull nginx
docker pull nginx:1.25-alpine

# Pull from AWS ECR
docker pull 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0

# Pull from a private registry
docker pull myprivateregistry.com/myapp:1.0
```

**What happens when you pull:**

```
Step 1: Docker contacts the registry
        (docker.io for Docker Hub, ECR URL for AWS ECR, etc.)

Step 2: Registry sends back the image manifest
        (a JSON file listing all layers that make up this image)

Step 3: Docker checks which layers you already have locally
        (layers are identified by SHA256 hash — if the hash matches, skip download)

Step 4: Docker downloads only the MISSING layers in parallel

Step 5: Docker assembles the layers into the local image cache

Step 6: You see: "Status: Downloaded newer image for nginx:latest"
```

**Why it downloads individual layers and not the whole image:**

This is the same layer sharing we learned in Core Concepts.
If you already have `ubuntu:22.04` locally and you pull `node:20`, Node.js is built on Ubuntu.
Docker recognises the Ubuntu layers are already present and downloads only the Node.js-specific layers.
This saves bandwidth and time.

### docker push — Upload an Image

`docker push` uploads an image from your local machine to a registry.

```bash
# Push to Docker Hub
# First login
docker login

# Then push (image must be tagged with your username)
docker tag myapp:1.0 muskanpatel71198/myapp:1.0
docker push muskanpatel71198/myapp:1.0

# Push to AWS ECR
# First authenticate with ECR
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin \
  123456789012.dkr.ecr.us-east-1.amazonaws.com

# Then push
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
```

**What happens when you push:**

```
Step 1: Docker checks if you are authenticated to the registry

Step 2: Docker sends the image manifest to the registry
        (listing which layers this image needs)

Step 3: Registry checks which layers it already has
        (if another image already pushed the ubuntu:22.04 layers, no need to upload again)

Step 4: Docker uploads only the MISSING layers

Step 5: Registry stores the layers and associates them with your image tag

Step 6: Anyone with access can now pull your image
```

### docker login and docker logout

```bash
# Login to Docker Hub
docker login
# Prompts for username and password
# Or non-interactive:
echo "mypassword" | docker login --username myusername --password-stdin

# Login to a specific registry
docker login myprivateregistry.com

# Login to AWS ECR (special command — generates a temporary token)
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin \
  123456789012.dkr.ecr.us-east-1.amazonaws.com

# Logout
docker logout
docker logout myprivateregistry.com
```

**Where does Docker store login credentials?**

On Linux, Docker stores credentials in:
```
~/.docker/config.json
```

`~` = your home directory (`/home/muskan/` in your case)
`.docker/` = Docker's configuration folder (hidden — starts with `.`)
`config.json` = the config file

```json
{
  "auths": {
    "https://index.docker.io/v1/": {
      "auth": "base64encodedusernamepassword"
    }
  }
}
```

**Security note:** In CI/CD, never hardcode credentials. Use environment variables or secret management systems. The CI tool should set `DOCKER_USERNAME` and `DOCKER_PASSWORD` as secrets.

## 7. AWS ECR — Elastic Container Registry

### What is ECR?

AWS ECR (Elastic Container Registry) is Amazon's private Docker registry service.

**Why companies use ECR instead of Docker Hub:**

| Feature | Docker Hub (Free) | AWS ECR |
|---------|------------------|---------|
| Private repos | Limited (1 free) | Unlimited |
| Pull limits | Yes (100-200/6h) | No limits |
| Storage | Limited | Pay per GB |
| Integration with AWS | None | Native (IAM, ECS, EKS) |
| Image scanning | Basic | Built-in with Snyk |
| Geo-replication | No | Yes |
| Cost | Free tier then paid | Pay per GB stored + data transfer |

### ECR Key Concepts

**Repository** = storage for one image with all its tags.
One repository holds `myapp:1.0`, `myapp:1.1`, `myapp:2.0` etc.

**Registry URL format:**
```
<aws-account-id>.dkr.ecr.<region>.amazonaws.com
```

Example for account 123456789012 in us-east-1:
```
123456789012.dkr.ecr.us-east-1.amazonaws.com
```

**Authentication:**
ECR uses AWS IAM (Identity and Access Management) for authentication.
You get a temporary 12-hour token using the AWS CLI.

### Working With ECR — Step by Step

```bash
# Step 1: Create a repository in ECR (one time)
aws ecr create-repository \
  --repository-name myapp \
  --region us-east-1
```

`aws` = the AWS CLI tool
`ecr` = the ECR subcommand
`create-repository` = create a new repository
`--repository-name myapp` = name of the repository
`--region us-east-1` = which AWS region

**Output will show:**
```json
{
  "repository": {
    "repositoryUri": "123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp",
    ...
  }
}
```

```bash
# Step 2: Authenticate Docker to ECR
aws ecr get-login-password --region us-east-1 | \
  docker login \
  --username AWS \
  --password-stdin \
  123456789012.dkr.ecr.us-east-1.amazonaws.com
```

`aws ecr get-login-password` = ask AWS for a temporary login token (valid 12 hours)
`--region us-east-1` = which region
`|` = pipe the token to the next command
`docker login` = log in to the registry
`--username AWS` = ECR always uses the username "AWS" (literally)
`--password-stdin` = read the password from stdin (the pipe)
`123456789012.dkr.ecr.us-east-1.amazonaws.com` = the registry URL to log in to

```bash
# Step 3: Tag your image with the ECR repository URL
docker tag myapp:1.0 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
```

```bash
# Step 4: Push the image
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
```

```bash
# Step 5: Pull on any machine authenticated to your AWS account
docker pull 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:1.0
```

### ECR Lifecycle Policies — Automatic Cleanup

ECR can automatically delete old images so your storage costs do not grow forever.

```json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Keep only last 10 images",
      "selection": {
        "tagStatus": "any",
        "countType": "imageCountMoreThan",
        "countNumber": 10
      },
      "action": {
        "type": "expire"
      }
    }
  ]
}
```

Apply via AWS Console or CLI:
```bash
aws ecr put-lifecycle-policy \
  --repository-name myapp \
  --lifecycle-policy-text file://lifecycle.json \
  --region us-east-1
```

## 8. Other Popular Registries

### GitHub Container Registry (ghcr.io)

Free for public repositories.
Integrated with GitHub — great if your code is already on GitHub.

```bash
# Login with GitHub personal access token
echo $GITHUB_TOKEN | docker login ghcr.io \
  --username YOUR_GITHUB_USERNAME \
  --password-stdin

```

### Google Artifact Registry (artifact.registry.google.com)

Google's registry for GCP (Google Cloud Platform) users.
Similar to ECR but for Google Cloud.

### Azure Container Registry (ACR)

Microsoft's registry for Azure users.

### Quay.io

Red Hat's public registry.
Popular in the open-source and enterprise Linux community.

### Self-Hosted Registry

Docker provides an official `registry` image you can run yourself:

```bash
# Run a private registry on your own server
docker run -d \
  --name my-registry \
  -p 5000:5000 \
  -v registry-data:/var/lib/registry \
  registry:2
```

```bash

docker tag myapp:1.0 localhost:5000/myapp:1.0
docker push localhost:5000/myapp:1.0

# Pull from your private registry
docker pull localhost:5000/myapp:1.0
```

## 9. Image Scanning — Trivy and Snyk

### Why Scan Docker Images?

A Docker image contains:
- A base OS (Ubuntu, Alpine, Debian)
- Installed packages (nginx, node, python)
- Your application code
- Libraries your application uses

Any of these components might have **known security vulnerabilities**.

A **CVE** (Common Vulnerabilities and Exposures) is a published security vulnerability with an ID like `CVE-2021-44228` (the famous Log4Shell vulnerability).

Without scanning, you could deploy images containing:
- Packages with critical vulnerabilities that let attackers take control
- Libraries with known data leak vulnerabilities
- OS components with privilege escalation bugs

**Image scanning checks your image against a database of known CVEs** and tells you what needs updating.

### Trivy — Free Open Source Scanner

Trivy is the most popular free, open-source image scanner.
It is maintained by Aqua Security.
It can scan Docker images, filesystems, Git repositories, and Kubernetes clusters.

**Running Trivy:**

```bash
# Scan an image (Docker image method — no installation needed)
docker run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v trivy-db:/root/.cache/ \
  aquasec/trivy image nginx:latest

# Or install trivy on your machine
sudo apt-get install -y trivy
trivy image nginx:latest
trivy image node:20-alpine
trivy image myapp:1.0
```

**Trivy output shows:**

```
nginx:latest (debian 11.7)
==========================
Total: 147 (UNKNOWN: 0, LOW: 78, MEDIUM: 48, HIGH: 18, CRITICAL: 3)

┌─────────────────────┬────────────────┬──────────┬─────────────────────┬───────────────────────────────────────────────┐
│       Library       │  Vulnerability │ Severity │   Installed Version │ Fixed Version                                 │
├─────────────────────┼────────────────┼──────────┼─────────────────────┼───────────────────────────────────────────────┤
│ libssl1.1           │ CVE-2023-5678  │ HIGH     │ 1.1.1n-0+deb11u5   │ 1.1.1n-0+deb11u6                              │
│ libexpat1           │ CVE-2023-52425 │ CRITICAL │ 2.2.10-2+deb11u5   │ 2.2.10-2+deb11u6                              │
└─────────────────────┴────────────────┴──────────┴─────────────────────┴───────────────────────────────────────────────┘
```

**Severity levels:**

| Severity | Meaning | What to Do |
|----------|---------|-----------|
| CRITICAL | Can be exploited immediately, severe damage | Fix immediately, block deployment |
| HIGH | Serious vulnerability, likely exploitable | Fix soon, consider blocking |
| MEDIUM | Moderate risk, may not be directly exploitable | Fix in next release |
| LOW | Minimal risk | Fix when convenient |
| UNKNOWN | Not enough information | Investigate |

**Useful Trivy flags:**

```bash
# Only show HIGH and CRITICAL (ignore low noise)
trivy image --severity HIGH,CRITICAL nginx:latest

# Fail the command (non-zero exit) if CRITICAL found — useful in CI
trivy image --exit-code 1 --severity CRITICAL nginx:latest

# Output as JSON for processing
trivy image --format json nginx:latest > scan-results.json

# Scan and ignore specific CVEs (if you know they are false positives)
trivy image --ignore-unfixed nginx:latest  # only show vulnerabilities with fixes available
```

### Snyk — Commercial Scanner With Free Tier

Snyk is a commercial security platform with a generous free tier.
It integrates with GitHub, GitLab, Jenkins, and other CI/CD tools.

```bash
# Install Snyk CLI
npm install -g snyk

# Login to Snyk
snyk auth

# Scan a Docker image
snyk container test nginx:latest

# Monitor an image (stores results in Snyk dashboard)
snyk container monitor nginx:latest
```

Snyk gives you:
- Vulnerability scanning
- Fix recommendations (which version to upgrade to)
- License compliance checking
- Container configuration checks

### Image Scanning in CI/CD Pipeline

The standard practice is to scan images BEFORE pushing to the registry:

```bash
# CI/CD pipeline steps for Docker

# Step 1: Build the image
docker build -t myapp:${GIT_HASH} .

# Step 2: Scan for vulnerabilities BEFORE pushing
trivy image --exit-code 1 --severity CRITICAL myapp:${GIT_HASH}
# If this finds CRITICAL vulnerabilities, exit code 1, pipeline fails
# Do not push a vulnerable image

# Step 3: If scan passed, push to registry
docker push myapp:${GIT_HASH}

# Step 4: Deploy
kubectl set image deployment/myapp myapp=myapp:${GIT_HASH}
```

This is called **"shifting security left"** — catching vulnerabilities early in the development process rather than in production.

## 10. Running a Private Registry

### Why Run Your Own Registry?

Sometimes you need a registry that:
- Is inside your private network (no internet access required)
- You fully control
- Has no rate limits
- Costs nothing in cloud fees

Common use cases:
- Air-gapped environments (no internet)
- Development lab networks
- Cost optimisation for very high pull rates

### Running the Official Docker Registry Image

```bash
# Basic private registry
docker run -d \
  --name private-registry \
  --restart unless-stopped \
  -p 5000:5000 \
  -v registry-data:/var/lib/registry \
  registry:2
```

`registry:2` = the official Docker registry image version 2
`-p 5000:5000` = expose the registry on port 5000
`-v registry-data:/var/lib/registry` = persist the stored images in a named volume

```bash
# Configure Docker to allow this insecure (HTTP) registry
# By default Docker only allows HTTPS registries
sudo nano /etc/docker/daemon.json

# Add:
{
  "insecure-registries": ["localhost:5000"]
}

sudo systemctl restart docker
```

`insecure-registries` = allow HTTP (not HTTPS) connections to these registry addresses.
Only use this for localhost or internal network registries. Never for public internet registries.

```bash
# Push to your private registry
docker tag myapp:1.0 localhost:5000/myapp:1.0
docker push localhost:5000/myapp:1.0

# Pull from your private registry
docker pull localhost:5000/myapp:1.0
```

mkdir -p /home/$USER/docker-labs/registry-lab

`LABEL` = metadata instruction in a Dockerfile. Adds key-value labels to the image.

### Lab 2 — Explore Image Tags and Layers

```bash
# Pull multiple versions of the same image
docker pull nginx:latest
docker pull nginx:1.25-alpine
docker pull nginx:1.24-alpine

# List all nginx images
docker images nginx
```

**Expected output:**
```
REPOSITORY   TAG           IMAGE ID       CREATED        SIZE
nginx        latest        abc123def456   2 weeks ago    187MB
nginx        1.25-alpine   xyz789ghi012   3 weeks ago    41.1MB
nginx        1.24-alpine   mnop345qrst6   3 months ago   40.7MB
```

Notice the SIZE difference:
- `nginx:latest` = Debian-based = 187MB
- `nginx:1.25-alpine` = Alpine-based = 41MB

Alpine-based images are much smaller because Alpine Linux itself is only 5MB.

```bash
# Inspect an image's full details
docker inspect nginx:1.25-alpine

# See just the labels
docker inspect nginx:1.25-alpine | jq '.[0].Config.Labels'

# See the architecture
docker inspect nginx:1.25-alpine | jq '.[0].Architecture'
# Output: "amd64"

# See which OS it is built for
docker inspect nginx:1.25-alpine | jq '.[0].Os'
# Output: "linux"
```

```bash
# See the image digest (immutable SHA256 hash)
docker inspect nginx:1.25-alpine | jq '.[0].RepoDigests'
# Output: ["nginx@sha256:abc123...64chars..."]

# Pull by digest (guaranteed to get exact same image, even if tag is moved)
docker pull nginx@sha256:abc123def456...
```

`RepoDigests` = the SHA256 hash of the image manifest. This never changes. The tag can be moved to point to a different image, but the digest is permanent.

### Lab 3 — Tagging Strategy Practice

```bash
cd /home/$USER/docker-labs/registry-lab

# Simulate building v1.0 of your app
docker build -t myapp .

# Apply a proper versioned tagging strategy
VERSION="1.0.0"
MAJOR="1"
MINOR="1.0"
GIT_HASH="abc1234"  # in real CI this would be: $(git rev-parse --short HEAD)

docker tag myapp muskanpatel71198/myapp:${VERSION}
docker tag myapp muskanpatel71198/myapp:${MINOR}
docker tag myapp muskanpatel71198/myapp:${MAJOR}
docker tag myapp muskanpatel71198/myapp:latest
docker tag myapp muskanpatel71198/myapp:${GIT_HASH}

# See all tags for this image
docker images muskanpatel71198/myapp
```

**Expected output:**
```
REPOSITORY                   TAG       IMAGE ID       CREATED        SIZE
muskanpatel71198/myapp       1.0.0     abc123def456   1 minute ago   7.05MB
muskanpatel71198/myapp       1.0       abc123def456   1 minute ago   7.05MB

muskanpatel71198/myapp       latest    abc123def456   1 minute ago   7.05MB
muskanpatel71198/myapp       abc1234   abc123def456   1 minute ago   7.05MB
```

**Notice:** All tags show the SAME `IMAGE ID` (`abc123def456`).
Tags are just labels pointing to the same image data.
No extra disk space is used for each additional tag.

```bash

```

`--all-tags` = push all tags for this image name, not just one.

### Lab 5 — Run a Private Registry on Your Machine

```bash
# Step 1: Start a local private registry
docker run -d \
  --name local-registry \
  --restart unless-stopped \
  -p 5000:5000 \
  -v registry-data:/var/lib/registry \
  registry:2

# Verify it is running
curl http://localhost:5000/v2/
```

`curl http://localhost:5000/v2/` = the `/v2/` endpoint is the Docker Registry API health check.
Expected output: `{}` (empty JSON) = registry is running.

```bash
# Step 2: Allow Docker to use this insecure (HTTP) registry
sudo nano /etc/docker/daemon.json
```

Add this content:
```json
{
  "insecure-registries": ["localhost:5000"]
}
```

```bash
# Restart Docker to apply
sudo systemctl restart docker

# Verify the setting
docker info | grep -A2 "Insecure Registries"
```

```bash
# Step 3: Push an image to your private registry
docker tag my-first-push:1.0 localhost:5000/my-first-push:1.0
docker push localhost:5000/my-first-push:1.0
```

```bash
# Step 4: List images in your registry using the API
curl http://localhost:5000/v2/_catalog
```

`/v2/_catalog` = Docker Registry API endpoint that lists all repositories.
Expected output: `{"repositories":["my-first-push"]}`

```bash
# List tags for a specific image
curl http://localhost:5000/v2/my-first-push/tags/list
```

Expected output: `{"name":"my-first-push","tags":["1.0"]}`

```bash
# Step 5: Pull from your private registry
docker rmi localhost:5000/my-first-push:1.0  # remove local copy
docker pull localhost:5000/my-first-push:1.0  # pull from your registry
docker run --rm localhost:5000/my-first-push:1.0  # run it
```

Works! You have your own private registry.

```bash
# Cleanup
docker rm -f local-registry
docker volume rm registry-data
```

### Lab 6 — Inspect the Docker Hub Credentials File

```bash
# See where Docker stores your login credentials
cat ~/.docker/config.json
```

`~` = home directory (shortcut for `/home/muskan/`)
`.docker` = hidden folder (starts with `.`) — Docker's config folder
`config.json` = the credentials file

**Expected output (partial):**
```json
{
  "auths": {
    "https://index.docker.io/v1/": {
      "auth": "bXVza2FucGF0ZWw3MTE5ODp..."
    }
  },
  "HttpHeaders": {
    "User-Agent": "Docker-Client/29.1.3 (linux)"
  }
}
```

`"auth"` = base64-encoded string of `username:password`

```bash
# Decode to see what it contains (shows your credentials in plain text!)
cat ~/.docker/config.json | jq -r '.auths["https://index.docker.io/v1/"].auth' | base64 --decode
```

**This shows why you should never commit this file to Git and why proper secret managers are important.**

# Logout to clear credentials

# The auths entry is removed

## 12. Quick Revision Cheatsheet

| Concept | Summary |
|---------|---------|
| Registry | Server that stores and distributes Docker images |
| Repository | Collection of images with same name, different tags |
| Docker Hub | Default public registry at docker.io |
| Official images | No username prefix — maintained by Docker or vendors |
| Community images | `username/imagename` format — quality varies |
| `latest` tag | Default tag — mutable, dangerous in production |
| Semantic versioning | `MAJOR.MINOR.PATCH` — use this for production tags |
| ECR | AWS's private container registry |
| CVE | Common Vulnerabilities and Exposures — security vulnerability ID |
| Trivy | Free open-source image vulnerability scanner |
| Snyk | Commercial image scanner with free tier |
| Shift left | Scan for vulnerabilities early in CI/CD, not in production |

| Command | What It Does |
|---------|-------------|
| `docker login` | Authenticate to Docker Hub |
| `docker login registry.url` | Authenticate to a specific registry |
| `docker logout` | Remove stored credentials |
| `docker pull image:tag` | Download image from registry |
| `docker push image:tag` | Upload image to registry |
| `docker tag source:tag target:tag` | Add a new tag/name to an image |
| `docker images` | List all local images |
| `docker rmi image:tag` | Remove a local image |
| `docker push image --all-tags` | Push all tags for an image |
| `docker inspect image` | See full image metadata |
| `trivy image image:tag` | Scan image for vulnerabilities |
| `trivy image --severity HIGH,CRITICAL image:tag` | Only show high/critical |
| `trivy image --exit-code 1 --severity CRITICAL image:tag` | Fail if critical found |

| ECR Command | What It Does |
|-------------|-------------|
| `aws ecr create-repository --repository-name name` | Create ECR repo |
| `aws ecr get-login-password \| docker login --username AWS --password-stdin URL` | Authenticate to ECR |
| `aws ecr describe-repositories` | List ECR repositories |
| `aws ecr list-images --repository-name name` | List images in a repo |
| `aws ecr delete-image --repository-name name --image-ids imageTag=1.0` | Delete an image |

| Registry URL Format | Registry |
|--------------------|---------|
| `docker.io/library/nginx` | Docker Hub official |
| `docker.io/username/imagename` | Docker Hub community |
| `123456789012.dkr.ecr.us-east-1.amazonaws.com/name` | AWS ECR |
| `ghcr.io/username/imagename` | GitHub Container Registry |
| `gcr.io/project-id/imagename` | Google Container Registry |
| `localhost:5000/imagename` | Local private registry |
