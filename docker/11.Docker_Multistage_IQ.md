### Q1. What is a multi-stage build in Docker? Why do we use it?

**How the interviewer asks it:**
> "Explain what a multi-stage build is and what problem it solves."

**Your Answer:**

> "A multi-stage build is a Dockerfile that uses multiple `FROM` instructions. Each `FROM` starts a new, completely isolated build stage. You can copy files from one stage into another using `COPY --from=stagename`.
>
> The problem it solves is image bloat. When you build an application, you need build tools — TypeScript compiler, webpack, test frameworks, Maven, Go compiler. These tools are needed to BUILD the code but are completely useless at runtime. Without multi-stage builds, all these tools end up in your production image.
>
> For example, a Node.js TypeScript application in a single-stage build might be 1.2GB because it contains the TypeScript compiler, all dev dependencies like Jest, webpack source maps, and test files. But at runtime, you only need the compiled JavaScript and production dependencies — maybe 120MB.
>
> Multi-stage builds let you use a full toolchain in stage 1 to build, then copy only the compiled artifact to a minimal stage 2. The build tools never make it into the final image. That 1.2GB becomes 120MB — 90% reduction.
>
> Benefits: faster deployment (smaller image pulls faster), lower storage cost, smaller attack surface for security scanning, and faster auto-scaling since new pods do not wait as long for large image pulls."

### Q2. How do you copy files between stages?

**How the interviewer asks it:**
> "How does the final stage get the compiled code from the builder stage?"

**Your Answer:**

> "You use the `COPY` instruction with the `--from` flag.
>
> ```dockerfile
> FROM node:20-alpine AS builder
> WORKDIR /app
> RUN npm run build   # produces /app/dist/
>
> FROM node:20-alpine AS production
> COPY --from=builder /app/dist ./dist
> ```
>
> The `--from=builder` flag tells Docker: do not copy from the local machine (build context). Copy from the stage named `builder`.
>
> You specify: the source path inside the builder stage (`/app/dist`) and the destination in the current stage (`./dist`).
>
> You can also copy from multiple stages in a single final stage:
> ```dockerfile
> COPY --from=frontend-builder /app/build /var/www/html
> COPY --from=backend-builder /app/api /usr/local/bin/api
> ```
>
> And you can even copy from any public Docker image, not just stages you defined:
> ```dockerfile
> COPY --from=alpine:3.19 /bin/busybox /bin/busybox
> ```
>
> This is powerful because you can pull specific binaries from well-maintained official images without installing a full package manager."

### Q3. What is the `AS` keyword in a multi-stage build?

**How the interviewer asks it:**
> "What does `FROM golang:1.22-alpine AS builder` mean?"

**Your Answer:**

> "`AS builder` gives the stage a human-readable name. Without it, Docker numbers stages starting from 0, and you would have to write `COPY --from=0 /app/server /server` which is unreadable.
>
> With naming, you write `COPY --from=builder /app/server /server` which is clear and self-documenting.
>
> Names are also used with the `--target` flag when building:
> ```bash
> docker build --target builder -t myapp:builder .
> ```
>
> This builds only up to the stage named `builder` and stops there. The final production stage is not executed.
>
> This is very useful in CI pipelines. You can have stages named `test`, `lint`, `builder`, and `production`. In CI:
> ```bash
> docker build --target test -t myapp:test .    # run tests
> docker build --target lint -t myapp:lint .    # run linter
> docker build -t myapp:prod .                  # build full image if tests passed
> ```
>
> The tests run in a full environment with all dev tools. The final image only contains what is needed for production."

### Q4. What is `FROM scratch` and when do you use it?

**How the interviewer asks it:**
> "I've seen Dockerfiles with `FROM scratch`. What is that?"

**Your Answer:**

> "`scratch` is a special Docker keyword for an empty base image. It is literally nothing — zero bytes. No OS, no shell, no tools, no libraries. Just emptiness.
>
> You can only use `scratch` as a base when your application is a statically compiled binary that needs no external libraries. Go is the most common language for this because Go compiles to a single self-contained binary with `CGO_ENABLED=0 GOOS=linux go build`.
>
> ```dockerfile
> FROM golang:1.22-alpine AS builder
> WORKDIR /app
> COPY . .
> RUN CGO_ENABLED=0 GOOS=linux go build -o server .
>
> FROM scratch
> COPY --from=builder /app/server /server
> COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
> ENTRYPOINT ['/server']
> ```
>
> The result is a 8-12MB image containing only the Go binary and TLS certificates. The golang build image that compiled it was 350MB — all of that is gone.
>
> The trade-off: no shell, no debugging tools. You cannot `docker exec` into the container for debugging. But in production that is often acceptable — you use logs and metrics instead of shell access.
>
> Alternatives to scratch with slightly more convenience: Google's distroless images add CA certificates and timezone data but still no shell or package manager."

### Q5. What is the difference between `node:20` and `node:20-alpine` for a final stage?

**How the interviewer asks it:**
> "Should I use `node:20` or `node:20-alpine` as my base image?"

**Your Answer:**

> "`node:20` is built on Debian. It is a full Linux distribution with many packages and tools pre-installed. Comfortable to use, broad compatibility, but large — around 1.1GB.
>
> `node:20-alpine` is built on Alpine Linux — a minimal Linux distribution designed specifically for containers. The Alpine base is only 5MB. The full node:20-alpine image is around 55MB — about 95% smaller than node:20.
>
> For production images, I always use `node:20-alpine`. The size difference is dramatic. Smaller means faster deploys, lower storage costs, and fewer packages means fewer potential CVEs.
>
> The one caveat: Alpine uses musl libc instead of glibc (GNU C Library). Most Node.js packages work fine with musl, but some native addons compiled against glibc may not work on Alpine. If you hit this issue, use `node:20-slim` (Debian slim) as a compromise — smaller than full Debian, uses glibc.
>
> My decision process:
> - Alpine first — try it, if native addons fail, switch to slim
> - For Go binaries — use `scratch`
> - For Java — use `eclipse-temurin:17-jre-alpine` (JRE, not JDK)
> - For maximum security — use Google distroless images (no shell at all)"

### Q6. Walk me through a complete multi-stage Dockerfile for a Node.js TypeScript application.

**How the interviewer asks it:**
> "How would you Dockerize a TypeScript Node.js application using best practices?"

**Your Answer:**

> "Here is my standard template with everything explained:
>
> ```dockerfile
> # Stage 1: Install ALL dependencies (including dev)
> FROM node:20-alpine AS deps
> WORKDIR /app
> COPY package*.json ./
> RUN npm ci
>
> # Stage 2: Build (compile TypeScript)
> FROM deps AS builder
> COPY tsconfig.json ./
> COPY src/ ./src/
> RUN npm run build          # outputs to /app/dist/
>
> # Stage 3: Production (minimal, secure)
> FROM node:20-alpine AS production
>
> # Security: non-root user
> RUN addgroup -S -g 1001 appgroup && \
>     adduser -S -u 1001 -G appgroup appuser
>
> WORKDIR /app
>
> # Install ONLY production dependencies
> COPY package*.json ./
> RUN npm ci --only=production && npm cache clean --force
>
> # Copy ONLY compiled output from builder
> COPY --from=builder /app/dist ./dist
>
> RUN chown -R appuser:appgroup /app
> USER appuser
>
> EXPOSE 3000
>
> HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
>   CMD wget -qO- http://localhost:3000/health || exit 1
>
> CMD ['node', 'dist/index.js']
> ```
>
> Why three stages instead of two?
>
> The `deps` stage installs all node_modules. The `builder` stage inherits from `deps` — so it does not re-run `npm ci`, saving time. The `production` stage starts fresh and only installs production deps. This structure maximises layer cache reuse.
>
> What gets cut: TypeScript compiler, jest, eslint, webpack, source .ts files, test files, and roughly 70% of node_modules. Result: 1.2GB → 120MB."

### Q7. How do multi-stage builds improve security?

**How the interviewer asks it:**
> "Beyond size reduction, are there security benefits to multi-stage builds?"

**Your Answer:**

> "Yes — several important ones.
>
> First, reduced attack surface. Every package and binary in an image is a potential vulnerability. A production image without a compiler, package manager, or shell has far fewer things that can be exploited. If an attacker gains code execution inside the container, they have much less to work with.
>
> Second, no shell in scratch or distroless images. If you use `FROM scratch` or a distroless image, there is no `sh` or `bash`. An attacker who exploits the application cannot get an interactive shell — there is none. They can only work through your application process, which is very limited.
>
> Third, no package manager. Without `apt` or `apk`, an attacker cannot install additional tools. They cannot download netcat, nmap, or any other post-exploitation tools.
>
> Fourth, fewer CVEs to scan. A 8MB Go binary image might have 0 CVEs. A 1.2GB full node image might have 200+. Fewer packages means fewer vulnerabilities means less to patch.
>
> Fifth, the build environment secrets stay in the build environment. If you use `RUN --mount=type=secret,id=npm_token npm install` in the builder stage, that npm token is never in any layer of the production image.
>
> In practice, the combination of multi-stage (remove build tools) + non-root user + read-only filesystem + image scanning is the standard security posture for containerised applications in regulated industries."

### Q8. How do you optimise layer caching in a multi-stage build?

**How the interviewer asks it:**
> "My multi-stage builds are still slow in CI. How do you optimise caching?"

**Your Answer:**

> "Layer caching in multi-stage builds follows the same rule as single-stage: Docker caches each layer and reuses it if nothing above it has changed. If a layer changes, all subsequent layers rebuild.
>
> The key principle: put things that change rarely at the top, things that change frequently at the bottom.
>
> For Node.js, the pattern:
> ```dockerfile
> FROM node:20-alpine AS deps
> WORKDIR /app
> # Copy package files FIRST — these only change when adding/removing packages
> COPY package*.json ./
> # npm ci cached unless package*.json changed
> RUN npm ci
>
> FROM deps AS builder
> # Copy source AFTER install — changes every commit but does not bust install cache
> COPY . .
> RUN npm run build
> ```
>
> This way, on most commits: source code changes, so `COPY . .` layer is rebuilt. But `npm ci` uses the cache because `package.json` did not change. This saves 2-3 minutes per build in CI.
>
> For even faster CI, use BuildKit cache mounts:
> ```dockerfile
> RUN --mount=type=cache,target=/root/.npm \
>     npm ci
> ```
> The npm package cache persists between builds. Even if package.json changes, npm redownloads only the new packages, not everything.
>
> For Go:
> ```dockerfile
> COPY go.mod go.sum ./
> RUN go mod download   # cached unless go.mod changes
> COPY . .
> RUN go build .        # rebuilds on any source change
> ```
>
> For Maven/Java:
> ```dockerfile
> COPY pom.xml .
> RUN mvn dependency:resolve -q   # cached unless pom.xml changes
> COPY src ./src
> RUN mvn package -DskipTests     # rebuilds when source changes
> ```"

### Q9. What is a distroless image and when should you use it over Alpine?

**How the interviewer asks it:**
> "I keep seeing distroless images mentioned. What are they and are they better than Alpine?"

**Your Answer:**

> "Distroless images are container images that contain only the language runtime and application, with no operating system distribution extras — no shell, no package manager, no coreutils. They are maintained by Google and available at `gcr.io/distroless/`.
>
> Distroless images include:
> - The language runtime (Node.js, Python, Java, .NET)
> - Standard library
> - CA certificates
> - Timezone data
>
> They do NOT include:
> - Shell (no sh, no bash)
> - Package manager (no apt, no apk)
> - Any system utilities (no ls, no cat, no wget)
>
> Alpine vs distroless trade-offs:
>
> Alpine: smaller (5MB base), has a shell so `docker exec ... sh` works for debugging, uses musl libc (occasionally incompatible with some native extensions)
>
> Distroless: no shell (higher security — attackers cannot get interactive access), based on Debian (glibc — better compatibility), slightly larger but still much smaller than full Debian, often preferred for production in security-conscious environments.
>
> Usage:
> ```dockerfile
> FROM golang:1.22-alpine AS builder
> RUN CGO_ENABLED=0 go build -o app .
>
> # Distroless static — for static binaries, has only CA certs
> FROM gcr.io/distroless/static-debian12
> COPY --from=builder /app /app
> ENTRYPOINT ['/app']
> ```
>
> My rule: use Alpine for development (shell helps debugging), distroless for production security-critical services. For Go static binaries where I want absolute minimum, scratch is the best option."

### Q10. How do you use multi-stage builds in a CI/CD pipeline?

**How the interviewer asks it:**
> "Walk me through how multi-stage builds fit into your CI/CD pipeline."

**Your Answer:**

> "Multi-stage builds integrate very naturally with CI/CD because you can target specific stages for different pipeline steps.
>
> Here is a typical pipeline using GitHub Actions:
>
> **Dockerfile with named stages:**
> ```dockerfile
> FROM node:20-alpine AS deps
> RUN npm ci
>
> FROM deps AS test
> COPY . .
> RUN npm test          # run tests
>
> FROM deps AS builder
> COPY . .
> RUN npm run build
>
> FROM node:20-alpine AS production
> # ... minimal setup ...
> COPY --from=builder /app/dist ./dist
> CMD ['node', 'dist/index.js']
> ```
>
> **Pipeline steps:**
> ```bash
> # Step 1: Build and run tests (cheap — uses full deps but no production build)
> docker build --target test -t myapp:test .
> docker run --rm myapp:test   # exit code 0 = tests passed
>
> # Step 2: Scan for vulnerabilities
> trivy image --exit-code 1 --severity CRITICAL myapp:test
>
> # Step 3: Build production image
> GIT_HASH=$(git rev-parse --short HEAD)
> docker build --target production -t myapp:${GIT_HASH} .
>
> # Step 4: Scan production image
> trivy image --exit-code 1 --severity CRITICAL myapp:${GIT_HASH}
>
> # Step 5: Push to registry
> docker push myapp:${GIT_HASH}
>
> # Step 6: Deploy
> kubectl set image deployment/myapp myapp=myapp:${GIT_HASH}
> ```
>
> The key insight: the test stage catches failures early with a fast build (no production minification). Only if tests pass do we build the (potentially slower) production image. This keeps the pipeline fast.
>
> For layer cache in CI, I push the build cache to the registry:
> ```bash
> docker buildx build \
>   --cache-from=type=registry,ref=myrepo/myapp:cache \
>   --cache-to=type=registry,ref=myrepo/myapp:cache,mode=max \
>   --target production \
>   -t myapp:${GIT_HASH} .
> ```
> This saves the build cache in the registry so each CI run reuses it even on fresh runners."

### Q11. How would you debug an issue that only appears in the production multi-stage image but not in development?

**How the interviewer asks it:**
> "My app works in dev but fails in the production multi-stage image. How do you debug?"

**Your Answer:**

> "This is a classic multi-stage problem. The production image is minimal — it is missing something that existed in the dev environment. Here is my systematic approach:
>
> **Step 1 — Build and examine the builder stage:**
> ```bash
> docker build --target builder -t debug:builder .
> docker run -it --rm debug:builder sh
> # Inside: check what files are there, run the app manually
> ```
>
> **Step 2 — Check what got copied:**
> ```bash
> docker run --rm debug:builder ls -la /app/dist/
> # Verify all expected files are present in the builder output
> ```
>
> **Step 3 — Try to run the production image with debugging:**
> ```bash
> # If using Alpine (has sh):
> docker run -it --entrypoint sh myapp:prod
> # Inside: ls /app, check files, try node dist/index.js manually
>
> # If using scratch/distroless (no shell):
> # Cannot exec in — must check at build time
> docker run --rm myapp:prod ls /app  # works if entrypoint allows it
> ```
>
> **Step 4 — Common root causes:**
>
> Missing files: `COPY --from=builder /app/dist ./dist` — did you copy ALL needed files? Source maps? Config files?
>
> Missing production dependencies: forgot `npm install --only=production` or ran it incorrectly
>
> Architecture mismatch: native modules compiled for the wrong platform (common when building on Apple M1 for Linux amd64)
>
> Environment variables: dev has values in .env file, production needs them injected
>
> File permissions: files owned by root in builder, app tries to write to them as non-root user
>
> ```bash
> # Check file ownership
> docker run --rm myapp:prod ls -la /app/
> # If owned by root and app runs as non-root → permission error
> ```
>
> **Step 5 — If distroless and cannot shell in:**
> Add a temporary debug stage that is NOT distroless:
> ```dockerfile
> FROM gcr.io/distroless/nodejs20-debian12 AS production
> COPY --from=builder /app/dist ./dist
>
> # Debug stage — only built with --target debug
> FROM node:20-alpine AS debug
> COPY --from=production / /
> # This copies everything from production and adds a shell
> ```
> ```bash
> docker build --target debug -t myapp:debug .
> docker run -it myapp:debug sh
> ```"

### Q12. Explain how you would dockerize a microservices application where services share code.

**How the interviewer asks it:**
> "We have 5 Node.js microservices that share a common utilities library. How do you handle this with Docker?"

**Your Answer:**

> "This is a real architectural challenge. There are two main approaches.
>
> **Approach 1 — Monorepo with shared build stage:**
>
> If the services live in a monorepo, use a shared base stage:
> ```dockerfile
> FROM node:20-alpine AS monorepo-base
> WORKDIR /app
> # Install all dependencies for all packages
> COPY package*.json ./
> COPY packages/shared/package*.json ./packages/shared/
> COPY services/auth/package*.json ./services/auth/
> RUN npm ci
>
> FROM monorepo-base AS shared-builder
> COPY packages/shared/ ./packages/shared/
> RUN npm run build -w packages/shared    # build shared library first
>
> FROM shared-builder AS auth-builder
> COPY services/auth/ ./services/auth/
> RUN npm run build -w services/auth      # build auth service (depends on shared)
>
> FROM node:20-alpine AS auth-production
> WORKDIR /app
> COPY --from=auth-builder /app/services/auth/dist ./dist
> COPY --from=shared-builder /app/packages/shared/dist ./node_modules/shared/dist
> # ... etc
> CMD ['node', 'dist/index.js']
> ```
>
> **Approach 2 — Publish shared library to private registry:**
>
> Publish the shared utilities as a private npm package to npm private registry or GitHub Packages. Each service installs it as a dependency.
>
> In the Dockerfile, use BuildKit secret mount to provide the npm token without baking it into the image:
> ```dockerfile
> # syntax=docker/dockerfile:1
>
> FROM node:20-alpine AS deps
> WORKDIR /app
> COPY package*.json ./
> RUN --mount=type=secret,id=npm_token \
>     NPM_TOKEN=$(cat /run/secrets/npm_token) \
>     npm ci   # fetches private shared package using token
>
> FROM deps AS builder
> COPY . .
> RUN npm run build
>
> FROM node:20-alpine AS production
> WORKDIR /app
> COPY package*.json ./
> RUN --mount=type=secret,id=npm_token \
>     NPM_TOKEN=$(cat /run/secrets/npm_token) \
>     npm ci --only=production
> COPY --from=builder /app/dist ./dist
> CMD ['node', 'dist/index.js']
> ```
>
> Build with: `docker build --secret id=npm_token,src=$HOME/.npmrc .`
>
> This approach has cleaner separation of concerns and is easier to manage as the number of services grows."

### Q13. "My Docker image is 3GB. Walk me through how you would reduce it."

**Your Answer:**

> "3GB is a classic sign that build tools and dev dependencies ended up in the production image. Here is my systematic approach:
>
> **Step 1 — Diagnose what is large:**
> ```bash
> docker history myimage:latest
> # Find the layers taking the most space
>
> docker run --rm wagoodman/dive myimage:latest
> # Dive shows exactly which files are in each layer
> ```
>
> **Step 2 — Identify the main offender:**
> Usually it is one of these:
> - `node_modules` with devDependencies (TypeScript, Jest, Webpack = hundreds of MB)
> - Build tools installed via apt/apk (gcc, g++, maven, go compiler)
> - Source files that are not needed at runtime
>
> **Step 3 — Implement multi-stage build:**
> ```dockerfile
> # Stage 1: Build with all tools
> FROM node:20 AS builder
> COPY package*.json ./
> RUN npm ci               # install everything including devDeps
> COPY . .
> RUN npm run build        # compile TypeScript → dist/
>
> # Stage 2: Production — start fresh
> FROM node:20-alpine AS production  # Alpine not Debian
> WORKDIR /app
> COPY package*.json ./
> RUN npm ci --only=production       # no devDependencies
> COPY --from=builder /app/dist ./dist  # only compiled output
> CMD ['node', 'dist/index.js']
> ```
>
> **Step 4 — Choose the smallest viable base:**
> - Switch from `node:20` (Debian, 1.1GB) to `node:20-alpine` (Alpine, 55MB)
> - For Go, use `scratch`
> - For Java, use JRE not JDK
>
> **Step 5 — Clean up in-layer:**
> ```dockerfile
> RUN apt-get update && apt-get install -y build-essential \
>     && do-the-thing \
>     && apt-get remove --purge -y build-essential \
>     && apt-get autoremove -y \
>     && rm -rf /var/lib/apt/lists/*
> ```
> All in ONE RUN so the packages are not committed to any layer.
>
> **Step 6 — Add .dockerignore:**
> Ensure test files, docs, and local node_modules are excluded.
>
> **Typical result:** Node.js app 3GB → 120MB. Go app 3GB → 10MB."

### Q14. "The build works locally but fails in CI. The error says 'No such file' in the COPY --from step."

**Your Answer:**

> "This is a common multi-stage issue. The error means the file you are trying to copy from a stage does not exist in that stage. A few likely causes:
>
> **Cause 1 — Build command failed silently:**
> The build step in the builder stage failed but the Dockerfile continued because the exit code was somehow ignored.
> ```bash
> # Add -q flag removal or explicit error checking
> docker build --target builder -t debug:builder .
> docker run --rm debug:builder ls /app/dist/
> # If empty or error — your build command failed
> ```
>
> **Cause 2 — Wrong path:**
> The file exists but at a different path. Alpine and Debian have different default paths for some things.
> ```bash
> docker run --rm debug:builder find /app -name '*.jar' 2>/dev/null
> # Find where the artifact actually is
> ```
>
> **Cause 3 — Different user context:**
> Locally you might run with root and have write permissions. CI might run as a different user.
> ```bash
> # In Dockerfile, verify file was created:
> RUN npm run build && ls -la /app/dist/  # will fail if dist/ not created
> ```
>
> **Cause 4 — BuildKit caching an old failed state in CI:**
> ```bash
> # Force a clean build in CI
> docker build --no-cache -t myapp:${GIT_HASH} .
> ```
>
> **Cause 5 — Different Docker version between local and CI:**
> Some Dockerfile syntax requires specific Docker/BuildKit versions. Add version pin:
> ```dockerfile
> # syntax=docker/dockerfile:1.6
> ```
>
> **My debugging process:**
> ```bash
> # Target only the builder stage
> docker build --target builder -t debug .
>
> # Check what is actually there
> docker run --rm debug find / -name '*.js' -path '*/dist/*' 2>/dev/null
>
> # Then fix the path in COPY --from based on what you find
> ```"

## Phrases That Show Senior-Level Thinking

- *"I reduced our Node.js image from 1.2GB to 120MB using multi-stage builds. This cut deploy time from 3 minutes to 20 seconds per pod, which became critical during auto-scaling events."*

- *"For our Go services, I use `FROM scratch` as the final stage with `CGO_ENABLED=0` during build. The result is a 8-10MB image with zero attack surface — no shell, no tools, nothing an attacker can use even if they exploit the application."*

- *"In CI, I target different stages for different pipeline steps. `--target test` runs the full test suite in an image with all dev tools. `--target production` is only built if tests pass, and gets scanned with Trivy before being pushed to ECR."*

- *"Layer caching is crucial in CI. I always copy dependency manifests (package.json, go.mod, pom.xml) before source code. The dependency install is cached for 95% of commits where only source changes. This saves 2-3 minutes per build."*

- *"For Java, I use JRE as the runtime base (not JDK) — the compiler is in the builder stage, never in production. And I always add `-XX:+UseContainerSupport` to the JVM flags so it reads cgroup memory limits instead of sizing the heap against total host RAM."*

- *"When someone asks me about a large Docker image, my first tools are `docker history` to find the large layers, and `dive` to see exactly which files are responsible. Almost always it is devDependencies or build tools that should have stayed in a build stage."*
