### Q1. What are the key security risks with Docker containers?

**How the interviewer asks it:**
> "What are the main security concerns when running applications in Docker?"

**Your Answer:**

> "Docker containers share the host kernel. This is the fundamental difference from VMs and the source of most security concerns. A vulnerability inside a container could potentially affect the host or other containers.
>
> The main risks are:
>
> First, containers running as root. By default, Docker containers run as the root user. If an attacker exploits a vulnerability in the application, they get root access inside the container, which with the right other vulnerabilities can lead to a host escape.
>
> Second, overprivileged containers. Using `--privileged` mode or adding too many Linux capabilities gives containers near-host-level access.
>
> Third, secrets in images. Accidentally copying .env files, API keys, or certificates into Docker images — these get stored in registry layers and can be read by anyone with pull access.
>
> Fourth, unscanned images. Running containers built from images with known CVEs in their OS packages or libraries.
>
> Fifth, no resource limits. A compromised or buggy container can exhaust CPU, memory, or process count, affecting other services on the same host.
>
> The defence is layered — you address all of these together, not just one."

### Q2. Why should you run containers as a non-root user?

**How the interviewer asks it:**
> "My Dockerfile doesn't have a USER instruction. Is that a problem?"

**Your Answer:**

> "Yes, it is a significant security problem. By default, the container process runs as root — UID 0.
>
> The risk: if an attacker finds a vulnerability in your application — a SQL injection, a remote code execution bug, an unpatched library — they get a shell inside the container. If the process is running as root, they have root inside the container. Combined with other vulnerabilities, this can lead to container escape — the attacker reaching the host machine.
>
> Even without a full escape, root inside a container can: write to any file in the container, install additional malicious software, read all config files and environment variables, and with certain volume mounts, affect the host filesystem.
>
> The fix is simple:
> ```dockerfile
> RUN addgroup -S -g 1001 appgroup && \
>     adduser -S -u 1001 -G appgroup appuser
>
> # Copy files with correct ownership
> COPY --chown=appuser:appgroup . .
>
> # Switch to non-root BEFORE CMD
> USER appuser
>
> CMD ['node', 'server.js']
> ```
>
> Now even if the attacker exploits the application, they get a shell as `appuser` with UID 1001 — very limited permissions, cannot install software, cannot access most system files. The blast radius is dramatically reduced.
>
> In our banking project, non-root containers were a hard security requirement from the client's security team. We also combined it with read-only filesystem and dropped all unnecessary capabilities."

### Q3. What is .dockerignore and why is it a security tool?

**How the interviewer asks it:**
> "I know .dockerignore speeds up builds. Is there any other reason to use it?"

**Your Answer:**

> ".dockerignore is actually a CRITICAL security tool — the performance benefit is secondary.
>
> When you run `docker build .`, Docker sends the entire current directory to the Docker daemon as the build context. Any `COPY . .` instruction in the Dockerfile copies everything in that context into the image. Without .dockerignore, your image might accidentally contain:
>
> - `.env` files with database passwords, API keys, and credentials
> - `.pem`, `.key`, `.p12` files — SSL certificates and private keys
> - `.git/` — your entire git history (which might have had secrets in old commits)
> - SSH private keys if your project folder contains them
>
> If you push this image to a registry — even a private one — anyone with pull access can run `docker run --rm --entrypoint cat myimage /app/.env` and read your production database password.
>
> This has caused real security incidents. Developers accidentally commit credentials to their Docker images thinking private registries are secure enough.
>
> My .dockerignore always includes at minimum:
> ```
> .env
> .env.*
> *.env
> *.pem
> *.key
> *.p12
> .git
> id_rsa
> secrets/
> ```
>
> After every Dockerfile change, I verify with: `docker run --rm myimage find / -name '*.env' -o -name '*.key' 2>/dev/null` — it should return nothing."

### Q4. What does `--privileged` do and why should you never use it in production?

**How the interviewer asks it:**
> "I've seen tutorials that suggest `--privileged` to fix permission problems. Is that okay?"

**Your Answer:**

> "Absolutely not in production. `--privileged` is essentially giving a container the keys to the kingdom.
>
> When a container runs with `--privileged`, it gets: all Linux capabilities enabled, access to all host devices under `/dev/`, ability to mount filesystems, ability to load kernel modules, and AppArmor and seccomp security profiles disabled.
>
> The consequence is that a container escape becomes trivial. Inside a privileged container, you can run:
> ```bash
> mkdir /host
> mount /dev/sda1 /host
> # You now have read/write access to the host's entire disk
> chroot /host
> # You are now effectively on the host machine as root
> ```
>
> This is not a vulnerability — this is the intended behaviour. `--privileged` was designed for very specific use cases like running Docker inside Docker for CI, or testing kernel features.
>
> The correct approach: instead of `--privileged`, use specific capabilities. If your app needs to bind to port 80, add only `--cap-add NET_BIND_SERVICE`. If it needs to configure network interfaces, add only `--cap-add NET_ADMIN`. You give the minimum permissions needed.
>
> I always reject pull requests that add `--privileged` without a very detailed justification and security review."

### Q5. How do you prevent secrets from ending up in Docker images?

**How the interviewer asks it:**
> "What is the correct way to handle passwords and API keys in Docker?"

**Your Answer:**

> "There are several layers here.
>
> First, never put secrets in Dockerfile instructions like ENV or ARG. Both are visible in `docker history`. Even if you delete a file in a later RUN instruction, it still exists in the earlier layer — anyone can read the image layer data.
>
> Second, always put secret file patterns in .dockerignore:
> ```
> .env
> *.key
> *.pem
> secrets/
> ```
>
> Third, for runtime secrets — inject them at container start time:
> ```bash
> docker run -e DATABASE_URL='${DATABASE_URL}' myapp
> ```
> The image contains no credentials. They are only in the running process environment.
>
> Fourth, for build-time secrets — like an npm token to install private packages — use BuildKit secret mounts:
> ```dockerfile
> RUN --mount=type=secret,id=npm_token \
>     NPM_TOKEN=$(cat /run/secrets/npm_token) npm install
> ```
> The secret is available ONLY during that RUN step. It is never written to any layer.
>
> Fifth, for production — use proper secret management. AWS Secrets Manager, HashiCorp Vault, or Azure Key Vault. The container fetches its secrets at startup from the secure store. Nothing is stored on disk or in the image.
>
> I check for secrets in images as part of code review and also run automated scans — Trivy can detect common secret patterns in image layers."

### Q6. Explain Linux capabilities in the context of Docker security.

**How the interviewer asks it:**
> "What are Linux capabilities and how do they relate to container security?"

**Your Answer:**

> "Traditionally, Linux had a binary model: root can do everything, non-root is very limited. Linux capabilities broke the 'root can do everything' into about 40 specific granular permissions.
>
> Examples of capabilities:
> - `CAP_NET_BIND_SERVICE` — bind to ports below 1024
> - `CAP_NET_ADMIN` — configure network interfaces
> - `CAP_SYS_ADMIN` — a massive catch-all for many privileged operations
> - `CAP_SYS_PTRACE` — spy on other processes
> - `CAP_SYS_MODULE` — load kernel modules
>
> Docker gives containers a limited set of capabilities by default — enough for most applications but missing the most dangerous ones like `CAP_SYS_ADMIN`.
>
> The security best practice is to drop ALL capabilities and add back only what your specific application needs:
> ```bash
> docker run --cap-drop ALL --cap-add NET_BIND_SERVICE myapp
> ```
>
> In Docker Compose:
> ```yaml
> cap_drop:
>   - ALL
> cap_add:
>   - NET_BIND_SERVICE
> ```
>
> This is the principle of least privilege applied at the kernel level. Most web applications need zero special capabilities — they just serve HTTP and talk to a database. Dropping all capabilities and adding none makes it much harder for an attacker to do anything meaningful even if they exploit the application."

### Q7. What is a read-only filesystem and how do you implement it in Docker?

**How the interviewer asks it:**
> "How do you prevent an attacker from writing malicious files inside a container?"

**Your Answer:**

> "The `--read-only` flag mounts the container's root filesystem as read-only. The container can read any file but cannot create, modify, or delete anything.
>
> This prevents an attacker who has gained code execution inside the container from: installing additional tools (no `apt-get install`), writing backdoor scripts, modifying application code, creating web shells, or writing malicious cron jobs.
>
> The challenge is that most applications need to write somewhere — log files, temp files, PID files. The solution is to combine read-only with tmpfs mounts for specific writable paths:
>
> ```bash
> docker run \
>   --read-only \
>   --tmpfs /tmp \
>   --tmpfs /run \
>   --tmpfs /var/cache/nginx \
>   nginx
> ```
>
> tmpfs paths are in RAM — writable during the container's life, automatically wiped when the container stops. For data that must persist across restarts, use named volumes on specific paths rather than making the whole filesystem writable.
>
> In Docker Compose:
> ```yaml
> services:
>   webapp:
>     read_only: true
>     tmpfs:
>       - /tmp
>       - /run
>     volumes:
>       - app-logs:/app/logs  # named volume for persistent writes
> ```
>
> Read-only filesystem is one of the security controls in the CIS Docker Benchmark — the industry standard security checklist for Docker environments."

### Q8. What is the `--no-new-privileges` flag and why should you use it?

**How the interviewer asks it:**
> "What does `--no-new-privileges` do?"

**Your Answer:**

> "`--no-new-privileges` prevents any process inside the container from gaining additional privileges through setuid or setgid programs, or through seccomp filters being bypassed.
>
> To understand why this matters, I need to explain setuid. On Linux, some executables have a special permission bit called setuid. When you run a setuid program, it temporarily runs with the OWNER's privileges rather than your own. The classic example is `passwd` — a regular user can run it to change their own password, but `passwd` needs root access to write to `/etc/shadow`. The setuid bit lets it do this.
>
> The security risk: if an attacker is inside a container as a non-root user and finds a setuid program they can exploit, they can potentially escalate to root. `--no-new-privileges` prevents this escalation path. Even if they find a setuid binary, it cannot grant them elevated privileges.
>
> Usage:
> ```bash
> docker run --no-new-privileges myapp
> ```
>
> In Docker Compose:
> ```yaml
> security_opt:
>   - no-new-privileges:true
> ```
>
> This is a defence-in-depth measure. Even with non-root user and dropped capabilities, `--no-new-privileges` closes an additional escalation path. I always include it in production configurations."

### Q9. How do AppArmor and seccomp protect containers?

**How the interviewer asks it:**
> "I see `apparmor` and `seccomp` in `docker info`. What do they actually do?"

**Your Answer:**

> "Both are Linux security mechanisms that Docker applies to containers by default — you get them automatically without any configuration.
>
> AppArmor is a mandatory access control system. It creates a security profile for each container that defines which files the container can access, which system operations it can perform, and which network connections it can make. Docker applies the `docker-default` AppArmor profile to every container. This profile restricts access to sensitive kernel paths like `/proc/sys/`, blocks ability to mount filesystems, and prevents loading kernel modules — even if the container is running as root.
>
> Seccomp (Secure Computing) filters which Linux system calls the container can make at the kernel level. Linux has over 400 system calls. A typical web application needs maybe 60-70. Docker's built-in seccomp profile blocks 44 dangerous syscalls including `reboot`, `kexec_load` (load new kernel), `create_module` (load kernel modules), `ptrace` (spy on processes), and `mount` (mount filesystems).
>
> What makes these powerful: they are enforced by the kernel, not by the container runtime. Even if someone exploits Docker itself, these kernel-level restrictions remain in effect.
>
> You can run with custom profiles if you need more or less restrictive policies:
> ```bash
> docker run --security-opt seccomp=my-strict-profile.json myapp
> docker run --security-opt apparmor=my-custom-profile myapp
> ```
>
> And you can verify what is applied:
> ```bash
> docker inspect mycontainer | jq '.[0].HostConfig.SecurityOpt'
> ```"

### Q10. Walk me through a complete secure Dockerfile and run command for a production Node.js application.

**How the interviewer asks it:**
> "Show me how you would harden a Node.js container for production."

**Your Answer:**

> "Here is my approach with every security layer applied:
>
> **Secure Dockerfile:**
> ```dockerfile
> FROM node:20-alpine
>
> # Non-root user with specific UID/GID
> RUN addgroup -S -g 1001 appgroup && \
>     adduser -S -u 1001 -G appgroup appuser
>
> WORKDIR /app
>
> # Copy dependency files with correct ownership
> COPY --chown=appuser:appgroup package*.json ./
>
> # Install production dependencies only
> RUN npm ci --only=production && npm cache clean --force
>
> # Copy application code
> COPY --chown=appuser:appgroup . .
>
> # Switch to non-root before running
> USER appuser
>
> EXPOSE 3000
>
> HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
>   CMD wget -qO- http://localhost:3000/health || exit 1
>
> CMD ['node', 'server.js']
> ```
>
> **Companion .dockerignore:**
> ```
> .env
> .env.*
> *.key
> *.pem
> .git
> node_modules
> tests/
> ```
>
> **Secure run command:**
> ```bash
> docker run -d \
>   --user 1001:1001 \
>   --read-only \
>   --tmpfs /tmp \
>   --cap-drop ALL \
>   --no-new-privileges \
>   --memory=256m \
>   --cpus=0.5 \
>   --pids-limit=50 \
>   -e DATABASE_URL='${DATABASE_URL}' \  # secret from environment, not baked in
>   -p 8080:3000 \
>   myapp:1.0
> ```
>
> **In CI pipeline before pushing:**
> ```bash
> trivy image --exit-code 1 --severity CRITICAL myapp:1.0
> ```
>
> Each layer has a purpose: non-root limits blast radius, read-only prevents persistence, cap-drop removes dangerous kernel permissions, no-new-privileges blocks escalation, resource limits prevent DoS, scanning catches CVEs before deployment.
>
> In our banking project, this configuration was the template for every microservice. The security team reviewed any deviation from this template."

### Q11. How do you audit a running container environment for security issues?

**How the interviewer asks it:**
> "You inherit a production Docker environment. How do you assess its security posture?"

**Your Answer:**

> "I would do a systematic audit covering these areas:
>
> **Step 1 — Check which containers run as root:**
> ```bash
> docker ps -q | xargs docker inspect --format '{{.Name}} User: {{.Config.User}}'
> # Empty user field = running as root = problem
> ```
>
> **Step 2 — Find privileged containers:**
> ```bash
> docker ps -q | xargs docker inspect --format '{{.Name}} Privileged: {{.HostConfig.Privileged}}'
> # Any 'true' is a critical finding
> ```
>
> **Step 3 — Check resource limits:**
> ```bash
> docker ps -q | xargs docker inspect --format '{{.Name}} Memory: {{.HostConfig.Memory}} PIDs: {{.HostConfig.PidsLimit}}'
> # Memory: 0 = no limit = problem
> ```
>
> **Step 4 — Find open ports (what is exposed to the internet):**
> ```bash
> docker ps --format 'table {{.Names}}\t{{.Ports}}'
> # Anything bound to 0.0.0.0 is reachable from anywhere
> ```
>
> **Step 5 — Scan all running images:**
> ```bash
> docker ps --format '{{.Image}}' | sort -u | \
>   xargs -I{} docker run --rm \
>     -v /var/run/docker.sock:/var/run/docker.sock \
>     aquasec/trivy image --severity HIGH,CRITICAL {}
> ```
>
> **Step 6 — Check for secrets in images:**
> ```bash
> docker ps --format '{{.Image}}' | sort -u | \
>   xargs -I{} trivy image --secret-config trivy-secret.yaml {}
> ```
>
> **Step 7 — Check docker daemon configuration:**
> ```bash
> cat /etc/docker/daemon.json
> # Check: userns-remap, no-new-privileges defaults, log settings
> ```
>
> I document every finding with severity and remediation steps, then prioritise: privileged containers and exposed credentials are P0 — fix immediately. No resource limits and root users are P1 — fix within 24 hours."

### Q12. What is container breakout and what Docker security controls prevent it?

**How the interviewer asks it:**
> "Can an attacker 'escape' from a container to the host? How?"

**Your Answer:**

> "Yes, container breakout is a real attack class. Since containers share the host kernel, a kernel vulnerability or container misconfiguration can allow an attacker to escape isolation and reach the host.
>
> Common container breakout paths:
>
> **Privileged containers:** A privileged container can mount the host filesystem directly. This is the most common path I see in security reviews — someone added `--privileged` to fix a permission problem and opened a complete host escape.
>
> **Docker socket mount:** Mounting `/var/run/docker.sock` into a container gives it complete control of Docker on the host. An attacker inside the container can then run `docker run --privileged --pid=host ubuntu nsenter -t 1 -m -u -i -n sh` to get a host shell.
>
> **Kernel exploits:** Vulnerabilities in the kernel can be exploited from inside a container to escape to the host. This is why keeping the kernel updated is critical.
>
> **runc vulnerabilities:** CVE-2019-5736 (Runc CVE) allowed container processes to overwrite the runc binary itself, gaining host code execution. Docker patched this quickly but it showed that even the runtime can be attacked.
>
> Controls that prevent or limit breakout:
> - No `--privileged` mode
> - Never mount docker.sock unless absolutely required, and only in trusted containers
> - Run as non-root (limit what code can do if it executes)
> - seccomp profile (blocks dangerous syscalls like `ptrace`, `mount`)
> - AppArmor profile (restricts file access and operations)
> - `--no-new-privileges` (blocks setuid escalation)
> - Keep host kernel and Docker updated (patch known kernel CVEs)
> - Use rootless Docker or gVisor for highest security requirements"

### Q13. "Security audit found our containers running as root. How do you fix this across 20 microservices?"

**Your Answer:**

> "This is a common finding during security reviews. Here is the systematic approach:
>
> **Phase 1 — Assessment (do not break things rushing):**
> First understand WHY they are running as root. Common reasons:
> - Binding to port 80 or 443 (requires root or CAP_NET_BIND_SERVICE)
> - Writing to directories owned by root
> - Using setuid programs
> - No one thought about it
>
> ```bash
> # Document current state
> docker ps -q | xargs docker inspect --format '{{.Name}} Port: {{.NetworkSettings.Ports}} User: {{.Config.User}}' > current-state.txt
> ```
>
> **Phase 2 — Standard fix (for most services):**
> Add to each Dockerfile:
> ```dockerfile
> RUN addgroup -S -g 1001 appgroup && \
>     adduser -S -u 1001 -G appgroup appuser
> COPY --chown=appuser:appgroup . .
> USER appuser
> ```
>
> **Phase 3 — Handle port binding:**
> Change all services from port 80 to port 8080 internally. Publish as `-p 80:8080`. Or add `--cap-add NET_BIND_SERVICE` specifically for services that need it.
>
> **Phase 4 — Handle directory permissions:**
> ```dockerfile
> RUN mkdir -p /app/logs && chown -R appuser:appgroup /app/logs
> USER appuser
> ```
>
> **Phase 5 — Roll out gradually:**
> Fix and deploy one service at a time. Test each one. Rollout takes a week for 20 services if done carefully.
>
> **Phase 6 — Prevent regression:**
> Add to CI pipeline: a Trivy check that fails if the USER instruction is missing. Or a custom OPA policy that rejects deployments with root containers."

### Q14. "Our CI scan found a CRITICAL CVE in our base image. What do you do?"

**Your Answer:**

> "A critical CVE means there is a known, exploitable vulnerability in something inside the image. This could be in the OS, the runtime, or a library. Here is my response:
>
> **Step 1 — Understand the CVE:**
> ```bash
> trivy image --severity CRITICAL myapp:1.0
> # Read the CVE ID, affected library, description, and Fixed Version column
> ```
> The Fixed Version column is crucial — if it says there is a fix, you can resolve it. If it says 'None', the fix has not been released yet.
>
> **Step 2 — Check if it is exploitable in your context:**
> Not all CVEs are exploitable in every application. A CVE in an image compression library only matters if your application handles user-uploaded images. A CVE in a network protocol implementation only matters if you use that protocol.
>
> **Step 3 — Fix it:**
>
> If the CVE is in the base image OS packages:
> ```dockerfile
> FROM node:20-alpine
>
> # Update all packages to latest patched versions
> RUN apk update && apk upgrade && rm -rf /var/cache/apk/*
>
> # OR switch to a newer base image version
> FROM node:20.15.0-alpine3.20  # specific version with patches
> ```
>
> If the CVE is in your application dependencies:
> ```bash
> npm audit fix   # for Node.js
> pip install --upgrade vulnerable-package  # for Python
> ```
>
> **Step 4 — Rebuild, rescan, redeploy:**
> ```bash
> docker build -t myapp:1.0.1-patched .
> trivy image --exit-code 1 --severity CRITICAL myapp:1.0.1-patched
> docker push myapp:1.0.1-patched
> # Deploy with rollout
> ```
>
> **Step 5 — If no fix is available yet:**
> Document it, set a review date, check daily for the fix to be released. Consider adding a Trivy ignore file with the specific CVE and an expiry date so the CI still runs while you wait for a fix."

## Phrases That Show Senior-Level Thinking

- *"We follow defence in depth — non-root user, read-only filesystem, dropped capabilities, and image scanning. No single control is perfect, so we layer them."*

- *"In our banking project, non-root containers and no-privileged were hard requirements from the client's security team. We enforced them with OPA policies that rejected any deployment that violated these rules."*

- *"I always check Trivy output for the Fixed Version column. If a fix exists, I update. If there is no fix yet, I document it with a Jira ticket and check weekly for a patch. I also use `--ignore-unfixed` in CI so unfixable CVEs do not block the pipeline while we wait."*

- *"I think of the attack surface in layers: reduce the image (use alpine), secure the runtime (non-root, read-only, cap-drop), protect the kernel (seccomp, AppArmor), and control the network (minimal published ports, network segmentation)."*

- *"A common mistake I see is adding `--privileged` to fix a permission error. There is almost always a more targeted fix — add a specific capability, change file ownership in the Dockerfile, or use a different port. `--privileged` is technical debt that creates serious security exposure."*

- *"For secrets, I have a zero-tolerance policy: nothing in the image, nothing in docker history. Runtime injection via environment variables for simple cases, AWS Secrets Manager for production. I verify with trivy secret scanning in CI."*
