## 1. Why Does `docker info` Exist?

### The Scenario

You are a DevOps engineer.
Something is broken in Docker on a server.
You SSH into the machine.
You need to understand the CURRENT STATE immediately.

Questions you need to answer:
- How many containers are running?
- Which storage driver is active?
- How much RAM does this machine have?
- Is this machine part of a cluster?
- What security systems are protecting it?

`docker info` answers ALL of these in one command.

### What This Command Does Step by Step

When you type `docker info`:

**Step 1** — Docker CLI opens `/var/run/docker.sock` and connects to `dockerd`

**Step 2** — Sends one request: "Give me a complete status report"

**Step 3** — `dockerd` collects from multiple sources:
- Its own memory → container counts, image counts
- The Linux kernel → CPU count, total RAM, kernel version
- containerd → storage driver, runtime info
- Security systems → AppArmor, seccomp status
- Swarm state → is this machine in a cluster?

**Step 4** — `dockerd` returns all of this as JSON

**Step 5** — CLI formats it and prints the output you see

Think of `docker info` as a **complete health report card** of your entire Docker system at this exact moment.

## 2. How Is It Different From `docker version`?

| | `docker version` | `docker info` |
|--|--|--|
| **Question it answers** | What versions are installed? | What is the current state? |
| **Changes over time?** | No — versions stay same | Yes — containers start/stop, images added |
| **Use case** | Checking compatibility, reporting bugs | Troubleshooting, understanding system |
| **Analogy** | Car model year and engine specs | Car's current fuel, temperature, tyre pressure |

**Rule of thumb:**
When you sit down at any new machine for the first time — run BOTH commands.
`docker version` tells you what you have.
`docker info` tells you what state it is in.

#### `Debug Mode: false`

**What is Debug Mode?**

When debug mode is ON, Docker prints every internal step it takes.

Normal output of `docker run nginx`:
```
Unable to find image 'nginx:latest' locally
latest: Pulling from library/nginx
Status: Downloaded newer image for nginx:latest
```

```
DEBU[0000] form data: {"Image":"nginx","HostConfig":{...}}
DEBU[0000] POST /v1.52/containers/abc123/start
... (hundreds of lines of internal steps)
```

`false` = debug is OFF. Normal behaviour. You only turn this ON when something is broken and you need to understand what Docker is doing internally.

**How to use debug mode when needed:**
```bash

docker --debug run nginx

# Enable permanently in daemon config
sudo nano /etc/docker/daemon.json
# Add: { "debug": true }
# Then restart: sudo systemctl restart docker
```

#### `Plugins:` / `trust plugin`

**What is a Plugin?**

A plugin is an extra piece of software that adds new commands to the main Docker CLI.
The core Docker CLI has commands like `run`, `ps`, `images`, `build`.
Plugins add MORE commands on top of these.

```
Plugins:
  trust: Manage trust on Docker images (Docker Inc.)
   Version: 29.1.3
   Path: /usr/libexec/docker/cli-plugins/docker-trust
```

**`trust` plugin** = adds the `docker trust` set of commands.

**What does `docker trust` do?**

When you pull an image from Docker Hub, how do you know it is genuine?
How do you know someone did not replace the real nginx image with a fake malicious one?

The trust plugin lets publishers **digitally sign** images.
A digital signature is a mathematical proof that:
- This image came from the original publisher
- Nobody changed the image after it was signed

You verify the signature before using the image.
If the signature is wrong — Docker warns you and refuses to run the image.

**`Path: /usr/libexec/docker/cli-plugins/docker-trust`**

Breaking down this path character by character:

`/usr` = a standard Linux folder for user-installed programs and their files.

`/usr/libexec` = programs inside this folder are NOT meant to be run directly by you.
They are helper programs that OTHER programs call internally.
You type `docker trust` — Docker CLI internally calls this binary.
You would never type the full path yourself.

`/docker/cli-plugins/` = Docker's specific subfolder for plugin binaries.

`docker-trust` = the actual plugin binary file (an executable program).

```bash
# See all available Docker CLI plugins installed on your machine
ls /usr/libexec/docker/cli-plugins/

# Try the trust plugin
docker trust --help
```

#### `Containers: 1` / `Running: 1` / `Paused: 0` / `Stopped: 0`

**This is a live snapshot of your Docker containers right now.**

```
Containers: 1    ← total containers that EXIST on this machine
  Running: 1     ← actively running right now
  Paused: 0      ← frozen (process suspended, memory still held)
  Stopped: 0     ← finished running but not deleted yet
```

**What is a Paused container?**

A paused container is like pressing **Pause on a video game**.
The process is frozen in place.
It is not using any CPU.
But it still holds its memory.
Everything is exactly as it was the moment you paused it.

```bash
docker pause mycontainer      # freeze the container
docker unpause mycontainer    # resume exactly where it stopped
```

**What is a Stopped container?**

A stopped container has finished running.
Its process is dead.
But the container itself — its configuration, its writable layer — still exists on your disk.
It is like a computer that is switched off but still sitting on your desk.

```bash
docker stop mycontainer       # stop the running process
docker start mycontainer      # start it again
docker rm mycontainer         # delete it completely — writable layer gone
```

**Why does a stopped container still exist?**

Because you might want to:
- Restart it later
- Inspect its logs (`docker logs`)
- Copy files out of it (`docker cp`)
- Commit it as a new image (`docker commit`)

If you do not need it anymore — always remove it to free up disk space:
```bash
# Remove all stopped containers at once
docker container prune
```

#### `Storage Driver: overlayfs` / `driver-type: io.containerd.snapshotter.v1`

**What is a Storage Driver?**

A storage driver is the system Docker uses to:
- Store image layers as files on your disk
- Create a new writable layer when a container starts
- Merge all layers together using OverlayFS (so the container sees one filesystem)

**`overlayfs`** = your Docker uses OverlayFS.
We studied this in the Core Concepts file.

**But wait — older Docker showed `overlay2`. Now it shows `overlayfs`. Why?**

This is an important architectural change in newer Docker:

**Old Docker (before ~2024):**
```
dockerd managed its OWN overlay2 storage
Layers stored in: /var/lib/docker/overlay2/
```

**New Docker (your version 29.x):**
```
dockerd delegates ALL storage to containerd
containerd manages "snapshots" (same concept as layers)
driver-type: io.containerd.snapshotter.v1
```

**`io.containerd.snapshotter.v1`** = containerd's snapshot manager, version 1.

A **snapshot** in containerd = same idea as a layer in old Docker.
Each image layer is an immutable snapshot.
When a container starts, containerd creates a new writable snapshot on top.
OverlayFS merges them all into one view for the container.

**Why did Docker make this change?**

Because Kubernetes also uses containerd.
If both Docker and Kubernetes use containerd for storage, they share the same image cache.
You pull an image with `docker pull` → Kubernetes can see it too.
No duplication. No wasted disk space.

#### `Logging Driver: json-file`

**What is a Logging Driver?**

When your container runs, it produces output — log messages, errors, status lines.
This output goes to STDOUT (standard output) and STDERR (standard error).

A logging driver decides: **where does this output get saved?**

**`json-file`** = Docker saves every log line to a JSON file on your disk.

**Exactly where on disk?**
```
/var/lib/docker/containers/<container-id>/<container-id>-json.log
```

Each log line looks like this inside the file:
```json
{"log":"2026-06-27 10:00:01 nginx: worker process started\n","stream":"stdout","time":"2026-06-27T10:00:01Z"}
```

`"log"` = the actual message from the container
`"stream"` = was it stdout or stderr?
`"time"` = when it happened (UTC)

**You never read this file directly.**
Docker provides a clean command:
```bash
docker logs mycontainer            # show all logs
docker logs -f mycontainer         # follow in real time (like tail -f)
docker logs --tail 50 mycontainer  # show last 50 lines only
docker logs -t mycontainer         # show with timestamps
```

**All logging drivers available on your machine:**
```
Log: awslogs fluentd gcplogs gelf journald json-file local splunk syslog
```

| Driver | Where logs go |
|--------|--------------|
| `json-file` | JSON files on local disk (default) |
| `awslogs` | AWS CloudWatch Logs |
| `journald` | Ubuntu's systemd journal |
| `splunk` | Splunk log management system |
| `fluentd` | Fluentd log collector |
| `syslog` | Linux system syslog |

**A critical production warning about `json-file`:**

Logs keep growing with NO limit.
A busy container can produce gigabytes of logs.
This can fill your entire disk and crash the server.

**Always configure log rotation in production:**
```bash
docker run \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  nginx

# --log-opt max-size=10m  = each log file maximum 10 megabytes
# --log-opt max-file=3    = keep maximum 3 log files, rotate and delete oldest
```

Or set it globally for ALL containers in `/etc/docker/daemon.json`:
```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

#### `Cgroup Driver: systemd`

**What is a Cgroup Driver?**

cgroups is the Linux kernel feature that limits container resources (CPU, memory, PIDs).
But something needs to **manage** these cgroup settings — create them, set values, delete them.

That something is the **cgroup driver**.

Two choices exist:

**Option 1 — `cgroupfs`:**
Docker writes directly to `/sys/fs/cgroup/` files itself.
Docker manages cgroups completely on its own.

**Option 2 — `systemd`:**
Docker asks Ubuntu's systemd: "Please create this cgroup for me."
systemd creates and manages it.

**Why is `systemd` the correct choice on Ubuntu?**

Ubuntu uses **systemd** as its init system — the master manager of all services and processes.
systemd ALSO manages cgroups for all system services.

If Docker used `cgroupfs` and managed cgroups itself, you would have TWO systems both managing cgroups at the same time — Docker AND systemd.
This creates conflicts and unpredictable behaviour.

With `systemd` driver:
Docker says to systemd: "Please handle cgroups for me."
systemd does it.
One system manages all cgroups. No conflicts. Clean.

**This is also what Kubernetes recommends** — always use `systemd` cgroup driver when running on Ubuntu/systemd systems.

---

#### `Cgroup Version: 2`

**cgroups v1 vs v2 — What changed?**

**cgroups v1 (old — released 2008):**
- Each resource type had its OWN separate hierarchy
- CPU limits in one folder, memory limits in another folder
- Inconsistent and hard to manage
- Some features like memory+swap limits together were broken

**cgroups v2 (new — default on Ubuntu 22.04+):**
- ONE unified hierarchy for ALL resources
- Better performance and more accurate accounting
- Proper memory+swap limit support
- Required for some Kubernetes pod security features

```
cgroups v2 on your machine:
/sys/fs/cgroup/
├── cgroup.controllers    ← lists what v2 can control
├── memory.max            ← memory limit for a group
├── cpu.max               ← cpu limit for a group
└── pids.max              ← process count limit
```

vs old cgroups v1:
```
/sys/fs/cgroup/
├── memory/               ← separate hierarchy for memory
├── cpu/                  ← separate hierarchy for CPU
└── pids/                 ← separate hierarchy for PIDs
```

`Cgroup Version: 2` = you are on the modern version. Good.

## 4. Docker Swarm — What Is It and Why Is It Inactive?

```
Swarm: inactive
```

### Start From Zero — What Problem Does Swarm Solve?

Imagine your web application becomes very popular.
It gets 50,000 requests per minute.
One machine cannot handle this.
You need to run your containers across **multiple machines**.

This is called **container orchestration** — managing containers across a fleet of machines.

Docker Swarm was Docker's built-in answer to this problem.

---

### What Does Docker Swarm Actually Do?

Swarm creates a **cluster** — a group of machines that work together as one system.

```
Without Swarm — single machine:
┌───────────────────────────────┐
│   Your ThinkPad L14           │
│   [web-container]             │
│   [db-container]              │
└───────────────────────────────┘
Problem: If this machine dies → everything dies

With Swarm — 3 machines working as ONE:
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│   Machine 1     │  │   Machine 2     │  │   Machine 3     │
│   (Manager)     │  │   (Worker)      │  │   (Worker)      │
│   [web-1]       │  │   [web-2]       │  │   [web-3]       │
│   [db-1]        │  │                 │  │   [db-2]        │
└─────────────────┘  └─────────────────┘  └─────────────────┘

If Machine 2 dies → Swarm automatically moves web-2 to Machine 1 or 3
You do not need to do anything manually
```

**Swarm key concepts:**

**Manager node** = the machine that controls the cluster.
It receives your commands.
It decides which worker runs which container.
It monitors health.

**Worker node** = machines that actually run the containers.
They do what the manager tells them.

**Service** = in Swarm, you do not run individual containers.
You define a **service** — "run 3 copies of nginx across my cluster."
Swarm creates and manages those 3 copies automatically.

**Replica** = one copy of your container.
3 replicas = 3 containers spread across your machines.

---

### Is Docker Swarm Dead?

**Honest answer: Mostly yes. Still exists but not recommended for new projects.**

Here is the complete history:

```
2014 → Docker releases Swarm. Simple clustering.
2014 → Google releases Kubernetes. More complex but much more powerful.
2015-2017 → Both exist. Companies try both. Kubernetes keeps winning.
2017 → Docker themselves add Kubernetes support to Docker Desktop.
       This was the signal — even Docker admitted Kubernetes won.
2019+ → Almost zero new companies adopt Swarm for production.
2023 → Swarm development mostly frozen. Only security patches.
2026 → Swarm still works. Gets security fixes.
       But ~95% of all container orchestration in industry is Kubernetes.
```

---

### Why Did Kubernetes Win? Honest Comparison

| Feature | Docker Swarm | Kubernetes |
|---------|-------------|------------|
| Setup difficulty | Very easy — 10 minutes | Complex — hours or days |
| Auto-scaling | Basic | Advanced (HPA, VPA, KEDA) |
| Self-healing | Basic | Very powerful |
| Rolling updates | Yes | Yes + canary, blue-green, etc. |
| Secret management | Basic | Proper secrets system |
| Storage | Limited | Rich (PV, PVC, StorageClass) |
| Networking | Simple | Powerful (CNI plugins) |
| Community | Small, shrinking | Massive, growing daily |
| Cloud support | Very limited | AWS EKS, Google GKE, Azure AKS |
| Industry adoption | Less than 5% | More than 95% |

Swarm was easier to START with.
But Kubernetes could do so much more.
Industry chose power and flexibility.

## 5. Security Options — How Docker Protects Your Machine

```
Security Options:
  apparmor
  seccomp
   Profile: builtin
  cgroupns
```

Docker applies **three security layers** to every container automatically.
You do not configure these — they are ON by default.

---

### Layer 1 — AppArmor

**AppArmor** = Application Armor.

**Start from zero — what is it?**

Linux lets any program do almost anything — read files, make network connections, write to any folder.
This is dangerous. If a container is compromised, the attacker can do anything.

AppArmor creates a **security profile** (a rulebook) for each program.
The profile says exactly what this program is allowed and NOT allowed to do.

**Real-life analogy:**

New employee joins a company.
The security department gives them an access card.
The card says:
- Floor 3 (their office): ✅ Access allowed
- Floor 1 (server room): ❌ Access denied
- Floor 2 (finance): ❌ Access denied
- Ground floor (cafeteria): ✅ Access allowed

The employee cannot go where the card does not allow — even if they want to.

AppArmor gives containers a similar access card for the Linux system.

**Docker's default AppArmor profile restricts:**
- Writing to sensitive system directories like `/proc/sys/`
- Mounting filesystems
- Loading kernel modules
- Accessing hardware devices

```bash
# See Docker's AppArmor profile
sudo cat /etc/apparmor.d/docker

# Check which profiles are active
sudo aa-status
# Look for 'docker-default' in the enforce mode list
```

---

### Layer 2 — Seccomp

**seccomp** = Secure Computing Mode.

**Start from zero — what is a system call?**

Every program that runs on Linux needs to ask the kernel to do things.
These requests are called **system calls** (syscalls).

Examples:
```
read()        = kernel, please read data from this file
write()       = kernel, please write this data to disk
connect()     = kernel, please open a network connection
clone()       = kernel, please create a new process
mount()       = kernel, please mount a filesystem
reboot()      = kernel, please restart the system
```

Linux has over 400 system calls.
A typical web server (nginx, node.js) needs maybe 50-60 of them.
It does NOT need `reboot()` or `kexec_load()` (load a new kernel).

**Seccomp creates a filter:**
"This container is ALLOWED to use these syscalls. Everything else — BLOCKED."

**`Profile: builtin`** = Docker uses its own built-in default seccomp profile.

**This profile blocks 44 dangerous syscalls including:**

| Blocked Syscall | Why It Is Dangerous |
|-----------------|---------------------|
| `reboot` | Could restart the host server |
| `kexec_load` | Could load a new malicious kernel |
| `mount` | Could mount sensitive host filesystems |
| `create_module` | Could load malicious kernel modules |
| `ptrace` | Could spy on other processes |
| `acct` | Could manipulate accounting |

**Simple analogy:**

You give a contractor access to your house to fix the bathroom.
But you give them a limited key — it only opens the bathroom and the front door.
The master bedroom key, the safe key, the server room key — they do not get those.
Even if they wanted to access those areas, the key simply does not work.

Seccomp is that limited key for containers.

---

### Layer 3 — cgroupns (Cgroup Namespaces)

**cgroupns** = cgroup namespace.

**What problem does it solve?**

Without cgroup namespace, a container could read `/sys/fs/cgroup/` and see:
- The names of ALL other containers on the host
- What resource limits ALL other containers have
- Information about the host's own cgroups

This is an information leak. A container should not know about other containers.

**With cgroupns:**
Each container sees ONLY its own cgroup information.
All other containers' cgroup data is invisible.

**Simple analogy:**

You are staying in a hotel.
Without privacy: you can walk into any other room and see their personal data.
With cgroupns: you see only YOUR room. All other rooms are invisible to you.

---

### All Three Working Together

```
Container tries to do something suspicious:

Action attempted: "Mount the host's /etc directory"

Layer 1 — AppArmor checks:  "Is mount allowed in this profile?"
                              → NO → BLOCKED. Action stopped.

If Layer 1 passed, Action attempted: "Call mount() system call"

Layer 2 — Seccomp checks:   "Is mount() in the allowed syscalls list?"
                              → NO → BLOCKED. Kernel refuses.

Layer 3 — cgroupns:          "Can this container see other containers' cgroup data?"
                              → NO → Isolated view only.
```

All three run on every container, all the time, with zero extra configuration from you.

## 6. Practical Labs

### Lab 1 — Run `docker info` and Read the Output

```bash
docker info
```

**What happens behind the scenes when this runs:**

`docker` = the CLI binary at `/usr/bin/docker` is executed

`info` = the subcommand tells the CLI: collect system information

The CLI opens `/var/run/docker.sock` and sends:
```
GET /v1.52/info HTTP/1.1
Host: /var/run/docker.sock
```

`dockerd` receives this HTTP request.
It collects data from memory, kernel, containerd, security systems.
It sends back a large JSON response.
The CLI formats the JSON into the human-readable output you see.

---

### Lab 2 — See the Raw JSON Behind `docker info`

```bash
docker info --format '{{json .}}' | jq .
```

**Every word explained:**

`docker` = the CLI program

`info` = the subcommand

`--format` = a flag meaning "change how the output is presented"

`'{{json .}}'` = a formatting template written in Go template syntax
- `{{` and `}}` = template expression delimiters
- `json` = function that converts data to JSON format
- `.` = the dot means "the entire data object" (all of it)

`|` = pipe operator

### Lab 4 — Measure the `/var/lib/docker` Folder Size

```bash
sudo du -sh /var/lib/docker/
```

**Every word explained:**

`sudo` = superuser do.
Run the next command as the root (administrator) user.
We need this because `/var/lib/docker/` is owned by root and normal users cannot read it.

`du` = disk usage.
A Linux command that measures how much disk space files and folders use.

`-s` = summary.
Do not list every single file and subdirectory.
Just give the TOTAL for the whole folder.

`-h` = human readable.
Show sizes as KB, MB, GB instead of raw bytes (bytes are hard to read: 2147483648 vs 2.0GB).

`/var/lib/docker/` = the path we want to measure.

Let us break down this path:

`/var` = variable data folder. Data that changes over time lives here.

`/var/lib` = library data. Persistent data that applications store for their own use.
`lib` = library (data stored by applications for themselves)

`/var/lib/docker/` = everything Docker stores permanently:
```
/var/lib/docker/
├── image/           ← image metadata (small JSON files)
├── containerd/      ← containerd's snapshot/layer data (large — all image layers here)
├── containers/      ← container config files and json-file logs
├── volumes/         ← named volume data
├── network/         ← network configuration
└── tmp/             ← temporary files during builds
```

**Expected output:**
```
2.1G    /var/lib/docker/
```

Docker is using 2.1 GB of your disk.
As you pull more images and run more containers, this grows.

**If disk fills up — how to clean:**
```bash
# Remove stopped containers, unused images, unused networks, build cache
docker system prune

# Remove EVERYTHING not currently used (be careful in production!)
docker system prune -a

# -a = all. Also removes images not used by any container.
```

### Lab 5 — Confirm cgroups v2 Is Active

```bash
cat /sys/fs/cgroup/cgroup.controllers
```

**Every word explained:**

`cat` = concatenate.
Reads a file and prints its contents to the screen.
(The name comes from its original use of joining multiple files together. Now mostly used to just read one file.)

`/sys/fs/cgroup/cgroup.controllers` — breaking down this path:

`/sys` = a special virtual filesystem.
It is NOT stored on your hard drive.
The Linux kernel generates its contents dynamically.
Reading files here asks the kernel for information.
Writing to files here sends instructions to the kernel.
Think of `/sys` as a window directly into the kernel's internal state.

`/sys/fs` = filesystem-related kernel information

`/sys/fs/cgroup` = the cgroup subsystem exposed as a folder.
This is where all cgroup data lives.

`cgroup.controllers` = a file that lists which resource types cgroups v2 can control.

**Expected output:**
```
cpuset cpu io memory hugetlb pids rdma misc
```

**What each word means:**
- `cpuset` = assign containers to specific CPU cores
- `cpu` = CPU time limits (what we set with `--cpus=`)
- `io` = disk read/write speed limits
- `memory` = RAM limits (what we set with `--memory=`)
- `pids` = process count limits (what we set with `--pids-limit=`)
- `hugetlb` = huge memory pages (for databases and high-performance apps)
- `rdma` = Remote Direct Memory Access (for high-speed network hardware)
- `misc` = miscellaneous resources

This output confirms cgroups v2 is active and working.

### Lab 7 — See iptables Rules Docker Creates for Networking

```bash
sudo iptables -L DOCKER -n -v
```

**Every word explained:**

`sudo` = need root to read iptables rules

`iptables` = Linux's built-in firewall and network packet routing tool.
Docker uses this to make port publishing work.

`-L DOCKER` = List rules in the chain named `DOCKER`.
`-L` = list.
`DOCKER` = the specific chain name.
iptables organises rules into "chains". Docker creates its own chain called DOCKER.

`-n` = numeric output.
Show IP addresses as numbers (172.17.0.2) instead of trying to look up hostnames.
Faster and clearer.

`-v` = verbose.
Show additional details like packet counts, byte counts, and network interfaces.

**Expected output when a container is running with port published:**
```
Chain DOCKER (1 references)
target     prot opt source               destination
ACCEPT     tcp  --  0.0.0.0/0            172.17.0.2           tcp dpt:80
```

**Decoding this rule:**

`ACCEPT` = allow this traffic through

`tcp` = this rule applies to TCP protocol traffic

`0.0.0.0/0` = from ANY source IP address (anywhere on the internet)

`172.17.0.2` = going TO this container's IP address

`tcp dpt:80` = TCP destination port 80

**In plain English:**
"Allow TCP traffic from anywhere, going to container at 172.17.0.2, on port 80."

This is exactly how `docker run -p 8080:80 nginx` works — Docker creates these iptables rules automatically.

### Lab 8 — Check Live Restore Setting

```bash
# Check current setting
docker info | grep "Live Restore"

# See the daemon config file
cat /etc/docker/daemon.json
```

**Breaking down `cat /etc/docker/daemon.json`:**

`cat` = read and print file

`/etc/docker/daemon.json` = Docker's main configuration file

`/etc` = a standard Linux folder for configuration files.
`etc` originally stood for "etcetera" — it is where system configuration files live.

`/etc/docker/` = Docker-specific configuration folder

`daemon.json` = configuration file for the `dockerd` daemon.
Written in JSON format.
All settings that control how `dockerd` behaves go here.

**If the file does not exist:**
Docker uses built-in defaults for everything.
The file only needs to exist when you want to change something.

**To enable Live Restore:**
```bash
# Open the file in nano text editor
sudo nano /etc/docker/daemon.json

# Type this content:
{
  "live-restore": true
}
# Save: Ctrl+O then Enter
# Exit: Ctrl+X

# Restart dockerd to apply the change
sudo systemctl restart docker

# Verify
docker info | grep "Live Restore"
# Output: Live Restore Enabled: true
```

**What does Live Restore actually do?**

Without Live Restore (`false`):
- You restart `dockerd` (for an upgrade or config change)
- All running containers STOP
- Users experience downtime

With Live Restore (`true`):
- You restart `dockerd`
- Running containers keep running throughout
- `dockerd` reconnects to them after restart
- Zero downtime for your containers

In production systems, Live Restore should always be `true`.

## 7. Why This Matters in Interviews

---

### Q: What is `docker info` and when do you use it?

> "I run `docker info` as one of the first commands when I connect to any new Docker host. It gives me an instant complete picture — how many containers are running, which storage driver is in use, what security options are active, the host's CPU and memory, whether it is part of a Swarm cluster. It is like a health report card for the entire Docker system. I also use it when troubleshooting — for example, if containers are behaving differently between two machines, comparing `docker info` output often reveals the difference immediately, like a different storage driver or cgroup version."

---

### Q: What does `Storage Driver: overlayfs` with `io.containerd.snapshotter.v1` mean?

> "It means Docker is using OverlayFS for layer management, but the storage is now delegated to containerd's snapshot system rather than managed by dockerd directly. In Docker 29.x, dockerd hands off image layer storage to containerd. This is a modern architecture change that means both Docker and Kubernetes on the same machine share the same containerd image store — no duplication. Functionally, OverlayFS still stacks image layers and gives each container a writable layer on top — the same behaviour as the older overlay2 driver."

---

### Q: What is Docker Swarm and why is it inactive?

> "Docker Swarm is Docker's built-in container orchestration tool for clustering multiple machines. In Swarm mode, you have manager nodes that schedule work and worker nodes that run containers. You deploy services — Docker maintains the specified number of replicas across the cluster and handles failover automatically. In my output it shows inactive because this is a standalone development machine. In terms of industry adoption, Swarm has largely been replaced by Kubernetes. Kubernetes offers much richer features, larger community, and native support from all cloud providers — AWS EKS, Google GKE, Azure AKS. In 2026 virtually all production orchestration uses Kubernetes."

---

### Q: What security options does Docker apply by default?

> "Docker applies three security layers by default to every container. First, AppArmor — a mandatory access control system that gives each container a security profile defining which files and operations it is allowed to access. Second, seccomp — it filters which Linux system calls the container can make. Docker's built-in profile blocks 44 dangerous syscalls including reboot, mount, and kexec_load. Third, cgroup namespaces — each container gets an isolated view of the cgroup filesystem so it cannot see other containers' resource information. These three layers are active on every container without any extra configuration and significantly reduce what a compromised container can do."

## 8. Quick Revision Cheatsheet

| Field | What It Tells You |
|-------|------------------|
| `Containers: N` | Total containers that exist (not just running) |
| `Running / Paused / Stopped` | Live breakdown of container states |
| `Images: N` | Docker images downloaded locally |
| `Storage Driver: overlayfs` | OverlayFS via containerd snapshotter — modern architecture |
| `Logging Driver: json-file` | Logs saved to JSON files in `/var/lib/docker/containers/` |
| `Cgroup Driver: systemd` | systemd manages cgroups — correct for Ubuntu |
| `Cgroup Version: 2` | Modern cgroups — better features and performance |
| `Swarm: inactive` | Standalone machine, not part of any cluster |
| `Default Runtime: runc` | runc creates containers by calling Linux kernel |
| `Init Binary: docker-init` | tini — proper PID 1 signal handling |
| `Security: apparmor` | File access control profile applied to each container |
| `Security: seccomp builtin` | 44 dangerous syscalls blocked by default |
| `Security: cgroupns` | Container cannot see other containers' cgroup data |
| `Kernel Version` | Linux kernel — Docker uses it directly for namespaces and cgroups |
| `CPUs / Total Memory` | Host machine hardware available to containers |
| `Docker Root Dir` | `/var/lib/docker` — ALL Docker data lives here |
| `Username` | Logged into Docker Hub (enables push/pull from your account) |
| `Insecure Registries` | Localhost allowed without HTTPS — external always requires HTTPS |
| `Live Restore: false` | Containers stop if dockerd restarts |
| `Firewall Backend: iptables` | Port forwarding and container routing managed by iptables |

| Important Path | What Lives There |
|----------------|-----------------|
| `/var/lib/docker/` | ALL Docker data — images, containers, volumes, logs |
| `/var/lib/docker/containers/` | Container config and json-file logs |
| `/var/lib/docker/volumes/` | Named volume data |
| `/etc/docker/daemon.json` | Docker daemon configuration |
| `/var/run/docker.sock` | Socket for CLI ↔ daemon communication |
| `/sys/fs/cgroup/` | cgroup limits and stats exposed by kernel |
| `/etc/apparmor.d/docker` | Docker's AppArmor security profile |
| `/usr/libexec/docker/cli-plugins/` | Docker CLI plugin binaries |
