## Basic Level Questions

### Q1. What is Docker Compose and why do we use it?

**How the interviewer asks it:**
> "Can you explain what Docker Compose is and what problem it solves?"

**Your Answer:**

> "Docker Compose is a tool for defining and running multi-container Docker applications. Instead of running a separate `docker run` command for each container with all its flags and options, you write everything once in a YAML file called `docker-compose.yml`.
>
> The problem it solves is operational complexity. A real application is never just one container — it is typically a frontend, a backend API, a database, maybe a cache, maybe a queue. Without Compose, to start this you run 5-6 long `docker run` commands, create networks manually, create volumes manually, and remember the correct startup order. If a new developer joins, they have to learn all these commands. Any mistake and the setup is broken.
>
> With Compose, all of this is captured in a single file that lives in your repository. Anyone can start the entire application with one command: `docker compose up -d`. Stop everything with one command: `docker compose down`. The configuration is version-controlled, reproducible, and shareable.
>
> One important thing to know: Compose is for single-machine deployments. For production across multiple machines, you use Kubernetes."

---

### Q2. What is the structure of a docker-compose.yml file?

**How the interviewer asks it:**
> "Walk me through the basic structure of a Compose file."

**Your Answer:**

> "A Compose file has three main top-level sections.
>
> `services:` is where you define every container you want to run. Each entry is a service with a name you choose, and under it you specify the image, ports, volumes, environment variables, and everything else about how that container should run.
>
> `networks:` is where you define custom networks. You assign services to networks to control which containers can communicate with each other. If you skip this section, Compose automatically creates a default network and all services can talk to each other by name.
>
> `volumes:` is where you declare named volumes. Any named volume referenced by a service must be declared here. Docker creates it automatically if it does not exist.
>
> A minimal example:
> ```yaml
> services:
>   web:
>     image: nginx:alpine
>     ports:
>       - '8080:80'
>   database:
>     image: postgres:15
>     volumes:
>       - pg-data:/var/lib/postgresql/data
>     environment:
>       POSTGRES_PASSWORD: secret
>
> volumes:
>   pg-data:
> ```
>
> Run it with `docker compose up -d` and both services start. Compose creates a shared network automatically so `web` can reach `database` using the name `database`."

### Q3. What is the difference between `docker compose up` and `docker compose start`?

**How the interviewer asks it:**
> "What is the difference between `up`, `start`, and `run` in Docker Compose?"

**Your Answer:**

> "These three do different things and it is easy to confuse them.
>
> `docker compose up` is the most common. It creates AND starts all services. If the containers do not exist yet, it creates them. If images need to be pulled or built, it does that too. This is the command you run to bring your entire application online from scratch. With `-d` it runs in the background.
>
> `docker compose start` only starts containers that already EXIST but are currently stopped. It does not create new containers. You would use this after `docker compose stop` — which stops containers without removing them.
>
> `docker compose run` creates a NEW container for ONE service and runs a command in it. It is for one-off tasks — like running database migrations, or opening a shell to debug. You almost always add `--rm` so the container is deleted when the command finishes:
> ```bash
> docker compose run --rm backend python manage.py migrate
> ```
>
> In my daily workflow I use `up -d` to start, `down` to stop and clean up, and `run --rm` for one-off administrative tasks."

### Q4. How do you handle environment variables in Docker Compose?

**How the interviewer asks it:**
> "How do you pass configuration to containers in a Compose file? How do you avoid committing passwords to Git?"

**Your Answer:**

> "There are three ways to pass environment variables in Compose.
>
> First, inline in the Compose file directly:
> ```yaml
> environment:
>   NODE_ENV: production
>   PORT: '3000'
> ```
> Simple but you cannot put passwords here if the file is in a public Git repository.
>
> Second, using an env_file:
> ```yaml
> env_file:
>   - .env
> ```
> You create a `.env` file with `KEY=VALUE` lines. This file stays off Git — you add `.env` to `.gitignore`. The compose file itself is safe to commit because it contains no secrets.
>
> Third, Compose automatically reads a `.env` file in the same directory for variable substitution in the compose file itself:
> ```yaml
> image: postgres:${POSTGRES_VERSION}
> ```
> The value comes from your `.env` file or your shell environment.
>
> In production, I never put real credentials in the Compose file. I use environment-specific `.env` files that exist on each server but never in the repository. For serious production workloads, I use proper secret management — AWS Secrets Manager, HashiCorp Vault, or Kubernetes secrets — and inject values at runtime."

### Q5. What does `docker compose down` do vs `docker compose stop`?

**How the interviewer asks it:**
> "What is the safest way to stop a Compose application without losing data?"

**Your Answer:**

> "`docker compose stop` stops all running containers but keeps them. The containers still exist — just not running. You can see them with `docker compose ps`. You restart them with `docker compose start`. Volumes are untouched.
>
> `docker compose down` stops containers AND removes them AND removes the networks Compose created. It is a fuller cleanup. But importantly, named volumes are NOT removed by default. Your data is safe.
>
> `docker compose down -v` is the dangerous one. The `-v` flag removes named volumes too. All your database data, uploaded files, everything in volumes — gone permanently.
>
> My rule: use `docker compose down` for normal stopping. Only use `docker compose down -v` when you explicitly want to wipe all data and start fresh — for example, in CI pipelines where you want a clean environment for each test run.
>
> Never run `docker compose down -v` on a production server without first taking a backup of your volumes."

### Q6. How does `depends_on` work? What are its limitations?

**How the interviewer asks it:**
> "My backend crashes on startup because the database is not ready. I added `depends_on` but it still crashes. Why?"

**Your Answer:**

> "This is one of the most common Compose misunderstandings. `depends_on` by default only guarantees that the CONTAINER has started — not that the service inside the container is ready to accept connections.
>
> PostgreSQL for example takes several seconds to initialize its data files, run startup scripts, and begin accepting TCP connections. Even though the postgres container starts in milliseconds, PostgreSQL itself might take 5-30 seconds. Your backend starts, tries to connect, gets 'connection refused', and crashes.
>
> The correct solution is `depends_on` with `condition: service_healthy`:
> ```yaml
> services:
>   backend:
>     depends_on:
>       database:
>         condition: service_healthy
>
>   database:
>     image: postgres:15
>     healthcheck:
>       test: ['CMD-SHELL', 'pg_isready -U postgres']
>       interval: 5s
>       timeout: 5s
>       retries: 5
>       start_period: 10s
> ```
>
> Now Compose waits until `database` passes its healthcheck before starting `backend`. The `pg_isready` command returns success only when PostgreSQL is actually accepting connections — not just when the container started.
>
> There is a second limitation: even with health checks, your application should implement retry logic for database connections. In production, connections can drop for many reasons — network blip, database restart for backup, failover. A well-designed service retries the connection with exponential backoff rather than crashing."

### Q7. How do networking work in Docker Compose?

**How the interviewer asks it:**
> "If I have two services in a Compose file, how do they communicate with each other?"

**Your Answer:**

> "When you run `docker compose up`, Compose automatically creates a default bridge network and connects all services to it. Every service can reach every other service using the service name as the hostname — Docker's embedded DNS handles the resolution.
>
> So if I have services named `frontend`, `backend`, and `database`, the backend can connect to the database using `postgresql://database:5432/mydb`. No IP addresses. No extra configuration. It just works.
>
> But sometimes you want isolation. Maybe you do not want the frontend to have any network path to the database — only the backend should reach it. For this you create custom networks:
>
> ```yaml
> services:
>   frontend:
>     networks: [public]
>
>   backend:
>     networks: [public, private]    # can reach both frontend and database
>
>   database:
>     networks: [private]            # only reachable by backend
>
> networks:
>   public:
>     driver: bridge
>   private:
>     driver: bridge
> ```
>
> Now if the frontend container is compromised, the attacker has no network path to the database at all. The isolation is enforced at the kernel networking level.
>
> This is the pattern I used in our banking project. Every microservice only had network access to the services it actually needed — nothing more."

### Q8. What is a healthcheck in Docker Compose and how does it work with `depends_on`?

**How the interviewer asks it:**
> "Explain how you would ensure services start in the right order AND that each service is actually ready before dependent services start."

**Your Answer:**

> "The combination of healthcheck and depends_on with condition is the proper solution to ordered startup.
>
> A healthcheck is a command that Compose runs periodically inside a container. If the command succeeds (exit code 0), the service is healthy. If it fails multiple times in a row (up to the `retries` limit), the service is unhealthy.
>
> The three states a service goes through: `starting` during the `start_period` grace window, `healthy` when the check passes, and `unhealthy` when it fails too many times.
>
> You configure it like this:
> ```yaml
> database:
>   image: postgres:15
>   healthcheck:
>     test: ['CMD-SHELL', 'pg_isready -U postgres -d mydb']
>     interval: 10s       # run every 10 seconds
>     timeout: 5s         # fail if check takes more than 5 seconds
>     retries: 5          # must fail 5 consecutive times to be unhealthy
>     start_period: 30s   # do not count failures in the first 30 seconds
> ```
>
> Then any dependent service uses `condition: service_healthy`:
> ```yaml
> backend:
>   depends_on:
>     database:
>       condition: service_healthy
> ```
>
> Compose will literally pause and wait before starting `backend` until `database` reports healthy. If `database` never becomes healthy, `backend` never starts and you see a clear error message.
>
> For the healthcheck test command, I choose the right tool for each service: `pg_isready` for PostgreSQL, `redis-cli ping` for Redis, `curl -f http://localhost/health` for HTTP services, `mysqladmin ping` for MySQL."

### Q9. What is the difference between `docker compose run` and `docker compose exec`?

**How the interviewer asks it:**
> "How do I run a one-off command or get a shell inside a running container in Compose?"

**Your Answer:**

> "They look similar but work on different things.
>
> `docker compose exec service_name command` runs a command in a CURRENTLY RUNNING container. The container must already be up. It is like `docker exec` but uses the service name instead of the container ID:
> ```bash
> docker compose exec database psql -U postgres  # connect to running database
> docker compose exec backend sh                 # shell into running backend
> ```
>
> `docker compose run service_name command` creates a NEW container from the service's image and runs the command in it. The service does not need to be running. When the command finishes, the container stops (and is deleted if you add `--rm`):
> ```bash
> docker compose run --rm backend python manage.py migrate   # run migrations
> docker compose run --rm backend sh                         # debug shell
> ```
>
> The `run` container inherits the service's volumes, networks, and environment — so it has database access and everything the main service would have.
>
> I use `exec` for interacting with already-running services — inspecting logs, checking database state, debugging a live issue. I use `run --rm` for administrative tasks that should happen before or after the main service — database migrations, seed data, one-time setup scripts."

### Q10. How do you use Docker Compose in a CI/CD pipeline?

**How the interviewer asks it:**
> "Describe how you would use Docker Compose in your CI/CD setup."

**Your Answer:**

> "Compose is very useful in CI for spinning up the full application stack for integration tests. Here is a pattern I used:
>
> We had a `docker-compose.test.yml` file specifically for CI:
> ```yaml
> services:
>   database:
>     image: postgres:15-alpine
>     environment:
>       POSTGRES_PASSWORD: testpassword
>     healthcheck:
>       test: ['CMD-SHELL', 'pg_isready -U postgres']
>       interval: 2s
>       retries: 10
>
>   app:
>     build: .
>     depends_on:
>       database:
>         condition: service_healthy
>     environment:
>       DATABASE_URL: postgresql://postgres:testpassword@database/testdb
>       NODE_ENV: test
>
>   tests:
>     build:
>       context: .
>       dockerfile: Dockerfile.test
>     depends_on:
>       app:
>         condition: service_healthy
>     command: npm run test:integration
> ```
>
> In the CI pipeline (GitHub Actions, Jenkins, etc.):
> ```bash
> # Start the full stack
> docker compose -f docker-compose.test.yml up -d
>
> # Wait for all services to be healthy (handled by depends_on)
>
> # Run tests
> docker compose -f docker-compose.test.yml run --rm tests
>
> # Capture exit code to determine pass/fail
> TEST_EXIT=$?
>
> # Clean up everything
> docker compose -f docker-compose.test.yml down -v
>
> # Exit with test result
> exit $TEST_EXIT
> ```
>
> Key points: I always use `down -v` in CI to wipe data between runs. I use healthchecks with tight intervals (2s) for fast CI feedback. And I use a separate Compose file for CI to avoid any conflict with development configuration."

### Q11. How do you manage secrets in Docker Compose for production?

**How the interviewer asks it:**
> "My Compose file has database passwords in environment variables. Is this secure? What should I do instead?"

**Your Answer:**

> "Having secrets directly in environment variables or `.env` files is acceptable for development but not for production. The problems are:
>
> Environment variables are visible to anyone who can run `docker inspect`, `docker compose exec env`, or access the process table. They can also show up in logs if an application accidentally prints its full environment.
>
> For production, here are the better options in increasing order of security:
>
> **Level 1 — .env file on the server (minimum):**
> Keep the `.env` file on the production server with strict permissions (`chmod 600 .env`, owned by root). Never in the repository. Better than nothing but still shows up in `docker inspect`.
>
> **Level 2 — Docker Swarm secrets:**
> If using Swarm mode, Docker has a proper secrets system. Secrets are encrypted at rest and in transit, and mounted as files inside the container (not environment variables):
> ```yaml
> secrets:
>   db_password:
>     external: true   # was created with: docker secret create db_password -
>
> services:
>   database:
>     secrets:
>       - db_password
>     # accessed at /run/secrets/db_password inside container
> ```
>
> **Level 3 — External secret management (proper production):**
> Use AWS Secrets Manager, HashiCorp Vault, or Azure Key Vault. Your containers fetch secrets at startup from these systems. The Compose file contains no credentials at all. If the Compose file is leaked, nothing is exposed.
>
> In my banking project, we used AWS Secrets Manager. The container startup script called the AWS API to fetch the database password and injected it as an environment variable just for that process. No credentials in any file on disk."

### Q12. How do you handle database migrations in a Compose setup?

**How the interviewer asks it:**
> "Your application needs to run database migrations before the app starts. How do you handle this with Docker Compose?"

**Your Answer:**

> "This is a real operational challenge and there are a few approaches.
>
> **Approach 1 — Separate migration service:**
> ```yaml
> services:
>   migrate:
>     image: myapp:latest
>     depends_on:
>       database:
>         condition: service_healthy
>     command: python manage.py migrate
>     restart: 'no'   # run once and exit
>
>   app:
>     image: myapp:latest
>     depends_on:
>       migrate:
>         condition: service_completed_successfully  # wait until migrate exits 0
>       database:
>         condition: service_healthy
> ```
>
> `condition: service_completed_successfully` means wait until the `migrate` container exits with code 0. If migration fails (non-zero exit), `app` never starts and you see the failure clearly.
>
> **Approach 2 — Entrypoint script:**
> The application entrypoint script runs migrations before starting the app:
> ```bash
> #!/bin/sh
> # docker-entrypoint.sh
> echo 'Running migrations...'
> python manage.py migrate
> echo 'Starting application...'
> exec python manage.py runserver 0.0.0.0:8000
> ```
>
> Simpler but migrations run every time the container restarts — which is usually fine for idempotent migration systems.
>
> **Approach 3 — Manual step:**
> For production, I often run migrations as an explicit step before deploying:
> ```bash
> docker compose run --rm app python manage.py migrate
> docker compose up -d
> ```
> This gives the most control and visibility. You see the migration output before the main app starts.
>
> In practice I use approach 3 for production (explicit control) and approach 2 for development (convenience)."

### Q13. "My container keeps restarting. How do you debug this in a Compose setup?"

**Your Answer:**

> "A container in a restart loop is usually crashing on startup. Here is my debugging process:
>
> **Step 1 — See what is happening:**
> ```bash
> docker compose ps
> # Look for restart count or 'Restarting' status
> ```
>
> **Step 2 — Read the logs:**
> ```bash
> docker compose logs webapp
> # Look for error messages near the bottom — that is where the crash reason is
>
> # If it is restarting fast, add --tail to see recent output
> docker compose logs --tail 50 webapp
> ```
>
> **Step 3 — Check the exit code:**
> ```bash
> docker inspect compose-project-webapp-1 | jq '.[0].State'
> # ExitCode tells you how it crashed
> # 0 = exited cleanly (maybe a task container that finished)
> # 1 = application error
> # 137 = OOM killed (needs more memory)
> # 139 = segfault
> ```
>
> **Step 4 — Temporarily disable restart and debug manually:**
> ```yaml
> # Change restart to 'no' temporarily
> restart: 'no'
> ```
> Then `docker compose up` and see the crash without the loop. Or run a shell:
> ```bash
> docker compose run --rm webapp sh
> # Inside: manually run the startup command and see what fails
> ```
>
> **Most common causes:**
> - Missing environment variable (app crashes with undefined variable error)
> - Cannot reach database (connection refused — check depends_on + healthcheck)
> - Missing file or wrong path
> - Permission denied on a volume mount
> - OOMKilled — needs more memory (check with `docker stats`)"

### Q14. "How do you update a service in Docker Compose without downtime?"

**Your Answer:**

> "True zero-downtime with Docker Compose on a single machine is limited — Compose was not designed for zero-downtime deployments. But there are approaches that minimise downtime.
>
> **Approach 1 — Pull and recreate one at a time:**
> ```bash
> # Pull new image
> docker compose pull webapp
>
> # Recreate just that service (stops old, starts new)
> docker compose up -d --no-deps webapp
> ```
> `--no-deps` = do not recreate dependent services, only recreate `webapp`
> Brief downtime during the container swap — usually 1-5 seconds.
>
> **Approach 2 — Scale up before scale down:**
> ```bash
> # Scale up to 2 copies
> docker compose up -d --scale webapp=2
>
> # Update the image and rolling recreate (manual)
> docker compose pull webapp
>
> # Scale back down
> docker compose up -d --scale webapp=1
> ```
>
> **Approach 3 — Use Nginx as a proxy with two backends:**
> Run two copies of your app on different ports with nginx in front. Update one, verify it works, then shift traffic.
>
> **The honest answer for interviews:**
> Docker Compose is for development and simple single-machine deployments. For true zero-downtime production deployments with health checks, rolling updates, and automatic rollback — you use Kubernetes. Kubernetes has rolling update strategy built-in at the core. This is one of the primary reasons companies move from Compose to Kubernetes as they scale."

### Q15. "A developer changed something in docker-compose.yml but the containers did not update when they ran `docker compose up`. Why?"

**Your Answer:**

> "`docker compose up` is smart — it compares what is running against what is in the Compose file. If a container is already running and its configuration has not changed, Compose does NOT recreate it. It prints 'Service is up-to-date' and moves on.
>
> Common reasons the change did not take effect:
>
> **Reason 1 — Configuration change needs container recreation:**
> Most configuration changes (environment variables, ports, volumes) require the container to be removed and recreated. Adding `--force-recreate` solves this:
> ```bash
> docker compose up -d --force-recreate
> ```
>
> **Reason 2 — Image was changed but not rebuilt:**
> If using `build:` and the Dockerfile or source changed, you need:
> ```bash
> docker compose up -d --build
> ```
>
> **Reason 3 — Image tag is the same but content changed:**
> If you use `image: myapp:latest` and pushed a new version with the same `latest` tag, you need to pull first:
> ```bash
> docker compose pull
> docker compose up -d
> ```
>
> **Reason 4 — Not running from the right directory:**
> Compose looks for `docker-compose.yml` in the current directory. If you are in a different directory, it may use a cached or different compose file.
>
> My workflow when something seems stuck:
> ```bash
> # Nuclear option — stop everything, force rebuild, restart
> docker compose down
> docker compose up -d --build --force-recreate
> ```"

## Rapid Fire Round

| Question | Answer |
|----------|--------|
| What command starts all Compose services? | `docker compose up -d` |
| What command stops and removes Compose containers? | `docker compose down` |
| What command also removes volumes? | `docker compose down -v` |
| How do you rebuild images before starting? | `docker compose up -d --build` |
| How to follow logs of one service? | `docker compose logs -f servicename` |
| How to shell into a running service? | `docker compose exec servicename sh` |
| How to run a one-off command? | `docker compose run --rm servicename command` |
| What does `depends_on` guarantee by default? | Container has started — NOT that the service is ready |
| What condition waits for service to be ready? | `condition: service_healthy` (requires healthcheck) |
| What is a Compose profile? | A label on a service — only starts when that profile is enabled |
| New command syntax vs old? | `docker compose` (space) — old was `docker-compose` (hyphen) |
| Where does Compose read variables from automatically? | `.env` file in the same directory |
| How do you use a variable from .env in the Compose file? | `${VARIABLE_NAME}` |
| What does `restart: unless-stopped` mean? | Always restart except if you manually stopped it |
| What does `docker compose config` do? | Validates the file and shows the final composed config |
| Can Compose do multi-machine deployments? | No — use Docker Swarm or Kubernetes for that |

## Phrases That Show Senior-Level Thinking

- *"I always use `condition: service_healthy` with `depends_on` rather than just listing the service. Just listing it only guarantees the container started, not that the database is accepting connections."*

- *"In CI/CD, I use `docker compose down -v` after every test run to ensure a clean environment. The `-v` removes volumes so the next run starts with a fresh database."*

- *"I never put real credentials in `docker-compose.yml`. Secrets go in `.env` which is in `.gitignore`, or better, in AWS Secrets Manager injected at runtime."*

- *"For development I use bind mounts for source code so I can edit files on my machine and see changes instantly without rebuilding. For production I use named volumes for data and always build the image cleanly."*

- *"Compose is great for local development and simple deployments. When we needed zero-downtime rolling updates, automatic scaling, and self-healing — we moved to Kubernetes. Those features are not what Compose was built for."*

- *"When debugging a crashed container, my first step is always `docker compose logs servicename`. The crash reason is almost always in the last few lines."*

- *"I separate my compose files — `docker-compose.yml` for production, `docker-compose.override.yml` for development overrides. Compose automatically merges them. This way the base file works in both environments."*
