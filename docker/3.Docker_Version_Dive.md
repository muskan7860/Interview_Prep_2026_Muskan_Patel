## 1. Why Does This Command Even Exist?

### The Problem It Solves

Imagine you are a DevOps engineer.
Something is broken in production.
A colleague asks you: "Which version of Docker are you running?"

If you do not know the version, you cannot:
- Search for known bugs in that version
- Check if a feature you need is available in that version
- Report the issue correctly to your team or to Docker support
- Confirm that your local machine matches the production server

`docker version` gives you all of this information in one command.

### What This Command Actually Does

When you type `docker version`:

1. The Docker CLI (the program you type commands into) wakes up
2. It connects to the Docker Server running in the background
3. It asks the Server: "What version are you? What are your components?"
4. The Server replies with all its version information
5. The CLI combines its OWN version info + the Server's reply
6. It prints everything on your screen

That is why you see TWO sections — **Client** and **Server**.

## 2. What is a Client? What is a Server?

### Start From Zero — What Do These Words Mean?

You have heard these words before. But let us understand them properly in the Docker context.

---

### What is a Server?

A **server** is a program that:
- Runs in the **background** all the time
- **Waits** for someone to send it a request
- **Does the actual work** when a request arrives
- **Sends back** the result

Think of a server like a **bank employee** sitting at their desk.
They do not come to you.
You go to them.
They wait for your request.
They do the work.
They give you the result.

In Docker, the server is called **`dockerd`** (Docker Daemon).

**What is a Daemon?**
A daemon is just a program that runs silently in the background.
You cannot see it on your screen.
It is always there, always running, waiting for instructions.

On your Ubuntu machine, `dockerd` starts automatically when your computer boots.
It keeps running all day and night.
It is always ready to receive Docker commands.

---

### What is a Client?

A **client** is a program that:
- You interact with **directly**
- Sends your request **to the server**
- Receives the result **from the server**
- Shows you the result

Think of a client like **you walking into the bank**.
You are the client.
You talk to the bank employee (server).
You get your result.
You leave.

In Docker, the client is the **`docker`** command.

When you open your terminal and type `docker run nginx` — you are using the Docker Client.

---

### The Critical Insight — They Are TWO Separate Programs

This surprises many beginners.

`docker` (client) and `dockerd` (server) are **two completely separate programs**.

You can see both of them on your machine:

```bash
# Find the docker client binary
which docker
# Output: /usr/bin/docker
# This is the CLI program you type commands with

# Find the dockerd server binary
which dockerd
# Output: /usr/bin/dockerd
# This is the background daemon doing all the real work
```

They just happen to be installed together when you install Docker.

---

### How Do Client and Server Talk to Each Other?

They talk through a **socket file** called `/var/run/docker.sock`

Let us break down this path completely:

**`/var`**
This is a folder on your Linux system.
`var` stands for "variable" — meaning data that changes over time.
This folder holds data that programs create while they are running.
Examples: log files, lock files, runtime files.

**`/var/run`**
A folder inside `/var/`.
`run` = runtime.
This folder holds files that programs create when they START running and delete when they STOP.
These files exist only while the programs are running.

**`/var/run/docker.sock`**
This is the **socket file** that `dockerd` creates when it starts.

**What is a socket?**
A socket is not a normal file.
It looks like a file on your filesystem, but it is actually a **communication channel** — like a pipe between two programs.

Think of it as a **letter drop box** in a door:
- `dockerd` is the person inside the room, waiting at the drop box
- `docker` CLI is the postman outside, putting letters (commands) in the drop box
- `dockerd` picks up the letter, does the work, puts the reply back
- `docker` CLI picks up the reply and shows you the result

When `dockerd` stops running, the socket file disappears.
When `dockerd` starts again, the socket file is created again.

**That is why if you see this error:**
```
Cannot connect to the Docker daemon at unix:///var/run/docker.sock.
Is the docker daemon running?
```
It means `dockerd` is not running. The socket file does not exist. Client cannot communicate.

### THE CLIENT SECTION

---

#### `Client:`

This heading means: everything below it describes the **Docker CLI** — the program you type commands into in your terminal.

---

#### `Version: 29.1.3`

This is the **version number** of the Docker CLI installed on your Ubuntu machine.

Version numbers follow a pattern called **Semantic Versioning**:

```
29  .  1  .  3
│      │     │
│      │     └── Patch version
│      │         Small bug fixes. No new features. No breaking changes.
│      │         Example: fixed a typo in error message
│      │
│      └── Minor version
│          New features added. Still backward compatible.
│          Example: added a new docker command
│
└── Major version
    Big changes. May break older behaviour.
    Example: completely redesigned networking
```

**29.1.3** means:
- Major version 29 (Docker has had many major releases over the years)
- Minor version 1 (first minor release in the 29.x series)
- Patch version 3 (third bug fix patch)

This is a recent version. Docker 29 is a 2026 release.

---

#### `API version: 1.52`

**API** = Application Programming Interface

What is an API in simple terms?

When the Docker Client wants to tell the Docker Server "please run this container", it cannot just shout it.
They need to speak in a **structured, agreed format**.

This agreed format is called an API.

Think of it like an **official order form** at a government office.
You cannot just write your request any way you want.
You must fill in the specific boxes on the official form.
The office only accepts requests in that specific format.

The Docker API works the same way.
The Client sends requests to the Server in a specific format.
The Server only understands requests in that format.

**API version 1.52** means both Client and Server are using version 1.52 of this format.

Why does the version of the API matter?
Each new Docker release may add new API features.
If your Client uses API version 1.52 but your Server only understands up to 1.44 — some features will not work.
Keeping Client and Server at the same version avoids this problem.

---

#### `Go version: go1.24.4`

**Go** (also called Golang) is a programming language.
It was created by Google in 2009.
Docker is written entirely in Go.

**go1.24.4** is the version of the Go compiler that was used to **build** the Docker CLI binary.

Think of it like this:
Go is the language.
The Go compiler is the tool that converts Go source code into a program your computer can run.
go1.24.4 = version 1.24.4 of that compiler was used.

Why do you care about this?
In daily Docker use, you mostly do not.
But it matters when:
- Reporting a bug — developers need to know which Go version was used
- Security patches — sometimes Go itself has security fixes
- Performance — newer Go versions often make programs faster

---

#### `Git commit: 29.1.3-0ubuntu3~24.04.2`

Let us break this down carefully because there is a lot of information here.

**What is Git?**
Git is a tool that developers use to track every change they make to their code.
Every time a developer saves a meaningful change, Git creates a record called a **commit**.
Each commit has a unique ID.

**What is a Git commit ID in this context?**
This tells you the **exact snapshot of source code** that was used to build your Docker binary.

Now let us decode: `29.1.3-0ubuntu3~24.04.2`

```
29.1.3          = Docker version (same as Version field above)
-               = separator
0ubuntu3        = Ubuntu made 3 small changes to Docker's original source code
                  before packaging it for Ubuntu users
~               = separator used in Debian/Ubuntu packaging
24.04           = this package is built for Ubuntu 24.04 (your Ubuntu version)
.2              = second revision of this package for Ubuntu 24.04
```

**The key insight here:**
Your Docker was NOT installed directly from Docker's official website.
It was installed from **Ubuntu's own package repository**.

Ubuntu takes Docker's source code, makes small adjustments for Ubuntu compatibility, packages it, and puts it in their repository.

This is why you see `0ubuntu3` — Ubuntu's own packaging fingerprint.

If you had installed from Docker's official repository, this would just show a short hash like `abc123d`.

**Is Ubuntu's package worse?**
Not really. It is just packaged differently.
Ubuntu ensures it works well with Ubuntu 24.04 specifically.
The trade-off: Ubuntu's packages sometimes lag behind Docker's official releases by a few weeks.

---

#### `Built: Wed Apr 29 16:41:06 2026`

The **exact date and time** this Docker CLI binary was compiled.

April 29, 2026 at 16:41:06 (UTC time).

This tells you how recent your Docker installation is.
Your installation is very recent — built in 2026.

---

#### `OS/Arch: linux/amd64`

This tells you what kind of computer this Docker CLI was built to run on.

**OS** = Operating System

**linux** = your machine runs Linux (Ubuntu is a Linux distribution).

**Arch** = Architecture = the type of CPU your computer has.

**amd64** = 64-bit x86 processor architecture.

Let us understand amd64 properly:

In the 1990s, AMD (a chip company) created an extension to the 32-bit x86 processor that made it 64-bit.
They called it AMD64.
Intel later adopted the same design.
Now all modern Intel and AMD laptop/desktop/server processors use this architecture.
It is called amd64 or x86_64.

Your ThinkPad L14 has an Intel or AMD processor.
That processor is amd64 architecture.
So this Docker CLI binary is the right one for your machine.

The other common architecture you will encounter:
- **arm64** = used in Apple M1/M2/M3 MacBooks, AWS Graviton EC2 instances, Raspberry Pi

This matters in Docker because:
- A Docker image built for amd64 will NOT run on arm64 (and vice versa)
- Unless you use multi-architecture images (which have both inside)

---

#### `Context: default`

**What is a Context in Docker?**

A Docker Context is a saved profile that tells the Docker CLI:
"When I run a command, which Docker Server should I connect to?"

By default there is one context called **`default`**.

`default` means: connect to the Docker Server on **this local machine** through `/var/run/docker.sock`.

**When would you use a different context?**

Imagine you are a DevOps engineer managing Docker on 5 different servers:
- dev-server (IP: 10.0.0.1)
- staging-server (IP: 10.0.0.2)
- prod-server (IP: 10.0.0.3)

Instead of SSH-ing into each server just to run Docker commands,
you can create contexts on your local machine:

```bash
# Create a context for the dev server
docker context create dev-server \
  --docker "host=ssh://ubuntu@10.0.0.1"

# Switch to that context
docker context use dev-server

# Now ALL docker commands go to the dev server
docker ps          # shows containers on dev-server, not your local machine
docker images      # shows images on dev-server

# Switch back to local
docker context use default
```

For now, you are just working locally. `default` is correct and expected.

### THE SERVER SECTION

---

#### `Server:`

Everything below this heading describes the **Docker Server** — the `dockerd` daemon running in the background on your Ubuntu machine.

---

#### `Engine:`

**Engine** is the official name for the Docker Server component.
The full name is **Docker Engine**.

It includes:
- `dockerd` — the main daemon process
- containerd — the container runtime
- runc — the low-level OCI runtime

---

#### `Version: 29.1.3`

The version of the Docker Engine (Server).

Notice: **Client is 29.1.3 and Server is 29.1.3**.
They are the same version.

This is the ideal situation.
When Client and Server versions match, everything works smoothly.
No compatibility issues.

---

#### `API version: 1.52 (minimum version 1.44)`

The Server speaks API version **1.52**.

**minimum version 1.44** — this is a backward compatibility guarantee.

It means: the Server can also communicate with older Docker Clients, as long as those clients use at least API version 1.44.

Why does this matter?

In real companies, you might have:
- Developers using Docker 25 on their laptops (older, uses API 1.47)
- Production servers running Docker 29 (newer, uses API 1.52)

The Server says: "I speak 1.52, but I can also understand 1.44 and above."
So Docker 25 clients (API 1.47) can still talk to Docker 29 servers. No problem.

This backward compatibility prevents breaking things when you upgrade one side but not the other.

#### `Git commit: 29.1.3-0ubuntu3~24.04.2`
#### `Built: Wed Apr 29 16:41:06 2026`
#### `OS/Arch: linux/amd64`

Same meanings as the Client section.

The fact that Client and Server have identical values for these fields confirms they were built from the exact same source code at the exact same time.
This makes sense since Ubuntu packages them together.

#### `Experimental: false`

Docker sometimes adds new features that are **not yet stable**.
These are called **experimental features**.

They are turned OFF by default because:
- They might have bugs
- Their behaviour might change in future versions
- They are not recommended for production use

**false** means experimental features are disabled.
This is the correct and expected setting for a production or learning environment.

If you ever needed experimental features (for example, some advanced BuildKit features), you would enable them by editing Docker's config file:

```bash
# Location of Docker daemon config
/etc/docker/daemon.json

# To enable experimental features:
{
  "experimental": true
}
```

But for everything you need — learning, interviews, projects — `false` is perfectly fine.

---

#### `containerd:`
#### `Version: 2.2.1`

**containerd** is the component that sits between `dockerd` and `runc`.

Remember the hierarchy:
```
dockerd (manages everything at high level)
  └── containerd (manages container lifecycle)
        └── runc (talks to Linux kernel)
```

containerd is responsible for:
- Creating and deleting containers
- Managing image storage (pulling, storing layers)
- Managing container snapshots (the OverlayFS layer data)

**Version 2.2.1** is the version of containerd installed.

containerd is developed separately from Docker by the **CNCF** (Cloud Native Computing Foundation) — the same organisation that manages Kubernetes.

This is why you see a separate version number (2.2.1) instead of 29.1.3.
containerd has its own release cycle independent of Docker.

**Why does Kubernetes matter here?**
Kubernetes (since version 1.24) talks directly to containerd without going through `dockerd`.
So containerd is not just a Docker component — it is the industry-standard container runtime used by both Docker AND Kubernetes.

---

#### `GitCommit:` (blank)

For containerd and runc, the GitCommit field is empty.

This is normal and expected for Ubuntu-packaged software.

When Ubuntu takes the source code and packages it, they strip out the git commit hash.
The version number (2.2.1) is enough to identify exactly which version you have.

---

#### `runc:`
#### `Version: 1.3.4-0ubuntu1~24.04.1`

**runc** is the lowest-level component. It does the actual work of creating containers.

When you run `docker run nginx`, the final step deep inside the chain is runc doing this:

```
runc calls Linux kernel:
  → create PID namespace (container gets its own process list)
  → create network namespace (container gets its own network)
  → create mount namespace (container gets its own filesystem view)
  → apply cgroup limits (memory cap, CPU cap)
  → mount OverlayFS (image layers become the container's filesystem)
  → exec nginx (start the actual nginx process)
  → runc exits (its job is done)
```

**Version: 1.3.4-0ubuntu1~24.04.1**

Decoding this the same way as before:
```
1.3.4      = runc version 1.3.4
-          = separator
0ubuntu1   = Ubuntu made 1 small change when packaging
~24.04.1   = packaged for Ubuntu 24.04, revision 1
```

runc is also a CNCF project, developed separately from Docker.
It implements the **OCI Runtime Specification**.

**What is OCI?**
OCI = Open Container Initiative.
It is an industry standard that defines exactly how containers should be created and run.
runc is the reference implementation — the official example program that follows the OCI standard perfectly.

Because runc follows OCI standard, any other OCI-compliant tool can replace it.
For example:
- **crun** = a faster alternative to runc written in C
- **kata-containers** = runs each container in a lightweight VM for stronger isolation
- **gVisor** = runs containers with a special kernel sandbox for security

---

#### `docker-init:`
#### `Version: 0.19.0`

**docker-init** is actually a program called **tini**.

To understand why it exists, you need to understand one Linux concept.

**What is PID 1?**

In Linux, every process (running program) has a number called a PID (Process ID).

When Linux boots, the very first process that starts is the init system (like systemd on Ubuntu).
That process always gets **PID 1**.

PID 1 has special responsibilities:
1. Handle signals (SIGTERM = please stop, SIGKILL = stop immediately)
2. **Reap zombie processes** (clean up dead child processes)

**What is a zombie process?**
When a child process finishes, it sends a "I am done" signal to its parent.
The parent must acknowledge this and clean up.
If the parent never acknowledges, the dead child stays in the process table as a zombie — using up a slot even though it is dead.

PID 1 must handle all of this.

**The Container Problem:**

When you run `docker run nginx`, nginx becomes PID 1 inside the container.
But nginx was not designed to be an init system.
nginx does not properly handle all signals.
nginx does not reap zombie processes.

This causes problems:
- `docker stop` sends SIGTERM to PID 1 (nginx). nginx might not handle it cleanly. Docker waits 10 seconds, then sends SIGKILL (force kill). Your app gets no chance for graceful shutdown.
- If nginx spawns child processes that die, they become zombie processes because nginx (as PID 1) is not cleaning them up.

**The tini / docker-init Solution:**

`tini` (tiny init) is a minimal init system designed for containers.
It is tiny — less than 1MB.
It does exactly two things:
1. Properly forwards signals to your app
2. Reaps zombie child processes

When you use it:
```bash
# Use docker-init as PID 1
docker run --init nginx
```

Now the process chain inside the container is:
```
tini (PID 1) → properly handles signals, reaps zombies
  └── nginx (PID 2) → your actual app, receives clean signals
```

`docker-init` is just what Docker calls tini.
**Version: 0.19.0** is the version of tini bundled with your Docker installation.

## 5. Practical Labs — Run These on Your Ubuntu Machine

### Lab 1 — Run `docker version` and Understand the Output

```bash
docker version
```

**What this command does step by step:**

Step 1: Your terminal finds the `docker` binary at `/usr/bin/docker` and runs it.

Step 2: The `docker` binary reads your command: `version`.

Step 3: The `docker` binary opens a connection to `/var/run/docker.sock`.

Step 4: It sends an HTTP GET request: `GET /version HTTP/1.1` to dockerd through the socket.

Step 5: dockerd receives the request, collects version information from itself, containerd, runc, and docker-init.

Step 6: dockerd sends back a JSON response with all the version data.

Step 7: The `docker` CLI formats this JSON into the human-readable output you see.

---

### Lab 2 — Confirm the Socket File Exists

```bash
ls -la /var/run/docker.sock
```

**Breaking down this command:**

`ls` = list. This command lists files and folders.

`-l` = long format. Show details: permissions, owner, size, date.

`-a` = all. Show hidden files too (files starting with `.`).

`-la` = combine both flags. Show all files in long format.

`/var/run/docker.sock` = the specific file we want to inspect.

**Expected output:**
```
srw-rw---- 1 root docker 0 Jun 27 10:00 /var/run/docker.sock
```

**Decoding this output:**

`s` = the first character. `s` means this is a **socket file**, not a regular file.
(Regular files show `-`, directories show `d`, sockets show `s`)

`rw-rw----` = permissions.
First `rw-` = root user can read and write.
Second `rw-` = docker group can read and write.
Final `---` = everyone else has NO access.

`1` = number of hard links (not important here).

`root` = this file is owned by the `root` user.

`docker` = this file belongs to the `docker` group.

`0` = size is 0 bytes. This confirms it is not a real file — real files have size. Sockets have 0 bytes because they are communication channels, not data storage.

`Jun 27 10:00` = when dockerd last started (created the socket).

`/var/run/docker.sock` = the full path.

**Why does this matter?**
If you are in the `docker` group, you can use this socket.
If you are NOT in the `docker` group, you get permission denied when running docker commands.

```bash
# Check which groups your user belongs to
groups
# If you see 'docker' in the list, you can use docker without sudo
# If you do not see 'docker', run this:
sudo usermod -aG docker $USER
# Then log out and log back in for it to take effect
```

### Lab 3 — Confirm dockerd is Running as a System Service

```bash
systemctl status docker
```

**Breaking down this command:**

`systemctl` = a tool to manage system services on Ubuntu/Linux.
Services are programs that run in the background (daemons).

`status` = the sub-command. It means: "tell me the current status of this service."

`docker` = the name of the service we want to check.
(On Ubuntu, dockerd runs as a service named `docker`)

**Expected output:**
```
● docker.service - Docker Application Container Engine
     Loaded: loaded (/lib/systemd/system/docker.service; enabled; vendor preset: enabled)
     Active: active (running) since Wed 2026-06-27 10:00:00 UTC; 2h ago
TriggeredBy: ● docker.socket
       Docs: https://docs.docker.com
   Main PID: 1234 (dockerd)
      Tasks: 15
     Memory: 45.2M
        CPU: 2.341s
     CGroup: /system.slice/docker.service
             └─1234 /usr/bin/dockerd -H fd:// --containerd=/run/containerd/containerd.sock
```

**Decoding this output:**

`● docker.service` = the service name. The green dot means it is running.

`Loaded: loaded` = systemd has loaded the service configuration.

`enabled` = this service will automatically start when Ubuntu boots.

`Active: active (running)` = the service is currently running right now.

`since Wed 2026-06-27 10:00:00 UTC; 2h ago` = it has been running for 2 hours since it started.

`TriggeredBy: ● docker.socket` = dockerd is actually triggered/started by the docker.socket service. This is a feature called socket activation — dockerd starts automatically when something first tries to connect to the socket.

`Main PID: 1234 (dockerd)` = the process ID of dockerd on your system. Your actual number will be different.

`Memory: 45.2M` = dockerd is currently using about 45MB of RAM.

`/usr/bin/dockerd -H fd:// --containerd=/run/containerd/containerd.sock` = the exact command that was used to start dockerd. The `--containerd` flag tells dockerd where to find containerd's own socket.

### Lab 4 — See the JSON Behind `docker version`

The `docker` CLI actually receives JSON data from dockerd and formats it nicely.
You can see the raw JSON like this:

```bash
docker version --format '{{json .}}' | jq .
```

**Breaking down this command:**

`docker version` = the base command.

`--format '{{json .}}'` = instead of the normal pretty output, give me the raw JSON.
`{{json .}}` is a Go template (Docker uses Go templates for formatting output).
`.` means "the entire data object".

`jq` = a tool for reading and formatting JSON data.
`jq .` means "pretty print the JSON with indentation".

### Lab 5 — Find All Docker-Related Processes Running on Your Machine

```bash
ps aux | grep -E 'docker|containerd|runc'
```

**Breaking down this command:**

`ps` = process status. Lists all running processes on your system.

`aux` = three flags combined:
- `a` = show processes from ALL users (not just yours)
- `u` = show in user-oriented format (shows username, CPU%, memory%, etc.)
- `x` = show processes that are NOT attached to a terminal (background daemons)

`|` = pipe. Output of `ps aux` goes into the next command.

`grep` = search tool. Finds lines that match a pattern.

`-E` = use Extended regular expressions (allows the `|` pattern inside grep to mean OR).

`'docker|containerd|runc'` = find lines containing "docker" OR "containerd" OR "runc".

**Expected output:**
```
root      1234  0.0  1.2  dockerd -H fd:// --containerd=...
root      1456  0.0  0.8  containerd --config /var/run/docker/containerd/...
```

This shows you that dockerd and containerd are separate processes with different PIDs.
They are both owned by root.
They are both running in the background right now on your machine.

### Lab 6 — Check Which Version You Installed From (Ubuntu vs Docker Official)

```bash
apt-cache show docker.io 2>/dev/null || apt-cache show docker-ce 2>/dev/null
```

**Breaking down this command:**

`apt-cache` = a tool to query Ubuntu's package information database.

`show` = show detailed information about a package.

`docker.io` = the name of Docker when installed from Ubuntu's repository (your case).

`2>/dev/null` = redirect error output to nowhere.
`2` = file descriptor 2 = stderr (error output).
`>` = redirect.
`/dev/null` = a special file that discards everything written to it.
So if the first package is not found, the error message is silently thrown away.

`||` = OR operator. If the first command fails (package not found), try the second command.

`docker-ce` = the name of Docker when installed from Docker's official repository.
`ce` = Community Edition.

**This tells you:**
If `docker.io` has information → you installed from Ubuntu's repository (your situation).
If `docker-ce` has information → you installed from Docker's official repository.

Both work. The key difference is update frequency:
- `docker.io` (Ubuntu): updated when Ubuntu releases a new package (can be weeks behind)
- `docker-ce` (Docker official): updated as soon as Docker releases a new version

## 6. Why This Matters in Interviews

When an interviewer asks you about `docker version` output, they are testing whether you understand Docker's architecture.

**Common interview questions from this topic:**

---

**Q: What is the difference between the Docker Client and Docker Server?**

> "The Docker Client (`docker`) is the CLI tool I interact with directly. The Docker Server (`dockerd`) is the daemon that runs in the background and does all the actual work. They are two separate programs that communicate through a Unix socket at `/var/run/docker.sock`. This architecture allows the Client and Server to run on different machines — for example, I can manage a remote Docker server from my laptop using Docker contexts."

---

**Q: What is `/var/run/docker.sock` and why is it important?**

> "It is a Unix domain socket — a special file that acts as a communication channel between the Docker CLI and the Docker daemon. It looks like a file on disk but is actually a pipe for sending messages. The CLI sends commands through this socket, and dockerd receives them and executes them. Because it is a file, access is controlled by Linux file permissions — only users in the `docker` group can read and write to it. This is also a security consideration — giving a container access to this socket file effectively gives it root access to the host."

---

**Q: What is containerd and how is it different from dockerd?**

> "dockerd is the high-level Docker Engine that provides the Docker API and manages images, networks, and volumes. containerd is the actual container runtime that sits below dockerd — it manages the container lifecycle (create, start, stop, delete) and image storage. runc sits below containerd and does the lowest-level work of actually talking to the Linux kernel. Since Kubernetes 1.24, Kubernetes talks directly to containerd without going through dockerd, because it only needs the container runtime functionality."

---

**Q: What is docker-init and why would you use it?**

> "docker-init is tini — a tiny init system for containers. When a container starts, the main process becomes PID 1. But most applications are not designed to be PID 1. PID 1 has special responsibilities: handling signals properly and reaping zombie child processes. If your app is PID 1 and does not handle SIGTERM correctly, `docker stop` will wait 10 seconds and then force-kill it, preventing graceful shutdown. Using `docker run --init` puts tini as PID 1, which then starts your app as a child. Tini correctly forwards signals and reaps zombies."

## 7. Quick Revision Cheatsheet

| Field | What It Tells You |
|-------|------------------|
| `Client: Version` | Version of the `docker` CLI you type commands with |
| `Server: Version` | Version of `dockerd` running in the background |
| `API version` | The protocol version Client and Server use to talk |
| `minimum version` | Oldest Client API version the Server can still understand |
| `Go version` | Programming language version used to compile Docker |
| `Git commit` | Exact source code snapshot this binary was built from |
| `Built` | Date and time the binary was compiled |
| `OS/Arch` | Operating system and CPU architecture this binary runs on |
| `Context` | Which Docker Server the CLI is currently connected to |
| `Experimental` | Whether unstable preview features are enabled |
| `containerd` | Container lifecycle manager sitting below dockerd |
| `runc` | Lowest-level runtime that talks directly to Linux kernel |
| `docker-init` | Tini — tiny init system for proper PID 1 signal handling |

| Path | What It Is |
|------|-----------|
| `/usr/bin/docker` | The Docker CLI binary |
| `/usr/bin/dockerd` | The Docker daemon binary |
| `/var/run/docker.sock` | The Unix socket connecting CLI to daemon |
| `/var/lib/docker/` | Where Docker stores all its data (images, containers, volumes) |
| `/etc/docker/daemon.json` | Docker daemon configuration file |
| `/sys/fs/cgroup/` | Where cgroup limits are exposed as readable files |
