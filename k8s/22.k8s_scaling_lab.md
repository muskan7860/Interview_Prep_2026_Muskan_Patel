## 🧠 SECTION 1 — WHY DOES KUBERNETES NEED SCALING? (Story First)

### Forget Kubernetes for 3 minutes — start with a story

Imagine you own a **call center** with customer service agents.

Monday morning — 10 calls per minute. You have 3 agents. Fine.

Friday afternoon — shopping season — 500 calls per minute. Your 3 agents are overwhelmed. Customers wait 30 minutes. They leave. You lose money.

Sunday midnight — 0 calls. Your 3 agents are sitting doing nothing. You are paying them for zero work.

**The perfect solution would be:**
- When calls increase → automatically hire more agents
- When calls decrease → automatically send agents home
- Always have JUST ENOUGH agents for the current load

**This is exactly what Kubernetes Scaling does for your applications.**

```
CALLS PER MINUTE  =  HTTP requests / CPU usage / custom metrics
AGENTS            =  Pods
HIRING MORE       =  Horizontal Pod Autoscaler (HPA) — add more pods
BIGGER DESK       =  Vertical Pod Autoscaler (VPA) — give each pod more CPU/memory
MORE OFFICE SPACE =  Cluster Autoscaler (CA) — add more nodes when nodes are full
```

### The Three Levels of Scaling

```
LEVEL 1: HORIZONTAL POD AUTOSCALER (HPA)
  Scale pods OUT/IN (more pods or fewer pods)
  "I need more workers" → add more pods
  "Traffic dropped" → remove pods
  Works within existing nodes

LEVEL 2: VERTICAL POD AUTOSCALER (VPA)
  Scale pods UP/DOWN (give existing pods more/less CPU and memory)
  "My pod needs a bigger engine" → increase resource limits
  Works within existing nodes

LEVEL 3: CLUSTER AUTOSCALER (CA)
  Scale nodes themselves (add or remove entire machines)
  "No more space for new pods" → add a new node (VM)
  "Nodes are mostly empty" → remove a node to save cost

THEY WORK TOGETHER:
  HPA tries to add pods → no space on nodes → CA adds a node → HPA pods scheduled
```

## ⚙️ SECTION 2 — RESOURCE REQUESTS AND LIMITS (Foundation)

### You MUST understand this before anything else

Before HPA, VPA, and Cluster Autoscaler make sense — you must deeply understand **resource requests and limits**. Everything in Kubernetes scheduling and autoscaling is built on top of this.

### Simple Story — The Office Desk

```
Every pod is like an employee at an office.

REQUESTS = the desk space you RESERVE for this employee
  → "I need a desk that is at least 2 meters wide"
  → The office manager GUARANTEES this space for you
  → Used by SCHEDULER to decide which node the pod goes on

LIMITS = the maximum space this employee can EVER use
  → "You can never take more than 4 meters of total space"
  → The operating system ENFORCES this — cannot exceed it
  → If exceeded: CPU is throttled, Memory causes OOMKill
```

### CPU — How It Works

```
CPU is measured in:
  1 CPU   = 1 vCPU/Core = 1000 millicores
  500m    = 0.5 CPU (half a core)
  100m    = 0.1 CPU (one tenth of a core)
  250m    = 0.25 CPU

CPU REQUEST:
  → Scheduler uses this to find a node with enough free CPU
  → If no node has requested CPU free → pod stays Pending
  → Guaranteed minimum CPU for your pod
  → Even if node is busy → your pod gets at LEAST this much

CPU LIMIT:
  → Maximum CPU the container can use
  → If pod tries to use more → Linux kernel THROTTLES it
  → Throttling = pod runs slower but does NOT crash
  → CPU throttling is invisible to the app — it just runs slow
```

### Memory — How It Works

```
Memory is measured in:
  Mi  = Mebibyte (1Mi = 1,048,576 bytes)
  Gi  = Gibibyte (1Gi = 1,073,741,824 bytes)
  M   = Megabyte (1M = 1,000,000 bytes)
  G   = Gigabyte

MEMORY REQUEST:
  → Same as CPU — Scheduler uses this for node selection
  → Guaranteed minimum memory for your pod

MEMORY LIMIT:
  → Maximum memory the container can use
  → If pod tries to use MORE than limit:
    → Linux kernel sends SIGKILL to the container process
    → Container dies with exit code 137
    → Pod shows: OOMKilled (Out Of Memory Killed)
    → Unlike CPU (which throttles), memory KILLS

MEMORY LIMIT IS HARD. CPU LIMIT IS SOFT.
  CPU over limit → slow down (throttle)
  Memory over limit → die (OOMKill)
```

### Resource YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-pod
spec:
  containers:
  - name: payment-app
    image: payment:1.0
    resources:
      requests:
        cpu: "250m"       # scheduler: find node with 250m free CPU
        memory: "256Mi"   # scheduler: find node with 256Mi free memory
      limits:
        cpu: "500m"       # max CPU — throttle if exceeded
        memory: "512Mi"   # max memory — OOMKill if exceeded
```

**Every line explained:**

```yaml
      requests:
        cpu: "250m"
```
→ `requests` → minimum GUARANTEED resources.
→ `cpu: "250m"` → request 250 millicores = 0.25 of one CPU core.
→ The SCHEDULER reads this: "find a node where at least 250m CPU is not yet requested by other pods."
→ Important: requests are about what is RESERVED, not what is USED.
→ A node can have 1000m CPU total. If pods have requests totaling 1000m → scheduler says node is full, even if pods are only using 100m actually.

```yaml
        memory: "256Mi"
```
→ Request 256 Mebibytes of memory.
→ Scheduler finds a node with 256Mi of unreserved memory.

```yaml
      limits:
        cpu: "500m"
```
→ `limits` → maximum allowed resources.
→ Pod can burst up to 500m CPU when the node has spare capacity.
→ If pod tries to use more than 500m → kernel throttles it.

```yaml
        memory: "512Mi"
```
→ Maximum 512Mi memory.
→ If the process inside tries to allocate more → kernel OOMKills the container.

### Requests vs Limits — The Three Scenarios

```
SCENARIO 1: requests == limits (Guaranteed QoS)
  requests: cpu: 500m, memory: 512Mi
  limits:   cpu: 500m, memory: 512Mi
  → Pod gets EXACTLY this amount, no more, no less
  → Highest priority — last to be evicted under pressure
  → Best for: databases, critical services

SCENARIO 2: requests < limits (Burstable QoS)
  requests: cpu: 250m, memory: 256Mi
  limits:   cpu: 500m, memory: 512Mi
  → Pod gets minimum 250m but can burst to 500m
  → Middle priority — evicted after BestEffort
  → Best for: most applications

SCENARIO 3: No requests or limits (BestEffort QoS)
  requests: (nothing)
  limits:   (nothing)
  → Pod gets whatever is available
  → LOWEST priority — evicted FIRST under memory pressure
  → Pod can be killed anytime the node needs memory
  → NEVER do this in production
```

### QoS Classes — Why They Matter

```
GUARANTEED:  requests == limits for ALL containers
  → Evicted last under node pressure

BURSTABLE:   requests < limits (or only one set)
  → Evicted second under node pressure

BESTEFFORT:  no requests and no limits at all
  → Evicted FIRST under node pressure

When a node runs out of memory:
  Kubernetes evicts BestEffort pods first → then Burstable → then Guaranteed
  This is why always setting requests and limits matters.
```

### The Danger of Wrong Values

```
REQUESTS TOO LOW:
  Scheduler thinks pod is light → schedules too many pods on one node
  At runtime: all pods compete for actual CPU/memory
  Node becomes overloaded → all pods slow down or OOMKill
  This is called OVERCOMMITTING

REQUESTS TOO HIGH:
  Scheduler thinks pod needs a lot → can't find suitable nodes
  Pod stays in Pending (no node has enough "free" resources)
  Even though nodes are mostly idle in actual usage

LIMITS TOO LOW:
  App hits memory limit during normal operation → OOMKill loop
  App hits CPU limit → throttled → slow response times
  CrashLoopBackOff or poor performance

LIMITS TOO HIGH:
  One noisy pod can consume the entire node
  Other pods on that node suffer
```

## 📈 SECTION 3 — HORIZONTAL POD AUTOSCALER (HPA)

### What is HPA?

**HPA automatically scales the NUMBER of pod replicas** based on observed metrics. When CPU goes up → add pods. When CPU comes down → remove pods.

### Simple Story — The Call Center Supervisor

HPA is like a **supervisor watching a dashboard** at the call center:

```
Target: each agent should handle at most 50% of their capacity

Dashboard shows: average agent load = 80%
Supervisor thinks: "Too high. We need more agents."
Supervisor hires 2 more agents.

30 minutes later: average load = 25%
Supervisor thinks: "Too low. Agents are idle."
Supervisor sends 2 agents home.

Always targeting ~50% load.
```

### How HPA Works — The Math

```
DESIRED REPLICAS = CEIL( current replicas × (current metric value / target metric value) )

EXAMPLE:
  Current replicas: 3
  Current CPU usage: 90%
  Target CPU: 50%
  
  Desired = CEIL( 3 × (90 / 50) )
           = CEIL( 3 × 1.8 )
           = CEIL( 5.4 )
           = 6 replicas

HPA scales from 3 → 6 pods
```

```
SCALE DOWN EXAMPLE:
  Current replicas: 6
  Current CPU usage: 20%
  Target CPU: 50%
  
  Desired = CEIL( 6 × (20 / 50) )
           = CEIL( 6 × 0.4 )
           = CEIL( 2.4 )
           = 3 replicas

HPA scales from 6 → 3 pods
```

### HPA Requirements

```
REQUIRED:
  1. metrics-server installed in the cluster
     → Collects CPU and memory usage from all pods
     → HPA reads from metrics-server via metrics API
     → Without this: HPA shows <unknown> for metrics and does nothing

  2. Resource REQUESTS set on pods
     → HPA measures CPU as percentage of REQUEST
     → If no request is set: HPA cannot calculate percentage → fails
     → "90% CPU" means: using 90% of what was requested

  3. Deployment (not standalone pods)
     → HPA scales Deployments/StatefulSets/ReplicaSets
     → Cannot scale standalone pods
```

### Basic HPA YAML (CPU-based)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: payment-hpa
  namespace: banking
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-app          # which deployment to scale
  minReplicas: 2               # never go below this
  maxReplicas: 10              # never go above this
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50  # target 50% CPU usage
```

**Every line explained:**

```yaml
apiVersion: autoscaling/v2
```
→ HPA belongs to the `autoscaling` API group.
→ `v2` is the current version — supports multiple metrics, custom metrics.
→ The old `v1` only supported CPU. Always use `v2` for new clusters.

```yaml
kind: HorizontalPodAutoscaler
```
→ Creating an HPA object.

```yaml
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-app
```
→ `scaleTargetRef` → what to scale. HPA controls the replica count of this object.
→ `kind: Deployment` → target is a Deployment (could also be StatefulSet, ReplicaSet).
→ `name: payment-app` → the Deployment named `payment-app` in the same namespace.

```yaml
  minReplicas: 2
  maxReplicas: 10
```
→ `minReplicas: 2` → NEVER scale below 2 pods. Even if CPU is 0%, keep 2 pods running (for availability).
→ `maxReplicas: 10` → NEVER scale above 10 pods. Prevents runaway scaling from bankrupting your cloud bill.
→ These are hard limits — HPA will not go outside this range.

```yaml
  metrics:
  - type: Resource
    resource:
      name: cpu
```
→ `metrics` → list of metrics to use for scaling decisions.
→ `type: Resource` → a Kubernetes built-in resource metric (CPU or memory).
→ `name: cpu` → specifically CPU utilization.

```yaml
      target:
        type: Utilization
        averageUtilization: 50
```
→ `type: Utilization` → measure as percentage of request.
→ `averageUtilization: 50` → target: the AVERAGE CPU across all pods should be 50% of their request.
→ If average goes above 50% → scale up.
→ If average drops below 50% → scale down (after cooldown).

### HPA with Memory

```yaml
  metrics:
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 200Mi    # target 200Mi average memory per pod
```

→ `type: AverageValue` → measure in absolute value (not percentage).
→ `averageValue: 200Mi` → if average memory per pod goes above 200Mi → scale up.
→ Note: memory-based HPA is less common because memory doesn't drop easily after scaling (apps don't free memory just because you added more pods).

### HPA with Custom Metrics

Custom metrics allow you to scale on business-relevant metrics — not just CPU/memory:

```yaml
  metrics:
  # Scale on requests per second (from Prometheus)
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "100"     # target 100 RPS per pod

  # Scale on queue length (external metric)
  - type: External
    external:
      metric:
        name: sqs_messages_visible
        selector:
          matchLabels:
            queue: payment-queue
      target:
        type: AverageValue
        averageValue: "30"      # target 30 messages per pod
```

**Three metric types in HPA v2:**

```
Resource:
  → Built-in: cpu, memory
  → Measured as % of request or absolute value
  → Comes from metrics-server

Pods:
  → Custom metric averaged across all pods
  → Must come from Prometheus Adapter or similar
  → "http_requests_per_second" — averaged per pod

External:
  → Metric external to Kubernetes
  → AWS SQS queue depth, ActiveMQ queue length, etc.
  → Not averaged per pod — total cluster-level metric
```

### HPA Scaling Behavior (Cooldown / Stabilization)

```
WITHOUT COOLDOWN:
  CPU spikes to 90% → HPA scales to 10 pods
  CPU drops to 5% (because 10 pods handled it)
  HPA immediately scales back to 2 pods
  Those 2 pods can't handle load → CPU spikes again
  → THRASHING: constant scale up/down/up/down

WITH STABILIZATION WINDOW:
  Scale UP: act quickly (don't wait too long under high load)
  Scale DOWN: wait before acting (load might come back)
```

```yaml
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # wait 5 minutes before scaling down
      policies:
      - type: Percent
        value: 50                        # scale down max 50% of pods at once
        periodSeconds: 60                # per 60-second window
    scaleUp:
      stabilizationWindowSeconds: 0     # scale up immediately
      policies:
      - type: Pods
        value: 4                         # add max 4 pods at once
        periodSeconds: 60
```

**Line by line:**

```yaml
    scaleDown:
      stabilizationWindowSeconds: 300
```
→ Before scaling DOWN, HPA looks at metrics over the last 300 seconds (5 minutes).
→ Only scale down if it would have been the right decision for the ENTIRE window.
→ Prevents yo-yo scaling where traffic is temporarily low.

```yaml
      policies:
      - type: Percent
        value: 50
        periodSeconds: 60
```
→ Scale down at most 50% of current replicas per 60 seconds.
→ If you have 10 pods, remove at most 5 per minute.
→ Gradual scale down — less disruptive.

```yaml
    scaleUp:
      stabilizationWindowSeconds: 0
```
→ Scale up IMMEDIATELY with no waiting window.
→ You want to react fast to traffic spikes — don't wait.

```yaml
      policies:
      - type: Pods
        value: 4
        periodSeconds: 60
```
→ Add at most 4 pods per 60-second window.
→ Controlled scale-up — don't spin up 50 pods at once.

## 📊 SECTION 4 — VERTICAL POD AUTOSCALER (VPA)

### What is VPA?

**VPA automatically adjusts the CPU and memory REQUESTS (and limits) of existing pods** based on actual historical usage. Instead of adding more pods (horizontal), it makes each pod bigger (vertical).

### Simple Story — The Employee Desk

```
HPA says: "Too much work → hire more employees"
VPA says:  "This employee needs a BIGGER DESK to work efficiently"

You hired a data scientist (pod).
You gave her a tiny laptop with 1GB RAM (requests/limits).
She runs data analysis — needs 8GB RAM.
Laptop keeps crashing (OOMKill).

VPA watches: "This pod always uses 8GB. Let me increase its requests to 8GB."
Now the pod gets proper resources. No more crashes.
Next time the pod is created (restart) → it starts with 8GB RAM.
```

### VPA Components

```
VPA has THREE components:

1. Recommender:
   → Watches actual resource usage of pods over time
   → Calculates optimal requests and limits
   → Stores recommendations as VPA object status
   → Does NOT change anything itself

2. Updater:
   → Reads recommendations from Recommender
   → If current pod's resources differ significantly from recommendation
   → Evicts the pod (forces restart with new resources)
   → New pod starts with recommended values

3. Admission Plugin:
   → Intercepts new pod creation
   → Applies the VPA recommendation to the pod's resource spec
   → Even if YAML says 256Mi → plugin changes it to 2Gi (recommended)
```

### VPA YAML

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: payment-vpa
  namespace: banking
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-app
  updatePolicy:
    updateMode: "Auto"
  resourcePolicy:
    containerPolicies:
    - containerName: payment-app
      minAllowed:
        cpu: 100m
        memory: 128Mi
      maxAllowed:
        cpu: 2
        memory: 4Gi
      controlledResources: ["cpu", "memory"]
```

**Every line explained:**

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
```
→ VPA is NOT built into Kubernetes — it must be installed separately.
→ It uses CRDs (Custom Resource Definitions) — `autoscaling.k8s.io` is the CRD group.

```yaml
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment-app
```
→ Which workload VPA monitors and adjusts — same pattern as HPA's scaleTargetRef.

```yaml
  updatePolicy:
    updateMode: "Auto"
```
→ `updateMode` → how VPA applies recommendations. Four modes:

```
Off:
  → VPA only provides recommendations (in status section)
  → Does NOT change anything
  → Use to see what VPA would recommend without impact
  → Safe starting point

Initial:
  → Apply recommendation when pod is FIRST created
  → Does NOT evict running pods
  → New pods get recommended values, existing pods unchanged

Recreation:
  → Apply recommendation when pod restarts for any reason
  → Does NOT actively evict pods
  → Wait for natural restart events

Auto (default):
  → Actively evict pods when recommendation differs significantly
  → New pod starts with recommended resources
  → Most powerful but causes pod restarts
  → Not suitable for single-replica deployments (downtime!)
```

```yaml
  resourcePolicy:
    containerPolicies:
    - containerName: payment-app
      minAllowed:
        cpu: 100m
        memory: 128Mi
```
→ `resourcePolicy` → bounds on what VPA can recommend.
→ `containerName: payment-app` → policy for this specific container.
→ `minAllowed` → VPA will NEVER recommend below this (prevents going too low).

```yaml
      maxAllowed:
        cpu: 2
        memory: 4Gi
```
→ `maxAllowed` → VPA will NEVER recommend above this (prevents runaway large resources).

```yaml
      controlledResources: ["cpu", "memory"]
```
→ Which resources VPA can adjust. Could be just `["memory"]` if you only want VPA to manage memory.

### Checking VPA Recommendations

```bash
kubectl describe vpa payment-vpa -n banking
```

Output:
```
Status:
  Recommendation:
    Container Recommendations:
      Container Name: payment-app
      Lower Bound:
        Cpu:    50m
        Memory: 128Mi
      Target:                    ← VPA's recommended values
        Cpu:    250m
        Memory: 512Mi
      Upper Bound:
        Cpu:    500m
        Memory: 1Gi
      Uncapped Target:           ← recommendation without min/max constraints
        Cpu:    200m
        Memory: 480Mi
```

→ `Target` → what VPA actually recommends setting requests to.
→ `Lower Bound` → minimum to avoid OOMKill risk (90th percentile usage).
→ `Upper Bound` → maximum needed (95th percentile usage).

### ⚠️ VPA + HPA — CANNOT Use Both for Same Metric

```
⚠️ WARNING: VPA and HPA conflict when using same metric

WRONG (conflict):
  HPA scales on CPU utilization (%)
  VPA adjusts CPU requests
  → VPA increases CPU request → CPU utilization % drops → HPA scales down
  → HPA scales down → CPU rises → VPA increases request → HPA scales down
  → INFINITE LOOP — they fight each other

CORRECT (compatible combinations):
  HPA on CPU/memory + VPA in Off/Initial mode (VPA only recommends, HPA acts)
  HPA on custom metrics (RPS, queue depth) + VPA on CPU/memory
  Only HPA (no VPA) — most common production setup
  Only VPA (no HPA) — for workloads that can't scale horizontally (databases)
```

## 🖥️ SECTION 5 — CLUSTER AUTOSCALER (CA)

### What is Cluster Autoscaler?

**Cluster Autoscaler automatically adds or removes NODES** (virtual machines) from the cluster based on whether pods can be scheduled.

```
HPA added 5 new pods → no nodes have space → pods are Pending
         │
         ▼
Cluster Autoscaler detects: "Pods are Pending due to insufficient resources"
         │
         ▼
CA calls cloud API: "Add a new node (EC2 instance)"
         │
         ▼
New node joins cluster
         │
         ▼
Scheduler places pending pods on new node
         │
         ▼
Pods start running
```

```
Later: Traffic drops → HPA removed many pods → nodes are mostly empty
         │
         ▼
Cluster Autoscaler detects: "Node X only has small pods that could fit elsewhere"
         │
         ▼
CA cordons node X (no new pods scheduled there)
         │
         ▼
CA drains node X (evicts all pods to other nodes)
         │
         ▼
CA calls cloud API: "Terminate EC2 instance for node X"
         │
         ▼
Node removed — save money
```

### How CA Decides to Scale UP

```
CA checks every 10 seconds:
  Are there any Pending pods? (pods that can't be scheduled)
  
  If YES:
    Why are they Pending?
    → Not enough CPU? → add node with enough CPU
    → Not enough memory? → add node with enough memory
    → Pod has node affinity that requires specific node type? → add that type
    
    CA simulates: "If I add a node from node group X, would the pending pod schedule?"
    If YES → add that node
    
  If NO pending pods → no scale up needed
```

### How CA Decides to Scale DOWN

```
CA checks every 10 seconds:
  Are any nodes UNDERUTILIZED?
  
  A node is underutilized when:
    ALL pods on it could be moved to OTHER existing nodes
    AND the node's CPU utilization < 50% (configurable threshold)
    AND no pod on it has PodDisruptionBudget preventing eviction
    AND the node has been underutilized for 10+ minutes (scale-down-delay)

  If underutilized:
    CA simulates: "If I remove this node, can all pods fit on remaining nodes?"
    If YES → drain the node → terminate the cloud VM
```

### CA Configuration (AWS EKS Example)

CA is deployed as a Deployment in the cluster. Configuration via flags:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cluster-autoscaler
  namespace: kube-system
spec:
  template:
    spec:
      containers:
      - name: cluster-autoscaler
        image: registry.k8s.io/autoscaling/cluster-autoscaler:v1.28.0
        command:
        - ./cluster-autoscaler
        - --v=4
        - --stderrthreshold=info
        - --cloud-provider=aws
        - --skip-nodes-with-local-storage=false
        - --expander=least-waste
        - --node-group-auto-discovery=asg:tag=k8s.io/cluster-autoscaler/enabled,k8s.io/cluster-autoscaler/my-cluster
        - --balance-similar-node-groups
        - --scale-down-enabled=true
        - --scale-down-delay-after-add=10m
        - --scale-down-unneeded-time=10m
        - --scale-down-utilization-threshold=0.5
```

**Key flags explained:**

```
--cloud-provider=aws
  → Tell CA which cloud to use. Options: aws, gce, azure, alicloud, etc.

--expander=least-waste
  → When adding a node, which node group/type to pick?
  → least-waste: pick the node type that wastes least resources for pending pods
  → Other options: random, most-pods, price, priority

--node-group-auto-discovery=asg:tag=...
  → Don't hardcode node group names. Auto-discover by ASG tags.
  → Any AWS Auto Scaling Group with these tags is managed by CA.

--scale-down-delay-after-add=10m
  → After scaling UP, wait 10 minutes before considering scale down.
  → Prevents immediately removing nodes that were just added.

--scale-down-unneeded-time=10m
  → Node must be underutilized for 10+ minutes before being removed.
  → Prevents removing nodes for temporary traffic dips.

--scale-down-utilization-threshold=0.5
  → Node must be below 50% utilization to be considered for removal.

--skip-nodes-with-local-storage=false
  → Allow removing nodes that have pods using emptyDir or hostPath.
  → Those pods lose their local data but get rescheduled.

--balance-similar-node-groups
  → Try to keep similar node groups (e.g., multiple AZs) balanced in size.
```

### Node Groups (AWS ASG Integration)

```
AWS SETUP:
  Auto Scaling Group 1: t3.medium nodes, min=1, max=5, AZ=us-east-1a
  Auto Scaling Group 2: t3.medium nodes, min=1, max=5, AZ=us-east-1b
  Auto Scaling Group 3: m5.xlarge nodes, min=0, max=3 (for memory-intensive pods)

CA tags these ASGs and discovers them automatically.
CA sets ASG desired capacity to add/remove nodes.
AWS creates/terminates EC2 instances based on ASG desired.
```

### Preventing Nodes from Being Removed

```bash
# Annotate a node to prevent CA from removing it
kubectl annotate node node-1 \
  cluster-autoscaler.kubernetes.io/scale-down-disabled=true
```

This is useful for:
- Nodes with stateful pods that shouldn't be evicted
- Nodes running long jobs that can't be interrupted
- Nodes with special hardware (GPU)

### PodDisruptionBudget — Protect Pods During Scale Down

When CA removes a node, it evicts pods. PDB controls how many pods of a deployment can be evicted at once:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-pdb
  namespace: banking
spec:
  minAvailable: 2          # always keep at least 2 pods running
  selector:
    matchLabels:
      app: payment-app
```

→ `minAvailable: 2` → during eviction, at least 2 payment pods must stay running.
→ If CA tries to evict a node that would drop payment pods below 2 → CA cannot remove that node.
→ CA respects PDB — it will NOT drain a node if doing so violates the PDB.

Alternative using maxUnavailable:
```yaml
spec:
  maxUnavailable: 1    # at most 1 pod can be unavailable at any time
```

## 🔄 SECTION 6 — HOW ALL THREE WORK TOGETHER

### The Complete Autoscaling Story

```
NORMAL OPERATION (3 replicas, 2 nodes):
  Node 1: pod-1, pod-2
  Node 2: pod-3

TRAFFIC SPIKE:
  CPU jumps to 90% across all pods

  1. HPA detects: CPU 90% > target 50%
     HPA calculation: 3 × (90/50) = 5.4 → 6 replicas needed
     HPA sets replicas: 3 → 6
  
  2. Scheduler tries to place 3 new pods
     Node 1: full (not enough CPU left)
     Node 2: full (not enough CPU left)
     Pods 4, 5, 6: PENDING
  
  3. Cluster Autoscaler detects: 3 pending pods
     CA: "If I add a new node, can these pods schedule?" YES
     CA: calls AWS API → create EC2 instance → join as Node 3
  
  4. Node 3 joins cluster (takes ~2-3 minutes)
     Scheduler places pods 4, 5, 6 on Node 3
     All 6 pods running
  
  5. CPU drops to 30% (6 pods sharing the load)
  
TRAFFIC DROPS:
  CPU falls to 10%
  
  1. HPA detects: CPU 10% < target 50%
     Calculation: 6 × (10/50) = 1.2 → 2 replicas (minReplicas=2)
     HPA: stabilization window → wait 5 minutes
     HPA: scale from 6 → 2 replicas after window
  
  2. Node 3 only has small remaining pods
     CA: Node 3 underutilized for 10 minutes
     CA: Can these pods fit on Node 1 and Node 2? YES
     CA: Drains Node 3 (evicts pods to other nodes)
     CA: Calls AWS API → terminate EC2 → Node 3 removed
  
BACK TO NORMAL (2 replicas, 2 nodes)
```

### LAB 1 — Set Resource Requests and Limits on a Deployment

```bash
# Create deployment WITHOUT resource limits (bad practice demo)
kubectl create deployment no-limits-app --image=nginx --replicas=2

# Check QoS class — should be BestEffort
kubectl get pod -l app=no-limits-app -o yaml | grep -A2 qosClass
```
- `-l app=no-limits-app` → select pods with this label
- `-o yaml` → full YAML output
- `grep -A2 qosClass` → find qosClass and show 2 lines after

```bash
# Now add resource requests and limits
kubectl set resources deployment no-limits-app \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=200m,memory=256Mi
```
- `set resources deployment` → update resources on this deployment
- `--requests=cpu=100m,memory=128Mi` → set requests for both CPU and memory
- `--limits=cpu=200m,memory=256Mi` → set limits for both

```bash
# Verify resources are set
kubectl describe deployment no-limits-app | grep -A10 "Limits\|Requests"

# Check QoS class — now Burstable
kubectl get pod -l app=no-limits-app -o yaml | grep qosClass
```

```bash
# Create a Guaranteed QoS pod (requests == limits)

        cpu: "500m"
        memory: "256Mi"

```

### LAB 3 — Create HPA and Generate Load to Test It

```bash
# Step 1: Create a CPU-intensive test deployment with resource requests
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cpu-stress
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cpu-stress
  template:
    metadata:
      labels:
        app: cpu-stress
    spec:
      containers:
      - name: cpu-stress
        image: nginx
        resources:
          requests:
            cpu: "200m"
            memory: "64Mi"
          limits:
            cpu: "500m"
            memory: "128Mi"
EOF
```

```bash
# Step 2: Create HPA targeting 50% CPU
cat <<EOF | kubectl apply -f -
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: cpu-stress-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: cpu-stress
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
EOF
```

```bash
# Step 3: Check HPA initial status
kubectl get hpa cpu-stress-hpa
```
Output:
```

cpu-stress-hpa  Deployment/cpu-stress 0%/50%    1         5         1          30s
```
- `TARGETS: 0%/50%` → current 0%, target 50%
- `REPLICAS: 1` → currently 1 pod

```bash
# Step 4: Generate CPU load (in a separate terminal)
kubectl run load-generator \
  --image=busybox \
  --restart=Never \
  -- sh -c "while true; do wget -q -O- http://cpu-stress; done"
```

- `--restart=Never` → create a Pod (not a Deployment)
- `-- sh -c "while true; do wget -q -O- http://cpu-stress; done"` → infinite loop sending HTTP requests

## 📊 SECTION 8 — COMPLETE COMPARISON TABLE

| Feature | HPA | VPA | Cluster Autoscaler |
|---------|-----|-----|--------------------|
| What it scales | Pod count | Pod resources (CPU/memory) | Node count |
| Scale direction | Horizontal (out/in) | Vertical (up/down) | Cluster (add/remove nodes) |
| Trigger | Metric threshold (CPU, custom) | Historical usage patterns | Pending pods / underutilized nodes |
| Speed | Fast (seconds) | Slow (requires pod restart) | Slow (VM boot, 2-3 min) |
| Requires metrics-server | ✅ Yes | ✅ Yes (for recommendations) | ❌ No (uses scheduling) |
| Causes pod restart | ❌ No | ✅ Yes (evicts and recreates) | ✅ Yes (evicts during drain) |
| Works for stateful apps | ✅ Often | ✅ Yes | ✅ With PDB |
| Cloud integration needed | ❌ No | ❌ No | ✅ Yes (cloud provider API) |
| Built into Kubernetes | ✅ Yes | ❌ No (install separately) | ❌ No (install separately) |

## 🔑 SECTION 9 — KEY TERMS TO REMEMBER

| Term | Simple Meaning |
|------|---------------|
| **Resource Request** | Minimum guaranteed resources — used by Scheduler |
| **Resource Limit** | Maximum allowed resources — enforced by kernel |
| **CPU Throttling** | Pod runs slower when hitting CPU limit — does NOT crash |
| **OOMKill** | Pod killed when hitting memory limit — exit code 137 |
| **Guaranteed QoS** | requests == limits — highest eviction priority (last evicted) |
| **Burstable QoS** | requests < limits — middle eviction priority |
| **BestEffort QoS** | No requests or limits — lowest priority (evicted first) |
| **HPA** | Horizontal Pod Autoscaler — scales pod count |
| **VPA** | Vertical Pod Autoscaler — scales pod resource size |
| **Cluster Autoscaler** | Scales node count — adds/removes VMs |
| **metrics-server** | In-cluster metrics aggregator — required for HPA and kubectl top |
| **averageUtilization** | HPA target: average CPU% across all pods |
| **averageValue** | HPA target: average absolute value (e.g., 200Mi memory per pod) |
| **stabilizationWindowSeconds** | How long HPA waits before scaling down (prevents thrashing) |
| **minReplicas / maxReplicas** | Hard bounds on HPA scaling range |
| **VPA updateMode: Off** | VPA only recommends — does not change anything |
| **VPA updateMode: Auto** | VPA actively evicts pods to apply recommendations |
| **PodDisruptionBudget (PDB)** | Policy: minimum pods that must stay running during eviction |
| **Cordon** | Mark node as unschedulable — no new pods placed here |
| **Drain** | Evict all pods from a node (respects PDB) |
| **Node Group** | A set of nodes with same specs (AWS: Auto Scaling Group) |
| **Scale-down delay** | How long CA waits before removing an underutilized node |
| **Expander** | CA strategy for picking which node group to scale up |
| **Overcommit** | Limits > node capacity — fine for limits, bad for requests |
| **millicores (m)** | 1/1000th of a CPU core. 1000m = 1 CPU |
