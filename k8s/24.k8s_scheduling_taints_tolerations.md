## 🧠 SECTION 1 — WHAT IS SCHEDULING IN KUBERNETES? (Story First)

### Forget Kubernetes for 3 minutes — start with a story

Imagine you are the **HR manager** of a large company with 10 office floors (nodes) and 200 employees (pods).

Every new employee who joins needs to be assigned a desk on one of the floors. But it is not random — there are rules:

```
FLOOR RULES (Node-side rules):
  Floor 8 (GPU Lab):
    "Only machine learning researchers allowed here.
     Nobody else can sit here."
    → This is a TAINT on the node

  Floor 9 (Executive):
    "Only VPs and above allowed here."
    → Another TAINT

EMPLOYEE PREFERENCES (Pod-side rules):
  Data Scientist:
    "I have special permission to work in the GPU Lab (Floor 8)"
    → This is a TOLERATION

  CEO:
    "I MUST sit on the Executive floor. I refuse to sit anywhere else."
    → This is NODE AFFINITY (required)

  Sales team member:
    "I prefer to sit near the Sales department"
    → This is NODE AFFINITY (preferred)

  Two competing sales managers:
    "We should NOT sit next to each other — we share resources"
    → This is POD ANTI-AFFINITY

  Teammates:
    "Our whole development team should sit on the same floor"
    → This is POD AFFINITY
```

**Kubernetes Scheduling = assigning pods to nodes using these rules.**

### The Kubernetes Scheduler — What It Does

```
SCHEDULER'S JOB:
  For each UNSCHEDULED pod:
    1. FILTERING phase — eliminate nodes that CANNOT host this pod
       → Node doesn't have enough CPU/memory → removed
       → Node has a taint the pod doesn't tolerate → removed
       → Pod requires GPU label the node doesn't have → removed
       
    2. SCORING phase — rank remaining nodes
       → Nodes with preferred labels score higher
       → Nodes with more free resources score higher
       → Spread constraints prefer less-used nodes
       
    3. BINDING — assign pod to highest-scoring node
       → Write nodeName into pod spec in etcd
       → Kubelet on that node detects and starts the pod

If NO node passes filtering → pod stays PENDING
```

### All Scheduling Topics in One Map

```
SCHEDULING CONTROLS:
  ├── NODE-SIDE RULES (node decides who can come)
  │     └── Taints + Effect (NoSchedule, PreferNoSchedule, NoExecute)
  │
  ├── POD-SIDE RULES (pod decides where it wants to go)
  │     ├── NodeSelector         → simple label match
  │     ├── Node Affinity        → complex label rules (required/preferred)
  │     ├── Tolerations          → opt-in to tainted nodes
  │     ├── Pod Affinity         → "schedule me NEAR these pods"
  │     └── Pod Anti-Affinity    → "schedule me AWAY from these pods"
  │
  ├── SPREAD CONTROLS
  │     └── Topology Spread Constraints → distribute pods evenly across zones/nodes
  │
  └── PRIORITY CONTROLS
        └── PriorityClass        → high-priority pods preempt lower-priority ones
```

## 🚫 SECTION 2 — TAINTS (Node-Side Repellent)

### What is a Taint?

A **taint** is a marker placed on a NODE that **repels pods** unless those pods have a matching toleration.

Think of a taint like a **"Restricted Access" sign** on a door. By default, nobody can enter. Only people with the right badge (toleration) can get in.

### Taint Structure

```
FORMAT: key=value:Effect

EXAMPLE: dedicated=gpu:NoSchedule

Breaking it down:
  key    = dedicated      (the category/name of restriction)
  value  = gpu            (the specific value)
  Effect = NoSchedule     (what happens to pods without toleration)
```

### Three Taint Effects

```
NoSchedule:
  → New pods WITHOUT matching toleration will NOT be scheduled here
  → Existing pods already running on this node are NOT affected
  → HARD restriction for new pods

PreferNoSchedule:
  → Scheduler TRIES to avoid placing new pods here without toleration
  → But if no other node is available → pod CAN land here anyway
  → SOFT restriction / best-effort

NoExecute:
  → New pods without toleration are NOT scheduled (like NoSchedule)
  → EXISTING pods without toleration are EVICTED (kicked out)
  → Most powerful effect — affects running pods
  → Also used for node conditions (node not ready → NoExecute taint added)
```

### Tainting a Node — Commands

```bash
# Add a taint to a node
kubectl taint nodes node-1 dedicated=gpu:NoSchedule

# Add multiple taints to same node
kubectl taint nodes node-1 dedicated=gpu:NoSchedule
kubectl taint nodes node-1 environment=production:NoExecute

# Remove a taint (add minus at the end)
kubectl taint nodes node-1 dedicated=gpu:NoSchedule-

# View taints on a node
kubectl describe node node-1 | grep Taints
```

**Breaking down the taint command:**
- `kubectl taint nodes` → the command to add/remove taints
- `node-1` → which node to taint
- `dedicated=gpu:NoSchedule` → the full taint: `key=value:Effect`
- Adding `-` at the END removes the taint: `dedicated=gpu:NoSchedule-`

### Real-World Taint Use Cases

```
USE CASE 1: GPU Nodes
  kubectl taint nodes gpu-node-1 nvidia.com/gpu=true:NoSchedule
  → Regular CPU pods cannot land on expensive GPU nodes
  → Only ML training pods (with toleration) go here
  → Prevents wasting $10/hour GPU nodes on nginx pods

USE CASE 2: Production vs Dev Nodes
  kubectl taint nodes prod-node-1 environment=production:NoSchedule
  → Dev/test pods cannot accidentally land on production nodes
  → Only production-labeled pods land here

USE CASE 3: Master/Control Plane Nodes
  → Kubernetes automatically taints control plane nodes:
  node-role.kubernetes.io/control-plane:NoSchedule
  → Your app pods don't land on master nodes
  → Only system pods with matching tolerations run there

USE CASE 4: Spot/Preemptible Nodes
  kubectl taint nodes spot-node-1 cloud.google.com/gke-spot=true:NoSchedule
  → Only pods that can tolerate interruption go on cheap spot instances

USE CASE 5: Dedicated Node Pool
  kubectl taint nodes dedicated-node-1 dedicated=banking:NoSchedule
  → Only banking namespace pods land on these dedicated nodes
```

## ✅ SECTION 3 — TOLERATIONS (Pod-Side Permission)

### What is a Toleration?

A **toleration** is placed on a POD to say: "I can tolerate (accept) being placed on a node with this specific taint." It gives the pod permission to be scheduled on tainted nodes.

### CRITICAL UNDERSTANDING

```
Taint on node   = "Repel all pods by default"
Toleration on pod = "This pod is EXEMPT from that repulsion"

Toleration does NOT mean: "Schedule me ON the tainted node"
Toleration means: "Schedule me ON the tainted node IF needed"

You still need NODE AFFINITY to ATTRACT a pod to a tainted node.
Toleration = permission to go there
Node Affinity = desire/requirement to go there
```

### Toleration YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: ml-training-pod
spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
  - key: "environment"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 3600
  containers:
  - name: trainer
    image: tensorflow:latest
```

**Every line explained:**

```yaml
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
```
→ `tolerations` → list of taints this pod will tolerate.
→ `key: "dedicated"` → must match the taint's key exactly.
→ `operator: "Equal"` → match method: `Equal` means key AND value must match.
→ `value: "gpu"` → must match the taint's value exactly.
→ `effect: "NoSchedule"` → which effect this toleration covers.
→ This matches the taint `dedicated=gpu:NoSchedule` exactly.

```yaml
  - key: "environment"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 3600
```
→ `operator: "Exists"` → only checks if key EXISTS. Value doesn't matter.
→ `effect: "NoExecute"` → tolerates being evicted from NoExecute tainted nodes.
→ `tolerationSeconds: 3600` → BUT only for 3600 seconds (1 hour). After that, if the taint is still there, the pod IS evicted. If `tolerationSeconds` is omitted → tolerate forever.

### Toleration Operators

```
Equal:
  key AND value must match the taint exactly
  → tolerates only "dedicated=gpu:NoSchedule"
  → does NOT tolerate "dedicated=cpu:NoSchedule"

Exists:
  Only the key must exist (any value)
  → tolerates "dedicated=gpu:NoSchedule"
  → also tolerates "dedicated=cpu:NoSchedule"
  → also tolerates "dedicated=anything:NoSchedule"

Special — tolerate ALL taints:
  - operator: "Exists"
    (no key, no value, no effect specified)
  → This pod tolerates EVERY taint on EVERY node
  → Used for DaemonSets that must run everywhere
```

### Tolerate ALL Taints (DaemonSet Pattern)

```yaml
# DaemonSets need to run on ALL nodes including tainted ones
# Kubernetes automatically adds this toleration to DaemonSet pods
tolerations:
- operator: Exists    # no key = matches ALL taint keys
                      # no effect = matches ALL effects
```

## 📍 SECTION 4 — NODE SELECTOR (Simplest Node Assignment)

### What is NodeSelector?

`nodeSelector` is the SIMPLEST way to control which nodes a pod lands on. It requires the node to have specific labels.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  nodeSelector:
    accelerator: gpu          # node MUST have this label
    environment: production   # AND this label
  containers:
  - name: ml-app
    image: tensorflow:latest
```

**Line by line:**

```yaml
  nodeSelector:
    accelerator: gpu
    environment: production
```
→ `nodeSelector` → key-value map of required node labels.
→ Node must have ALL listed labels (AND logic).
→ If no node has both labels → pod stays Pending.
→ No flexibility — either match or Pending.
→ **nodeSelector is binary** — matched or not. No preferred/soft rules.

### Adding Labels to Nodes

```bash
# Add a label to a node
kubectl label node node-1 accelerator=gpu

# Add multiple labels
kubectl label node node-1 accelerator=gpu environment=production

# Remove a label
kubectl label node node-1 accelerator-    # minus removes the label

# View labels on nodes
kubectl get nodes --show-labels
kubectl describe node node-1 | grep Labels -A 20
```

### Limitation of NodeSelector

```
NodeSelector is simple but LIMITED:
  ❌ No "OR" logic — can't say "gpu OR fpga"
  ❌ No "NOT" logic — can't say "not production"
  ❌ No soft preferences — binary match or fail
  ❌ No weight/priority — all rules equal

For complex scenarios → use Node Affinity
```

## 🎯 SECTION 5 — NODE AFFINITY (Advanced Node Selection)

### What is Node Affinity?

Node Affinity is the **advanced version of NodeSelector**. It supports:
- OR logic (in operator)
- NOT logic (NotIn operator)
- Soft preferences (preferredDuringScheduling)
- Weight/priority on preferences

### Two Types of Node Affinity

```
requiredDuringSchedulingIgnoredDuringExecution:
  → REQUIRED: pod MUST land on matching node or stay Pending
  → IgnoredDuringExecution: if node loses the label AFTER pod is running
    → pod continues running (not evicted)
  → Think of it as: HARD rule at scheduling time

preferredDuringSchedulingIgnoredDuringExecution:
  → PREFERRED: scheduler TRIES to place on matching node
  → But if no matching node → schedule anywhere
  → Weight 1-100 to prioritize among preferences
  → Think of it as: SOFT rule / best-effort

FUTURE (not yet stable):
  requiredDuringSchedulingRequiredDuringExecution:
  → HARD rule at scheduling AND running
  → Pod evicted if node stops matching
  → Not yet implemented in stable Kubernetes
```

### Node Affinity YAML — Full Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-pod
  namespace: banking
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values:
            - us-east-1a
            - us-east-1b
          - key: node-type
            operator: In
            values:
            - compute-optimized
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: environment
            operator: In
            values:
            - production
      - weight: 20
        preference:
          matchExpressions:
          - key: ssd
            operator: Exists
  containers:
  - name: payment-app
    image: payment:1.0
```

**Every line explained:**

```yaml
  affinity:
    nodeAffinity:
```
→ `affinity` → the parent field for all affinity rules (node and pod).
→ `nodeAffinity` → rules about WHICH NODES to prefer/require.

```yaml
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values:
            - us-east-1a
            - us-east-1b
```
→ `requiredDuringSchedulingIgnoredDuringExecution` → HARD rule.
→ `nodeSelectorTerms` → list of term sets. Multiple terms = OR between them.
→ `matchExpressions` → list of conditions within a term. Multiple conditions = AND.
→ `key: topology.kubernetes.io/zone` → the node label key to check.
→ `operator: In` → node's label value must be IN this list.
→ `values: [us-east-1a, us-east-1b]` → acceptable values.
→ Result: pod MUST land on a node in us-east-1a OR us-east-1b.

```yaml
          - key: node-type
            operator: In
            values:
            - compute-optimized
```
→ Second condition in the SAME matchExpressions = AND.
→ Node must ALSO have label `node-type=compute-optimized`.
→ Combined required: (zone = 1a OR 1b) AND (node-type = compute-optimized).

```yaml
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: environment
            operator: In
            values:
            - production
```
→ `preferredDuringScheduling` → SOFT rule. Try to match, but not required.
→ `weight: 80` → how much to prefer this. Range: 1-100. Higher = more preferred.
→ If node has `environment=production` label → add 80 to its score.
→ Highest-scored node among all valid nodes is chosen.

```yaml
      - weight: 20
        preference:
          matchExpressions:
          - key: ssd
            operator: Exists
```
→ Second preference with weight 20.
→ `operator: Exists` → node just needs to HAVE the `ssd` label (any value).
→ Node with both `environment=production` AND `ssd` label gets 80+20=100 points.
→ Node with only `environment=production` gets 80 points.
→ Node with only `ssd` gets 20 points.
→ Node with neither gets 0 points (but can still be used if it passed required).

### Node Affinity Operators

```
In:         label value must be in the list
            operator: In, values: [gpu, tpu]
            → node must have key with value "gpu" OR "tpu"

NotIn:      label value must NOT be in the list
            operator: NotIn, values: [dev, test]
            → node must NOT have key with value "dev" or "test"

Exists:     label key must exist (any value)
            operator: Exists
            → node must have the key (value doesn't matter)

DoesNotExist: label key must NOT exist
            operator: DoesNotExist
            → node must NOT have this label at all

Gt:         label value must be GREATER than given number
            operator: Gt, values: ["4"]
            → node's label value (as integer) must be > 4

Lt:         label value must be LESS than given number
            operator: Lt, values: ["16"]
            → node's label value must be < 16
```

### nodeSelectorTerms — OR Logic

```yaml
nodeSelectorTerms:
- matchExpressions:        # TERM 1
  - key: zone
    operator: In
    values: [us-east-1a]
- matchExpressions:        # TERM 2 (separate term = OR)
  - key: zone
    operator: In
    values: [us-west-2a]
```

→ Multiple `nodeSelectorTerms` = OR between them.
→ Pod can go to us-east-1a OR us-west-2a.
→ matchExpressions within one term = AND.

```
SUMMARY:
  Multiple nodeSelectorTerms → OR (between terms)
  Multiple matchExpressions in one term → AND (within term)
```

## 🤝 SECTION 6 — POD AFFINITY AND POD ANTI-AFFINITY

### What is Pod Affinity?

Pod Affinity controls placement based on **where OTHER PODS are** — not node labels. It says: "Schedule me ON THE SAME node/zone as pods that match this selector."

### Simple Story

```
You are a new employee (new pod).
You want to sit on the SAME FLOOR as your teammates (other pods with label team=backend).
You don't care which floor — just be near them.
This is Pod Affinity.

You are a new employee.
You want to sit on a DIFFERENT FLOOR from your rival (pods with label role=frontend).
This is Pod Anti-Affinity.
```

### When to Use Pod Affinity

```
Pod Affinity — co-locate pods:
  ✅ App and its cache (Redis) should be on same node (reduce latency)
  ✅ All pods of a team should be in same AZ (reduce cross-AZ cost)
  ✅ Co-located services that communicate frequently

Pod Anti-Affinity — spread pods:
  ✅ Multiple replicas of same app should be on DIFFERENT nodes
     (one node failure doesn't take down ALL replicas)
  ✅ Two memory-intensive services should not share a node
     (would compete for memory and cause OOMKill)
  ✅ Stateful services that shouldn't share physical hardware
```

### Pod Affinity + Anti-Affinity YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-pod
  labels:
    app: payment
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: redis-cache        # co-locate with redis pods
        topologyKey: kubernetes.io/hostname  # same NODE
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: payment            # NOT same node as other payment pods
        topologyKey: kubernetes.io/hostname  # different NODE required
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: analytics        # PREFER different node from analytics
          topologyKey: kubernetes.io/hostname
  containers:
  - name: payment-app
    image: payment:1.0
```

**Every line explained:**

```yaml
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: redis-cache
        topologyKey: kubernetes.io/hostname
```
→ `podAffinity` → rules about co-location with other pods.
→ `labelSelector.matchLabels: app: redis-cache` → find pods with this label.
→ `topologyKey: kubernetes.io/hostname` → defines the SCOPE of co-location.
→ `kubernetes.io/hostname` = same NODE (each node has a unique hostname label).
→ Result: this pod MUST be on the same NODE as a pod labeled `app: redis-cache`.

**topologyKey values:**
```
kubernetes.io/hostname      → same NODE
topology.kubernetes.io/zone → same AVAILABILITY ZONE
topology.kubernetes.io/region → same REGION
custom-topology-key         → any custom grouping you define
```

```yaml
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: payment
        topologyKey: kubernetes.io/hostname
```
→ `podAntiAffinity` → rules about separation from other pods.
→ `app: payment` → find pods with this label (other payment pods).
→ `topologyKey: kubernetes.io/hostname` → must be on different hostname (node).
→ Result: this pod CANNOT be on same node as another payment pod.
→ This is the standard pattern for spreading replicas across nodes.

```yaml
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: analytics
          topologyKey: kubernetes.io/hostname
```
→ SOFT anti-affinity: PREFER to be on different node from analytics pods.
→ `weight: 100` → strong preference but not required.
→ If only one node available with analytics → pod can still go there.

## 🌐 SECTION 7 — TOPOLOGY SPREAD CONSTRAINTS

### What is Topology Spread Constraints?

Topology Spread Constraints ensure pods are **evenly distributed** across nodes, zones, or any custom topology — not just "not on the same node."

### The Problem Without Topology Spread

```
You have 6 replicas of payment-app across 3 zones:

WITHOUT constraints:
  Zone A: 5 pods  (zone overloaded)
  Zone B: 1 pod
  Zone C: 0 pods
  → If Zone A fails: 5/6 pods gone. Service degraded.

WITH Topology Spread Constraints:
  Zone A: 2 pods
  Zone B: 2 pods
  Zone C: 2 pods
  → If Zone A fails: 2/6 pods gone. 4 pods still serving. Resilient!
```

### Topology Spread YAML

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-app
spec:
  replicas: 6
  selector:
    matchLabels:
      app: payment
  template:
    metadata:
      labels:
        app: payment
    spec:
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels:
            app: payment
      - maxSkew: 1
        topologyKey: kubernetes.io/hostname
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: payment
      containers:
      - name: payment-app
        image: payment:1.0
```

**Every line explained:**

```yaml
      topologySpreadConstraints:
      - maxSkew: 1
```
→ `topologySpreadConstraints` → list of spread rules.
→ `maxSkew: 1` → the maximum DIFFERENCE in pod count between any two topology domains.
→ `maxSkew: 1` means: the most-loaded zone can have AT MOST 1 more pod than the least-loaded zone.
→ `maxSkew: 2` would allow a 2-pod difference.

```yaml
        topologyKey: topology.kubernetes.io/zone
```
→ Which topology domain to spread across.
→ `topology.kubernetes.io/zone` → spread evenly across availability zones.
→ Nodes with same zone label = same topology domain.

```yaml
        whenUnsatisfiable: DoNotSchedule
```
→ What to do if the spread constraint CANNOT be satisfied.
→ `DoNotSchedule` → pod stays Pending if it would violate maxSkew. HARD rule.
→ `ScheduleAnyway` → schedule even if it violates maxSkew but pick the node that minimizes the skew. SOFT rule.

```yaml
        labelSelector:
          matchLabels:
            app: payment
```
→ Which pods to COUNT when calculating spread.
→ Only payment pods are counted when computing the zone distribution.
→ Other pods don't affect the spread calculation.

## ⚡ SECTION 8 — PRIORITY CLASSES (Pod Eviction Priority)

### What is a PriorityClass?

**PriorityClass** defines the priority of pods. Higher-priority pods:
1. Are scheduled BEFORE lower-priority pods when resources are scarce
2. Can PREEMPT (evict) lower-priority pods to make room

### Simple Story

```
In a hospital emergency room:
  Critical patients (priority 1000) → treated immediately, others wait
  Urgent patients (priority 500) → treated after critical
  Non-urgent patients (priority 100) → wait for all others first

When emergency room is full:
  A critical patient arrives
  → A non-urgent patient gets asked to wait outside (preempted)
  → Critical patient gets their spot

This is PriorityClass in Kubernetes.
```

### PriorityClass YAML

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical-banking
value: 1000000          # higher number = higher priority
globalDefault: false    # is this the default for pods without a class?
preemptionPolicy: PreemptLowerPriority
description: "Priority for critical banking payment services"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 100000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "For important but non-critical services"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 1000
globalDefault: true     # all pods without explicit class get this
preemptionPolicy: Never  # cannot evict other pods
description: "Default for dev/batch workloads"
```

**Every line explained:**

```yaml
kind: PriorityClass
  name: critical-banking
```
→ PriorityClass is CLUSTER-SCOPED — no namespace.

```yaml
value: 1000000
```
→ Numeric priority. Higher = more important.
→ Built-in system critical priority: 2,000,000,000 (for kube-system pods).
→ User-defined should be below 1,000,000,000.

```yaml
globalDefault: false
```
→ `true` → all pods WITHOUT a priorityClassName use this class.
→ Only ONE PriorityClass can have globalDefault: true.

```yaml
preemptionPolicy: PreemptLowerPriority
```
→ `PreemptLowerPriority` → this pod CAN evict lower-priority pods if no space.
→ `Never` → this pod is scheduled when space is available, cannot preempt.

### Using PriorityClass in a Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-critical-pod
spec:
  priorityClassName: critical-banking    # reference the PriorityClass
  containers:
  - name: payment
    image: payment:1.0
```

### Built-in System Priority Classes

```bash
kubectl get priorityclass
```
Output:
```
NAME                      VALUE         GLOBAL-DEFAULT
system-cluster-critical   2000000000    false
system-node-critical      2000001000    false
```
→ These are used by critical system pods (CoreDNS, kube-proxy, etcd).
→ These pods are almost never preempted.

- `dedicated=banking:NoSchedule` → taint with key=dedicated, value=banking, effect=NoSchedule

```bash
# Verify taint was added
kubectl describe node node01 | grep Taints
# Output: Taints: dedicated=banking:NoSchedule
```

```bash
# Step 3: Try to schedule a pod WITHOUT toleration
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: no-toleration-pod
spec:
  containers:
  - name: nginx
    image: nginx
EOF
```

```bash
# Check where it went
kubectl get pod no-toleration-pod -o wide
```
- `-o wide` → shows NODE column

```bash
# Describe to see the scheduling decision
kubectl describe pod no-toleration-pod | grep -A5 Events
# Look for: "didn't tolerate" message in Events
```

```bash
# Step 4: Create pod WITH matching toleration
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: toleration-pod
spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "banking"
    effect: "NoSchedule"
  containers:
  - name: nginx
    image: nginx
EOF
```

```bash
# Check where it was scheduled
kubectl get pod toleration-pod -o wide
# This pod CAN go on the tainted node
```

```bash
# Step 5: Test NoExecute effect (eviction)
kubectl taint nodes node01 test-eviction=true:NoExecute
```

```bash
# Check what happens to existing pods on node01
kubectl get pods -o wide -w
# Pods WITHOUT matching toleration get evicted and move to other nodes
```

```bash
# Clean up — remove taints
kubectl taint nodes node01 dedicated=banking:NoSchedule-
kubectl taint nodes node01 test-eviction=true:NoExecute-
```
- Adding `-` at the END of the taint key:value:effect removes the taint

### LAB 3 — Node Affinity (Required + Preferred)

```bash
# Step 1: Label nodes
kubectl label node node01 zone=us-east-1a tier=frontend
kubectl label node node02 zone=us-east-1b tier=backend   # if you have node02
```

```bash
# Step 2: Required affinity
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: required-affinity-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: zone
            operator: In
            values:
            - us-east-1a
            - us-east-1b
  containers:
  - name: app
    image: nginx
EOF
```

```bash
kubectl get pod required-affinity-pod -o wide
# Should be on node01 or node02 (both have zone labels)
```

```bash
# Step 3: Preferred affinity
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: preferred-affinity-pod
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: zone
            operator: Exists
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
          - key: tier
            operator: In
            values:
            - frontend
  containers:
  - name: app
    image: nginx
EOF
```

```bash
kubectl get pod preferred-affinity-pod -o wide
# SHOULD prefer node01 (has tier=frontend with weight 100)
# But if node01 is full, will go to node02
```

### LAB 4 — Pod Anti-Affinity (Spread Replicas)

```bash
# Create deployment with anti-affinity to spread replicas
cat <<EOF | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: spread-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: spread-app
  template:
    metadata:
      labels:
        app: spread-app
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: spread-app
            topologyKey: kubernetes.io/hostname
      containers:
      - name: app
        image: nginx
EOF
```

```bash
# Check distribution — each pod should be on DIFFERENT node
kubectl get pods -l app=spread-app -o wide
# NODE column should show different nodes for each pod
```

```bash
# What happens if you scale beyond available nodes?
kubectl scale deployment spread-deployment --replicas=5
kubectl get pods -l app=spread-app
# If only 2 nodes available:
# 2 pods Running (one per node), 3 pods Pending
# Anti-affinity prevents scheduling more than 1 per node
```

## 📊 SECTION 10 — COMPLETE COMPARISON TABLE

| Feature | What It Controls | Side | Hard/Soft | Effect on Pods |
|---------|-----------------|------|-----------|----------------|
| Taint NoSchedule | Repel new pods from node | Node | Hard | New pods can't schedule |
| Taint PreferNoSchedule | Softly repel new pods | Node | Soft | New pods prefer other nodes |
| Taint NoExecute | Repel + evict existing pods | Node | Hard | Evicts running pods too |
| Toleration | Allow pod on tainted node | Pod | Permission | Exempt from specific taints |
| NodeSelector | Require specific node label | Pod | Hard | Binary match or Pending |
| Node Affinity Required | Require node label (advanced) | Pod | Hard | Supports operators, OR logic |
| Node Affinity Preferred | Prefer node label | Pod | Soft | Scored, fallback possible |
| Pod Affinity Required | Must be near certain pods | Pod | Hard | Co-locate with matching pods |
| Pod Anti-Affinity Required | Must be away from certain pods | Pod | Hard | Spread away from matching pods |
| Topology Spread | Even distribution across domains | Pod | Hard/Soft | maxSkew between domains |
| PriorityClass | Scheduling order + preemption | Pod | Priority | Higher preempts lower |

## 🔑 SECTION 11 — KEY TERMS TO REMEMBER

| Term | Simple Meaning |
|------|---------------|
| **Scheduler** | Control plane component that assigns pods to nodes |
| **Filtering** | Scheduler phase: remove nodes that CANNOT host the pod |
| **Scoring** | Scheduler phase: rank remaining nodes by fitness |
| **Taint** | Mark on a NODE that repels pods without matching toleration |
| **Toleration** | Mark on a POD that exempts it from a specific taint |
| **NoSchedule** | Taint effect: new pods without toleration cannot schedule here |
| **PreferNoSchedule** | Taint effect: try to avoid, but can schedule if no alternative |
| **NoExecute** | Taint effect: evicts running pods too, not just new ones |
| **tolerationSeconds** | How long to tolerate a NoExecute taint before eviction |
| **NodeSelector** | Simple label-based node requirement (binary, no operators) |
| **Node Affinity** | Advanced node label matching with operators and weights |
| **requiredDuringScheduling** | Hard rule — pod stays Pending if not satisfied |
| **preferredDuringScheduling** | Soft rule — try to satisfy, schedule elsewhere if can't |
| **IgnoredDuringExecution** | Changes to node labels after scheduling don't affect running pod |
| **In operator** | Node label value must be in the provided list |
| **NotIn operator** | Node label value must NOT be in the list |
| **Exists operator** | Node label key must exist (any value) |
| **DoesNotExist operator** | Node label key must NOT exist |
| **nodeSelectorTerms** | List of term groups — OR between terms |
| **matchExpressions** | List of conditions within a term — AND within a term |
| **Pod Affinity** | Schedule near pods matching a label selector |
| **Pod Anti-Affinity** | Schedule away from pods matching a label selector |
| **topologyKey** | Defines scope of affinity (hostname=node, zone=AZ) |
| **Topology Spread** | Even distribution across topology domains |
| **maxSkew** | Maximum pod count difference between topology domains |
| **whenUnsatisfiable** | What to do when spread can't be achieved (DoNotSchedule/ScheduleAnyway) |
| **PriorityClass** | Assigns numeric priority to pods for scheduling order |
| **Preemption** | High-priority pod evicts lower-priority pod to get resources |
| **globalDefault** | PriorityClass used by pods without explicit priorityClassName |
