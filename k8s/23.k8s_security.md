## 🧠 SECTION 1 — WHY DOES KUBERNETES NEED SECURITY? (Story First)

### Forget Kubernetes for 3 minutes — start with a story

Imagine you work in a **large bank building** with 500 employees.

The building has:
- A main entrance with security guards (Authentication)
- Different floors for different departments (Namespaces)
- Key card access per floor (RBAC)
- Firewall rules between departments (NetworkPolicy)
- Rules about what employees can bring inside (PodSecurityContext)
- Each employee's personal badge (ServiceAccount)

Now imagine if there were **NO security**:
```
❌ Any visitor can walk into any floor
❌ Junior clerk can access the CEO's files
❌ Payment department can see customer passwords
❌ Any employee can bring weapons into the building
❌ Someone can impersonate another employee
```

**Kubernetes without security is exactly this.**

Without security:
```
❌ Any pod can call the Kubernetes API and list all secrets
❌ A compromised pod can modify deployments cluster-wide
❌ Payment pods can reach internal admin APIs
❌ Containers run as root — one exploit = full node compromise
❌ Any developer can delete production workloads
```

**Kubernetes Security has five layers — each solves one problem:**

```
LAYER 1: RBAC
  → Who can do what to which Kubernetes objects?
  → "Only the payment-service can read secrets in banking namespace"

LAYER 2: ServiceAccount
  → Which identity does a pod use when calling the Kubernetes API?
  → "payment-pod uses payment-sa identity, not the all-powerful default"

LAYER 3: NetworkPolicy
  → Which pods can talk to which pods over the network?
  → "payment pods can ONLY reach database. Nothing else."

LAYER 4: PodSecurityContext
  → What OS-level permissions does the entire pod have?
  → "This pod runs as user 1000, not as root"

LAYER 5: securityContext (container level)
  → What OS-level permissions does each container have?
  → "This container cannot write to its filesystem"
```

## 🔐 SECTION 2 — RBAC (Role-Based Access Control)

### What is RBAC?

RBAC controls **who can do what to which Kubernetes objects**. It answers the question: "Is this person/service ALLOWED to perform this action on this resource?"

### Simple Story — The Hospital

```
HOSPITAL has different staff:
  Doctor     → can read AND write patient records on their floor
  Nurse      → can read patient records, cannot prescribe medicine
  Receptionist → can see patient names, nothing else
  Janitor    → can enter the building, cannot see ANY records

Each person has a JOB DESCRIPTION (Role) and an ASSIGNMENT (RoleBinding).

Job Description (Role):
  "Floor 3 Nurse: can READ patient-records, can UPDATE vitals"

Assignment (RoleBinding):
  "Sarah is the Floor 3 Nurse"

The combination says:
  "Sarah can READ patient-records and UPDATE vitals on Floor 3"
```

**In Kubernetes:**
```
Role         = Job Description (what actions on what resources)
RoleBinding  = Assignment (who gets that job description)
Subject      = WHO (User, Group, ServiceAccount)
```

### RBAC Has FOUR Objects

```
NAMESPACED (works within one namespace):
  Role          → defines permissions within ONE namespace
  RoleBinding   → assigns a Role to a subject within ONE namespace

CLUSTER-WIDE (works across all namespaces):
  ClusterRole        → defines permissions across ALL namespaces
                       OR for non-namespaced resources (nodes, PVs)
  ClusterRoleBinding → assigns a ClusterRole to a subject cluster-wide

SPECIAL TRICK:
  ClusterRole + RoleBinding = gives ClusterRole permissions but ONLY
  within the RoleBinding's namespace. Reuse permission templates!
```

### RBAC Building Blocks — Verbs and Resources

```
VERBS (actions you can take):
  get     → read ONE specific resource (kubectl get pod nginx)
  list    → read MANY resources (kubectl get pods)
  watch   → stream updates (kubectl get pods -w)
  create  → create new resource
  update  → modify existing resource (full replace)
  patch   → partially modify resource
  delete  → delete a resource
  deletecollection → delete multiple resources at once

RESOURCES (what you act on):
  pods, services, deployments, configmaps, secrets,
  persistentvolumeclaims, namespaces, nodes, etc.

SPECIAL:
  "*" means ALL verbs or ALL resources
  resourceNames: ["specific-name"] → restrict to specific object names
```

### Role YAML — Full Example

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: payment-service-role
  namespace: banking
rules:
- apiGroups: [""]
  resources: ["pods", "services"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list"]
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["db-credentials", "api-keys"]
  verbs: ["get"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "update", "patch"]
```

**Every line explained:**

```yaml
apiVersion: rbac.authorization.k8s.io/v1
```
→ RBAC objects belong to the `rbac.authorization.k8s.io` API group.
→ This is different from core objects (v1) or apps objects (apps/v1).

```yaml
kind: Role
```
→ Creating a Role — namespaced permissions only.
→ Use ClusterRole for cluster-wide permissions.

```yaml
  name: payment-service-role
  namespace: banking
```
→ This Role exists ONLY in the `banking` namespace.
→ A RoleBinding in a different namespace cannot reference this Role.

```yaml
rules:
```
→ `rules` is a LIST of permission rules. Each rule is one block.
→ Multiple rules = OR logic. Any matching rule grants permission.

```yaml
- apiGroups: [""]
  resources: ["pods", "services"]
  verbs: ["get", "list", "watch"]
```
→ `apiGroups: [""]` → empty string = the CORE API group.
→ Core group contains: pods, services, configmaps, secrets, endpoints, namespaces, nodes, PVs, PVCs.
→ `resources: ["pods", "services"]` → these specific resource types.
→ `verbs: ["get", "list", "watch"]` → read-only operations.

```yaml
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["db-credentials", "api-keys"]
  verbs: ["get"]
```
→ `resourceNames: ["db-credentials", "api-keys"]` → ONLY these specific secrets.
→ Without resourceNames: can read ALL secrets in the namespace.
→ With resourceNames: can ONLY read secrets with exactly these names.
→ This is the principle of least privilege — access only what's needed.

```yaml
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch", "update", "patch"]
```
→ `apiGroups: ["apps"]` → the `apps` group contains Deployments, ReplicaSets, StatefulSets, DaemonSets.
→ `verbs: ["update", "patch"]` → can modify deployments (but not create or delete).

### API Groups — Which Group for Which Resource?

```
apiGroups: [""]           → core group
  pods, services, configmaps, secrets, endpoints,
  namespaces, nodes, persistentvolumes,
  persistentvolumeclaims, serviceaccounts, events

apiGroups: ["apps"]       → apps group
  deployments, replicasets, statefulsets, daemonsets

apiGroups: ["batch"]      → batch group
  jobs, cronjobs

apiGroups: ["networking.k8s.io"]  → networking group
  ingresses, networkpolicies

apiGroups: ["rbac.authorization.k8s.io"]  → RBAC group
  roles, rolebindings, clusterroles, clusterrolebindings

apiGroups: ["autoscaling"]  → autoscaling group
  horizontalpodautoscalers

apiGroups: ["storage.k8s.io"]  → storage group
  storageclasses, volumeattachments

apiGroups: ["*"]           → ALL groups (use carefully)
```

### RoleBinding YAML — Full Example

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: payment-service-binding
  namespace: banking
subjects:
- kind: ServiceAccount
  name: payment-sa
  namespace: banking
- kind: User
  name: muskan
  apiGroup: rbac.authorization.k8s.io
- kind: Group
  name: banking-developers
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: payment-service-role
  apiGroup: rbac.authorization.k8s.io
```

**Every line explained:**

```yaml
kind: RoleBinding
  namespace: banking
```
→ RoleBinding lives in the `banking` namespace.
→ It grants the Role's permissions within the `banking` namespace only.

```yaml
subjects:
```
→ `subjects` → the LIST of WHO gets these permissions.
→ You can bind to multiple subjects in one RoleBinding.

```yaml
- kind: ServiceAccount
  name: payment-sa
  namespace: banking
```
→ `kind: ServiceAccount` → a pod's identity (covered in next section).
→ `name: payment-sa` → the ServiceAccount named payment-sa.
→ `namespace: banking` → MUST specify namespace for ServiceAccount subjects.

```yaml
- kind: User
  name: muskan
  apiGroup: rbac.authorization.k8s.io
```
→ `kind: User` → a human user authenticating via certificate or token.
→ `name: muskan` → the username as it appears in their certificate's CN field.
→ Kubernetes does NOT manage users — they are external (certificates, OIDC).

```yaml
- kind: Group
  name: banking-developers
  apiGroup: rbac.authorization.k8s.io
```
→ `kind: Group` → all users who are members of this group.
→ Groups come from certificate's O (Organization) field or OIDC claims.

```yaml
roleRef:
  kind: Role
  name: payment-service-role
  apiGroup: rbac.authorization.k8s.io
```
→ `roleRef` → WHICH Role to assign. This is immutable after creation.
→ `kind: Role` → referencing a namespaced Role (use ClusterRole for cluster-wide).
→ `name: payment-service-role` → must exist in the same namespace.
→ `apiGroup: rbac.authorization.k8s.io` → always this value for RBAC objects.

### ClusterRole and ClusterRoleBinding

```yaml
# ClusterRole — cluster-wide permissions
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
  # NO namespace field — ClusterRole is cluster-scoped
rules:
- apiGroups: [""]
  resources: ["nodes"]          # nodes are cluster-scoped, not namespaced
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods"]           # can also include namespaced resources
  verbs: ["get", "list"]        # but permission applies across ALL namespaces
```

```yaml
# ClusterRoleBinding — assigns ClusterRole to a subject cluster-wide
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: node-reader-binding
subjects:
- kind: ServiceAccount
  name: monitoring-sa
  namespace: monitoring
roleRef:
  kind: ClusterRole              # reference ClusterRole, not Role
  name: node-reader
  apiGroup: rbac.authorization.k8s.io
```

### The Special Trick — ClusterRole + RoleBinding

```yaml
# Same ClusterRole referenced in a RoleBinding (NOT ClusterRoleBinding)
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-pod-reader
  namespace: development          # permissions limited to THIS namespace
subjects:
- kind: User
  name: junior-dev
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole               # using a ClusterRole...
  name: pod-reader                # ...but in a RoleBinding = namespaced scope
  apiGroup: rbac.authorization.k8s.io
```

→ `junior-dev` gets the `pod-reader` ClusterRole permissions BUT ONLY in the `development` namespace.
→ This is powerful for reusing permission templates — define once as ClusterRole, assign to different namespaces via different RoleBindings.

## 🎫 SECTION 3 — SERVICEACCOUNT

### What is a ServiceAccount?

A **ServiceAccount** is the **identity of a pod** when it talks to the Kubernetes API Server. Every pod that calls the Kubernetes API authenticates using its ServiceAccount's token.

### Simple Story — The Employee Badge

```
In a company:
  Every employee has a BADGE.
  The badge has their name and department.
  When they badge into a secure area → security checks if THIS badge is allowed.

In Kubernetes:
  Every pod has a ServiceAccount (badge).
  When the pod calls the Kubernetes API → API Server checks if this SA is allowed.
  ServiceAccount is bound to RBAC Role/ClusterRole to define what it can do.
```

### The Default ServiceAccount Problem

```
PROBLEM:
  Every namespace automatically gets a 'default' ServiceAccount.
  Every pod that doesn't specify a ServiceAccount uses 'default'.
  In old Kubernetes: 'default' SA had broad permissions.
  A compromised pod could use 'default' SA to do dangerous things.

SOLUTION: Create specific SAs with minimal permissions per workload.
  payment-pod   → uses payment-sa   → can only read payment-related secrets
  reporting-pod → uses reporting-sa → can only read configmaps
  monitoring-pod → uses monitoring-sa → can read pods/nodes across cluster
```

### ServiceAccount YAML

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-sa
  namespace: banking
  annotations:
    # AWS IRSA: link SA to IAM role for AWS API access
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/PaymentServiceRole
automountServiceAccountToken: false   # don't auto-mount token (security best practice)
```

**Line by line:**

```yaml
kind: ServiceAccount
  name: payment-sa
  namespace: banking
```
→ ServiceAccount is NAMESPACED — lives in one namespace.
→ Pods in `banking` namespace can use this SA.
→ Pods in other namespaces cannot use this SA directly.

```yaml
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/PaymentServiceRole
```
→ This annotation links the SA to an AWS IAM Role.
→ This is IRSA (IAM Roles for Service Accounts) — the secure way for pods to access AWS services.
→ The pod's SA token is exchanged for AWS credentials automatically.
→ No need to hardcode AWS keys in pods.

```yaml
automountServiceAccountToken: false
```
→ By default, Kubernetes AUTOMATICALLY mounts the SA token into every pod at `/var/run/secrets/kubernetes.io/serviceaccount/token`.
→ `false` → don't automatically mount. The pod cannot call the Kubernetes API.
→ Use this for apps that don't need Kubernetes API access — prevents token theft.
→ You can still explicitly opt-in per pod with `automountServiceAccountToken: true` in pod spec.

### Using ServiceAccount in a Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-pod
  namespace: banking
spec:
  serviceAccountName: payment-sa       # use this specific SA
  automountServiceAccountToken: true   # mount the token (override SA setting)
  containers:
  - name: payment-app
    image: payment:1.0
```

**What gets mounted automatically:**
```bash
# Inside the container, at this path:
ls /var/run/secrets/kubernetes.io/serviceaccount/
ca.crt    ← cluster CA certificate (to verify API server identity)
namespace ← current namespace name
token     ← JWT token for this ServiceAccount

# The pod uses this token to authenticate to the API Server
curl -H "Authorization: Bearer $(cat /var/run/secrets/kubernetes.io/serviceaccount/token)" \
  https://kubernetes.default.svc/api/v1/namespaces/banking/pods
```

### ServiceAccount Token Projection (Modern Approach)

Old-style tokens never expire — security risk. Modern Kubernetes uses projected tokens:

```yaml
spec:
  volumes:
  - name: kube-api-access
    projected:
      sources:
      - serviceAccountToken:
          path: token
          expirationSeconds: 3600    # token expires after 1 hour
          audience: https://kubernetes.default.svc
      - configMap:
          name: kube-root-ca.crt
          items:
          - key: ca.crt
            path: ca.crt
```

→ `expirationSeconds: 3600` → token rotates every hour — even if stolen, expires quickly.
→ `audience` → token only valid for this specific API server endpoint.

### Checking What a ServiceAccount Can Do

```bash
# Can the payment-sa in banking namespace list pods?
kubectl auth can-i list pods \
  --as=system:serviceaccount:banking:payment-sa \
  -n banking

# Can it read secrets?
kubectl auth can-i get secrets \
  --as=system:serviceaccount:banking:payment-sa \
  -n banking

# Can it access cluster-wide nodes?
kubectl auth can-i list nodes \
  --as=system:serviceaccount:banking:payment-sa
```

→ `--as=system:serviceaccount:<namespace>:<name>` → impersonate a ServiceAccount.
→ `system:serviceaccount:banking:payment-sa` → the full name format Kubernetes uses internally.
→ `kubectl auth can-i` → dry-run permission check without actually doing the action.

## 🔥 SECTION 4 — NETWORKPOLICY

### What is NetworkPolicy?

A **NetworkPolicy** is a **firewall rule for pods** — it controls which pods can send traffic TO which other pods, and on which ports.

### Simple Story — The Office Firewall

```
An office building has different departments:
  Payment Department    → handles sensitive payment data
  Analytics Department  → reads reports
  Public Website Team   → serves web traffic
  Database Room         → stores all data

WITHOUT firewall:
  Analytics team can directly query payment database ❌
  Public website can reach internal APIs ❌
  Any laptop can connect to the database ❌

WITH firewall rules:
  Database Room: ONLY accept connections FROM Payment Department on port 5432
  Payment APIs:  ONLY accept connections FROM Website Team on port 8080
  Analytics:     ONLY read from Analytics DB, nothing else

NetworkPolicy is these firewall rules for Kubernetes pods.
```

### Default Behavior — No NetworkPolicy = All Allowed

```
CRITICAL FACT:
  By default, Kubernetes allows ALL pod-to-pod traffic.
  There is NO default deny.
  Any pod can reach any other pod in any namespace.

  If pod A in banking namespace calls pod B in monitoring namespace
  → works by default with no config needed.

NetworkPolicy works as OPT-IN DENY:
  Once you create a NetworkPolicy that selects a pod
  → that pod has default DENY for the policy types covered
  → you then add explicit ALLOW rules

Pods with NO NetworkPolicy selecting them → still wide open
```

### NetworkPolicy YAML — Full Example

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: database-access-policy
  namespace: banking
spec:
  podSelector:
    matchLabels:
      app: postgres           # this policy applies TO postgres pods
  policyTypes:
  - Ingress                   # control incoming traffic TO postgres
  - Egress                    # control outgoing traffic FROM postgres
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: payment-app    # allow FROM payment pods
      namespaceSelector:
        matchLabels:
          name: banking       # AND in banking namespace
    ports:
    - protocol: TCP
      port: 5432              # on PostgreSQL port only
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - protocol: UDP
      port: 53               # allow DNS (CoreDNS in kube-system)
```

**Every line explained:**

```yaml
  podSelector:
    matchLabels:
      app: postgres
```
→ `podSelector` → which pods does THIS NetworkPolicy apply TO?
→ `matchLabels: app: postgres` → applies to all pods with label `app: postgres` in the `banking` namespace.
→ `podSelector: {}` (empty) → applies to ALL pods in the namespace.

```yaml
  policyTypes:
  - Ingress
  - Egress
```
→ `policyTypes` → which traffic directions to control.
→ `Ingress` → control traffic COMING IN to selected pods.
→ `Egress` → control traffic GOING OUT from selected pods.
→ If you only specify `Ingress` → egress is unrestricted.
→ If you specify `Egress` with no egress rules → ALL outgoing traffic is DENIED.

```yaml
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: payment-app
      namespaceSelector:
        matchLabels:
          name: banking
```
→ `ingress.from` → WHERE can traffic come FROM?
→ **CRITICAL — AND vs OR logic:**
  - `podSelector` and `namespaceSelector` in the SAME list item → AND (both must match)
  - Separate list items (each with `-`) → OR (either can match)

```yaml
# AND logic (same item) — payment pods AND in banking namespace
  - from:
    - podSelector:
        matchLabels:
          app: payment-app
      namespaceSelector:
        matchLabels:
          name: banking

# OR logic (separate items) — payment pods OR anything in banking namespace
  - from:
    - podSelector:
        matchLabels:
          app: payment-app
    - namespaceSelector:
        matchLabels:
          name: banking
```

```yaml
    ports:
    - protocol: TCP
      port: 5432
```
→ Only allow traffic on TCP port 5432 (PostgreSQL default port).
→ Traffic on any other port is blocked even if source is allowed.

```yaml
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - protocol: UDP
      port: 53
```
→ Allow outgoing traffic to kube-system namespace on UDP port 53.
→ This is DNS resolution — without this, the pod cannot resolve any hostnames.
→ **Always add DNS egress when using Egress NetworkPolicy or your app breaks.**
→ `kubernetes.io/metadata.name` → built-in label on namespaces equal to the namespace name.

### Common NetworkPolicy Patterns

**Pattern 1 — Default Deny All (Security Baseline)**

```yaml
# Apply this to EVERY namespace first, then add specific allows
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: banking
spec:
  podSelector: {}          # empty = select ALL pods in namespace
  policyTypes:
  - Ingress
  - Egress
  # No ingress or egress rules = deny everything
```

**Pattern 2 — Allow Only From Same Namespace**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-namespace
  namespace: banking
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector: {}      # any pod in banking namespace
```

**Pattern 3 — Allow Ingress Controller to Reach App**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-controller
  namespace: banking
spec:
  podSelector:
    matchLabels:
      app: payment-app
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: ingress-nginx
    ports:
    - protocol: TCP
      port: 8080
```

**Pattern 4 — Allow Prometheus to Scrape Metrics**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-prometheus-scrape
  namespace: banking
spec:
  podSelector: {}                    # apply to all pods in namespace
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: monitoring
      podSelector:
        matchLabels:
          app: prometheus
    ports:
    - protocol: TCP
      port: 9090
```

## 🛡️ SECTION 5 — POD SECURITY CONTEXT

### What is SecurityContext?

A **securityContext** defines **OS-level security settings** for a pod or container. It controls things like:
- Which Linux user ID the process runs as
- Whether the process can gain extra privileges
- Whether the filesystem is read-only
- Which Linux capabilities are allowed

There are TWO levels:
```
POD-LEVEL (pod.spec.securityContext):
  → Applies to ALL containers in the pod
  → Controls: runAsUser, runAsGroup, fsGroup, sysctls

CONTAINER-LEVEL (pod.spec.containers[].securityContext):
  → Applies to ONE specific container
  → Controls: runAsUser, runAsNonRoot, allowPrivilegeEscalation,
              readOnlyRootFilesystem, capabilities, privileged
  → Overrides pod-level settings for that container
```

### Why This Matters — The Container Escape Risk

```
DEFAULT BEHAVIOR (dangerous):
  Container runs as ROOT (user ID 0)
  
  If an attacker exploits your app:
    → They are ROOT inside the container
    → If container escapes to host:
      → They are ROOT on the HOST NODE
      → Full node compromise
      → Access to all other pods on that node
      → Access to node's kubelet credentials

WITH SECURITY CONTEXT:
  Container runs as user ID 1000 (non-root)
  Filesystem is read-only (cannot write malware)
  No privilege escalation allowed
  
  If an attacker exploits your app:
    → They are user 1000 (limited permissions)
    → Cannot write to filesystem (read-only)
    → Cannot escalate to root
    → Impact is contained
```

### Pod-Level SecurityContext YAML

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
  namespace: banking
spec:
  securityContext:                    # POD-LEVEL — applies to all containers
    runAsNonRoot: true                # reject if container tries to run as root
    runAsUser: 1000                   # run all containers as user ID 1000
    runAsGroup: 3000                  # run as group ID 3000
    fsGroup: 2000                     # volumes owned by group 2000
    seccompProfile:
      type: RuntimeDefault            # apply default seccomp profile
    supplementalGroups: [4000]        # additional group memberships
  containers:
  - name: payment-app
    image: payment:1.0
```

**Every line explained:**

```yaml
    runAsNonRoot: true
```
→ Kubernetes VALIDATES that the container's image does not run as root (UID 0).
→ If the image's USER is root → pod is REJECTED with error before even starting.
→ This is a POLICY check — prevents accidentally running root containers.

```yaml
    runAsUser: 1000
```
→ Override the image's default USER and run as Linux UID 1000 instead.
→ Even if the image says `USER root` → the container process runs as UID 1000.
→ The process inside the container sees itself as user 1000.

```yaml
    runAsGroup: 3000
```
→ Set the primary GROUP ID for the container processes.
→ Affects file ownership of files created by the process.

```yaml
    fsGroup: 2000
```
→ All VOLUMES mounted into this pod have their group ownership changed to 2000.
→ The container process (which is in group 2000 via this setting) can read/write those volumes.
→ Critical for StatefulSet pods that need to write to PVs with correct permissions.

```yaml
    seccompProfile:
      type: RuntimeDefault
```
→ Seccomp = secure computing mode. Filters which Linux SYSTEM CALLS the container can make.
→ `RuntimeDefault` → apply the container runtime's (containerd/docker) default seccomp profile.
→ This blocks ~300 dangerous syscalls while allowing normal application operations.
→ Recommended for all production pods.

```yaml
    supplementalGroups: [4000]
```
→ Add group 4000 to the container process's group list.
→ Container process belongs to groups: primary(3000) + supplemental(4000).

### Container-Level SecurityContext YAML

```yaml
  containers:
  - name: payment-app
    image: payment:1.0
    securityContext:                      # CONTAINER-LEVEL — this container only
      runAsNonRoot: true
      runAsUser: 1000
      allowPrivilegeEscalation: false     # cannot gain more privileges than parent
      readOnlyRootFilesystem: true        # container filesystem is read-only
      capabilities:
        drop:
        - ALL                            # drop ALL Linux capabilities
        add:
        - NET_BIND_SERVICE               # allow binding to port < 1024 only
      privileged: false                  # not a privileged container
```

**Every line explained:**

```yaml
      allowPrivilegeEscalation: false
```
→ Prevents the process from gaining MORE privileges than it started with.
→ Blocks: `sudo`, `su`, SUID binaries, `setuid()` syscall.
→ Even if an attacker finds a privilege escalation vulnerability → this blocks it.
→ **Always set to false in production.**

```yaml
      readOnlyRootFilesystem: true
```
→ Mounts the container's root filesystem as READ-ONLY.
→ The container process CANNOT write files to its own filesystem.
→ Attackers cannot: write malware, modify binaries, create reverse shells.
→ Legitimate writes go to explicitly mounted volumes (`/tmp`, `/data`).
→ **Best practice for all stateless containers.**

```yaml
      capabilities:
        drop:
        - ALL
        add:
        - NET_BIND_SERVICE
```
→ Linux capabilities are fine-grained root privileges.
→ `drop: ALL` → remove ALL capabilities from this container.
→ `add: NET_BIND_SERVICE` → add back ONLY the ability to bind to ports < 1024.
→ Full root = all 40+ capabilities. After drop ALL + add back specific ones = minimal privilege.

Common capabilities:
```
NET_BIND_SERVICE → bind to ports < 1024 (for web servers on port 80/443)
SYS_PTRACE       → debug other processes (needed for some monitoring tools)
SYS_ADMIN        → dangerous — almost like root. Never add this.
NET_ADMIN        → modify network settings (needed for CNI plugins)
```

```yaml
      privileged: false
```
→ `privileged: true` would give the container nearly full root access to the host.
→ The container could see all host devices, mount filesystems, modify kernel parameters.
→ Only needed for very specific system-level containers (some CNI plugins, storage drivers).
→ **NEVER true in production applications.**

### Complete Secure Pod Example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: fully-secure-pod
  namespace: banking
spec:
  serviceAccountName: payment-sa
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: payment-app
    image: payment:1.0
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop:
        - ALL
    volumeMounts:
    - name: tmp-dir            # writable /tmp for the app
      mountPath: /tmp
    - name: cache-dir          # writable cache directory
      mountPath: /app/cache
  volumes:
  - name: tmp-dir
    emptyDir: {}               # temporary writable space
  - name: cache-dir
    emptyDir: {}
```

→ `readOnlyRootFilesystem: true` → needs explicit writable volumes for any writes.
→ `emptyDir: {}` → provides writable space for /tmp and /app/cache.
→ App can write to /tmp and /app/cache, nothing else.

## 🔒 SECTION 6 — POD SECURITY ADMISSION (PSA)

### What Replaced PodSecurityPolicy?

PodSecurityPolicy (PSP) was deprecated in K8s 1.21 and removed in 1.25. It was replaced by **Pod Security Admission (PSA)** — simpler, built-in.

PSA enforces three **Pod Security Standards** at the namespace level:

```
PRIVILEGED:
  → No restrictions. Any pod spec allowed.
  → Only for trusted namespaces (kube-system, monitoring with node access)

BASELINE:
  → Prevents known privilege escalation paths.
  → Allows most common configurations.
  → Blocks: hostPID, hostIPC, hostNetwork, privileged containers.
  → Good for: general workloads.

RESTRICTED:
  → Strongly hardened. Follows current best practices.
  → Requires: runAsNonRoot, drop ALL capabilities, no privilege escalation.
  → Good for: high-security workloads like banking applications.
```

### How to Apply PSA to a Namespace

```bash
# Label the namespace with the desired policy
kubectl label namespace banking \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted
```

→ `enforce` → violating pods are REJECTED.
→ `warn` → violating pods are ALLOWED but a warning is shown.
→ `audit` → violating pods are ALLOWED and logged in audit log.
→ Use `warn` and `audit` first to find violations, then switch to `enforce`.

```bash
# Create a Role that allows reading pods and configmaps

apiVersion: rbac.authorization.k8s.io/v1

  name: pod-configmap-reader
```

```bash
# Create a RoleBinding linking SA to Role

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-sa-binding
  namespace: security-lab
subjects:
- kind: ServiceAccount
  name: app-sa
  namespace: security-lab
roleRef:
  kind: Role
  name: pod-configmap-reader
  apiGroup: rbac.authorization.k8s.io
EOF
```

```bash
# Test: can app-sa list pods in security-lab?
```

### LAB 3 — NetworkPolicy — Default Deny Then Allow

```bash
# Create two test pods
kubectl run web-pod \
  --image=nginx \
  --labels="app=web" \
  -n security-lab

kubectl run db-pod \
  --image=nginx \
  --labels="app=database" \
  -n security-lab

# Wait for them
kubectl wait pod web-pod db-pod -n security-lab \
  --for=condition=Ready --timeout=60s
```

```bash
# Get db-pod IP
DB_IP=$(kubectl get pod db-pod -n security-lab -o jsonpath='{.status.podIP}')
echo "DB Pod IP: $DB_IP"
```
- `-o jsonpath='{.status.podIP}'` → extract just the IP field

```bash
# Test BEFORE NetworkPolicy — should WORK
kubectl exec web-pod -n security-lab -- wget -qO- --timeout=3 http://$DB_IP
# Output: nginx default page (CONNECTED)
```

```bash
# Apply Default Deny NetworkPolicy to database pods
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-to-db
  namespace: security-lab
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes:
  - Ingress
EOF
```

```bash
# Test AFTER default deny — should TIMEOUT
kubectl exec web-pod -n security-lab -- wget -qO- --timeout=3 http://$DB_IP
# Output: wget: download timed out (BLOCKED)
```

```bash
# Add an allow rule: web-pod can reach db-pod
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-db
  namespace: security-lab
spec:
  podSelector:
    matchLabels:
      app: database
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: web
    ports:
    - protocol: TCP
      port: 80
EOF
```

```bash
# Test AFTER allow rule — should WORK again
kubectl exec web-pod -n security-lab -- wget -qO- --timeout=3 http://$DB_IP
# Output: nginx default page (CONNECTED again)
```

### LAB 4 — SecurityContext — Non-Root Pod

```bash
# Create pod running as non-root
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: nonroot-pod
  namespace: security-lab
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
  - name: app
    image: nginx:1.25
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: false   # nginx needs to write — set true carefully
      capabilities:
        drop:
        - ALL
EOF
```

```bash
# Wait and check
kubectl wait pod nonroot-pod -n security-lab --for=condition=Ready --timeout=60s

# Verify user inside container
kubectl exec nonroot-pod -n security-lab -- id
# Output: uid=1000 gid=3000 groups=3000,2000
# NOT root!

# Try to create a file as root — should fail
kubectl exec nonroot-pod -n security-lab -- touch /etc/test-file
# Output: touch: /etc/test-file: Permission denied
# (because running as UID 1000, not root)
```

```bash
# Try to create a pod that runs as root — should be BLOCKED if runAsNonRoot: true
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: root-rejected-pod
  namespace: security-lab
spec:
  securityContext:
    runAsNonRoot: true
  containers:
  - name: app
    image: ubuntu          # ubuntu runs as root by default
EOF
```

```bash
kubectl describe pod root-rejected-pod -n security-lab
# Look for: Error: container has runAsNonRoot and image will run as root
# Pod is REJECTED before even starting
```

## 📊 SECTION 8 — SECURITY COMPARISON TABLE

| Security Layer | What It Controls | Object Type | Level |
|---------------|-----------------|-------------|-------|
| RBAC Role | Who can do what to K8s API objects in ONE namespace | Role + RoleBinding | Namespace |
| RBAC ClusterRole | Who can do what to K8s API objects cluster-wide | ClusterRole + ClusterRoleBinding | Cluster |
| ServiceAccount | Pod's identity when calling K8s API | ServiceAccount | Namespace |
| NetworkPolicy | Pod-to-pod network traffic (L3/L4 firewall) | NetworkPolicy | Namespace |
| Pod securityContext | OS user, group, fsGroup for all containers | Pod spec | Pod |
| Container securityContext | Capabilities, privilege escalation, read-only FS | Container spec | Container |
| Pod Security Admission | Namespace-level pod security standard enforcement | Namespace label | Namespace |

## 🔑 SECTION 9 — KEY TERMS TO REMEMBER

| Term | Simple Meaning |
|------|---------------|
| **RBAC** | Role-Based Access Control — controls K8s API permissions |
| **Role** | Permission set for ONE namespace |
| **ClusterRole** | Permission set for ALL namespaces or cluster-scoped resources |
| **RoleBinding** | Assigns Role/ClusterRole to a subject in ONE namespace |
| **ClusterRoleBinding** | Assigns ClusterRole to a subject cluster-wide |
| **Subject** | WHO gets the permission — User, Group, or ServiceAccount |
| **Verb** | Action: get, list, watch, create, update, patch, delete |
| **apiGroups: [""]** | Core API group — pods, services, configmaps, secrets |
| **apiGroups: ["apps"]** | Apps group — deployments, statefulsets, daemonsets |
| **resourceNames** | Restrict RBAC to specific named resources |
| **ServiceAccount** | Pod's identity when calling Kubernetes API |
| **automountServiceAccountToken** | Whether SA token is auto-mounted into pod |
| **IRSA** | IAM Roles for Service Accounts — AWS pod identity |
| **kubectl auth can-i** | Check if a user/SA has permission |
| **NetworkPolicy** | Firewall rules for pod-to-pod traffic |
| **podSelector** | Which pods the NetworkPolicy applies TO |
| **namespaceSelector** | Filter traffic by namespace label |
| **policyTypes** | Ingress (incoming) or Egress (outgoing) or both |
| **Default deny** | NetworkPolicy pattern — deny all, then add allows |
| **AND vs OR in NetworkPolicy** | Same list item = AND, separate `-` items = OR |
| **securityContext (pod)** | OS-level settings for ALL containers in pod |
| **securityContext (container)** | OS-level settings for ONE container |
| **runAsNonRoot** | Reject pod if container tries to run as root |
| **runAsUser** | Which Linux UID to run container process as |
| **fsGroup** | Group ownership of mounted volumes |
| **allowPrivilegeEscalation: false** | Container cannot gain more than starting privileges |
| **readOnlyRootFilesystem** | Container's filesystem is read-only |
| **capabilities: drop: ALL** | Remove all Linux root capabilities |
| **privileged: false** | Container does NOT get host-level root access |
| **seccompProfile** | Filter which Linux syscalls the container can make |
| **PSA** | Pod Security Admission — namespace-level pod security enforcement |
| **Restricted** | Strictest PSA standard — requires non-root, drop ALL |
